---
title: Keep a Database Password in Git With SOPS and age
sidebarTitle: Keep secrets in Git with SOPS and age
description: Commit a database password to your repository as a SOPS-encrypted env file, let Sencho decrypt it only while it deploys, and back up the key that opens it.
---

Say `ledger` is a Postgres stack whose password lives in a `db.env` file. You want the compose file and the env file in Git like everything else, but anyone who can read the repository can read a plaintext password. This walks through encrypting `db.env` with [SOPS](https://github.com/getsops/sops) and [age](https://github.com/FiloSottile/age), giving Sencho the key to open it, requiring encryption on the source, deploying, and backing up the key so you can still read the file after you lose the node.

This tutorial covers one stack on the node you are signed in to, with the age identity Sencho generates for it. It doesn't cover importing an existing identity, rotating a key, PGP or cloud KMS backends, or linking a stack you already run; see [Repository secrets](/features/git-secrets) and [Deploy Compose Changes by Pulling From Git Instead of Editing by Hand](/tutorials/connect-a-git-source) for those.

## Prerequisites

- The `admin` or `node-admin` role. Creating the stack needs `stack:create`, changing its secrets settings needs `stack:edit`, and deploying needs `stack:deploy`; `deployer`, `viewer`, and `auditor` do not hold all three.
- Available on every tier, including Community.
- A workstation with `git`, [`sops`](https://github.com/getsops/sops/releases) 3.9 or later, and [`age`](https://github.com/FiloSottile/age/releases) installed.
- A Git repository over HTTPS or SSH that you can push to, with these two files committed on `main`. The password is a placeholder on purpose; the real one goes in later, already encrypted.

  ```yaml compose.yaml
  services:
    db:
      image: postgres:17-alpine
      restart: unless-stopped
      env_file:
        - db.env
      volumes:
        - ledger-data:/var/lib/postgresql/data

  volumes:
    ledger-data:
  ```

  ```bash db.env
  POSTGRES_USER=ledger
  POSTGRES_DB=ledger
  POSTGRES_PASSWORD=change-me
  ```

- Shell access to the host that runs Sencho, for the backup in the last step.

<Note>
  Keep the image tag and any published port as plain values in `compose.yaml`, as above. Sencho resolves those before it decrypts anything, so an encrypted value there breaks the deploy. [Repository secrets](/features/git-secrets#where-encrypted-values-can-be-used) lists where encrypted values do work.
</Note>

<Note>
  The **Secrets** tab does not currently load for a stack on a remote node that you manage through this instance. Do this tutorial on the node you are signed in to, or sign in to the remote node's own Sencho.
</Note>

<Steps>
  <Step title="Create the stack from the plaintext commit">
    Select **Create Stack**, open the **From Git** tab, and fill in:

    - **Stack Name**: `ledger`
    - **Repository URL**: your repository's HTTPS or SSH address
    - **Ref**: `main`
    - **Authentication**: **Public (no auth)** for a public repository, otherwise the token or deploy key your Git host needs. [Git hosts and authentication](/features/git-authentication) covers each. Leave **Custom CA certificate** empty unless your Git server uses a private certificate authority.
    - **Apply behavior**: **Review only**, so a fetched commit never writes or deploys on its own.

    Leave **Deploy after create** unticked, then select **Create from Git**.

    <Frame>
      <img src="/images/tutorials/keep-secrets-in-git-with-sops/create-stack-from-git.png" alt="New stack dialog on the From Git tab with Stack Name ledger, a repository URL, Ref main, compose.yaml as the primary compose file, Public (no auth) selected, an empty Custom CA certificate field, Review only selected under Apply behavior, and an unticked Deploy after create checkbox." />
    </Frame>

    Start from a plaintext commit because Sencho opens every encrypted file when it links a repository, and it has no key yet. A repository whose current commit is already encrypted stops at **Required age identity is not available on this node**. Leaving the deploy for later matters too. Postgres reads `POSTGRES_PASSWORD` only when it first initializes an empty data volume, so deploying the placeholder would lock `change-me` in.

    The stack opens with **Source** naming your repository and **ENV_FILE** listing `db.env` with 3 vars.
  </Step>
  <Step title="Generate an identity on the node">
    Select the **Source** row on the stack's **Anatomy** tab to open the **Git source** sheet, then open the **Secrets** tab. It reads **Ready** with **No age identities on this node yet**, because a plaintext commit needs no key. Select **Generate identity**. A toast reads `Age identity generated`.

    <Frame>
      <img src="/images/tutorials/keep-secrets-in-git-with-sops/secrets-tab-empty.png" alt="Secrets tab of the Git source sheet for ledger showing a Ready readiness chip, Allow plaintext secrets selected, the text No age identities on this node yet, a Generate identity button, and an Import identity field." />
    </Frame>

    The tab now lists the identity's public recipient, a string starting `age1`. Select the copy button beside it and paste it somewhere you can reach from your workstation.

    <Frame>
      <img src="/images/tutorials/keep-secrets-in-git-with-sops/identity-generated.png" alt="Secrets tab after generating an identity, listing one recipient starting age1hslu with copy, rotate, and delete buttons." />
    </Frame>

    The private half stays on this node, encrypted in Sencho's database, and the API never returns it. That is why the last step matters: Sencho has no export for it.
  </Step>
  <Step title="Add the recipient and a recovery key">
    On your workstation, create a second key pair that you keep, so the file stays readable if the node is ever lost:

    ```bash
    age-keygen -o recovery.key
    ```

    It prints `Public key: age1...`. Store `recovery.key` in your password manager and never commit it. Then, in the repository, create `.sops.yaml` with both recipients, replacing the two `age1...` values with Sencho's recipient from the previous step and your recovery public key:

    ```yaml .sops.yaml
    creation_rules:
      - path_regex: ^db\.env$
        age: >-
          age1hslu6d258eg7ed8dt305ka2753f2x95zzqjuulchfpv0rfd66c6sg9g484,
          age1t2u2qgca90sgkyeqv6jajm268teaghtufyfkkfqvw6u7vkzx8y8qlt9fxp
    ```

    A file encrypted to several recipients opens with any one of them. Only the `sops` command reads `.sops.yaml`; Sencho reads the recipients that SOPS records inside the encrypted file itself.
  </Step>
  <Step title="Encrypt the env file and push it">
    Open `db.env` and replace `change-me` with the real password, here `POSTGRES_PASSWORD=ledger-demo-pw-2026`. Then encrypt the file in place and push:

    ```bash
    sops encrypt --in-place db.env
    git add .sops.yaml db.env
    git commit -m "Encrypt db.env with SOPS"
    git push
    ```

    `db.env` now looks like this. The variable names stay readable and every value is ciphertext, with the recipients listed at the bottom:

    ```text
    POSTGRES_USER=ENC[AES256_GCM,data:b49jZ86Q,iv:6L5W/KEOKX5HTq7NyqoodMZ7kAnscG5o1eZqnDsKC78=,tag:...,type:str]
    POSTGRES_DB=ENC[AES256_GCM,data:3G9aLULh,iv:TKUCaO31Nu0SkyEKNdVKl8mBZ8+amfaI6JHxsj5J0SI=,tag:...,type:str]
    POSTGRES_PASSWORD=ENC[AES256_GCM,data:6pfFXiF1GeuEvWX/NPx4ehP16w==,iv:9r/5kU3ju4jJh26SHBJd...,tag:...,type:str]
    sops_age__list_0__map_recipient=age1hslu6d258eg7ed8dt305ka2753f2x95zzqjuulchfpv0rfd66c6sg9g484
    sops_age__list_1__map_recipient=age1t2u2qgca90sgkyeqv6jajm268teaghtufyfkkfqvw6u7vkzx8y8qlt9fxp
    ```
  </Step>
  <Step title="Require SOPS encryption">
    Back on the **Secrets** tab, select **Require SOPS encryption** under **Encrypted source policy**. A toast reads `Encrypted source policy updated.`

    <Frame>
      <img src="/images/tutorials/keep-secrets-in-git-with-sops/require-sops-policy.png" alt="Secrets tab with Require SOPS encryption selected, the recipient listed, and a success toast reading Encrypted source policy updated." />
    </Frame>

    The default, **Allow plaintext secrets**, accepts anything. With this policy on, Sencho refuses a pull in which a secret-bearing file is plaintext. A commit with a hand-edited, unencrypted `db.env` shows `Encrypted source policy requires SOPS-encrypted secret inputs`, and the stack stays on its accepted commit. A hand-edited commit can't put the password back in plaintext on the stack.
  </Step>
  <Step title="Pull and deploy">
    Select **Pull now**. The **Git · Change plan** dialog lists `db.env` as **Modify**, labelled **secret-bearing managed path**, with no diff and `1 unchanged file` for `compose.yaml`. Sencho names the file without showing what is in it.

    Make sure **Deploy after apply** is ticked, then select **Apply**. The box keeps its last state between pulls, so check it instead of clicking blindly. If it is unticked, Sencho writes the files but deploys nothing. The stack then reads **Applied not deployed**, and the **Drift** tab shows the container on the previous generation. Pull and apply the next commit with the box ticked to catch up. The first deploy pulls the Postgres image, so allow a minute. A toast reads `Changes applied and deployed.`

    <Frame>
      <img src="/images/tutorials/keep-secrets-in-git-with-sops/change-plan-encrypted.png" alt="Git Change plan dialog for ledger listing Modify, secret-bearing managed path, with 1 unchanged file, a ticked Deploy after apply checkbox, and Dismiss and Apply buttons." />
    </Frame>
  </Step>
  <Step title="Back up the identity">
    Sencho keeps the identity's private key in `sencho.db`, encrypted with the key in `encryption.key`. You need both, so back them up together. From the host that runs Sencho:

    ```bash
    docker compose exec sencho node dist/cli/backupData.js
    ```

    ```text
    Backup written to /app/data/backups/sencho-backup-2026-10-24T20-58-08-583Z (sencho.db + encryption.key). Store it somewhere safe; it contains your encryption key.
    ```

    The folder appears under `backups` in your Sencho data directory. Copy it off the host to somewhere you control. The copy holds your encryption key, so protect it as carefully as the original; [Emergency command-line recovery](/operations/emergency-cli#back-up-the-data-directory) covers the command in full.

    Your `recovery.key` from step 3 is the second safeguard, and it works without Sencho at all. Keep both: if you lose the backup and the recovery key together, nothing can open `db.env`.
  </Step>
</Steps>

## Verify it worked

Check from three places, since each shows something the others can't.

**The Git source sheet.** Reopen it. The header shows the short commit SHA, `accepted`, and `main`, the **Overview** answers **Accepted**, and the stage row ends **Runtime synced and healthy**. For a few seconds right after a deploy it can read **Artifact unverified**; reopen the sheet and it settles. The **Secrets** tab reads **Ready** with **Require SOPS encryption** selected.

<Frame>
  <img src="/images/tutorials/keep-secrets-in-git-with-sops/overview-accepted.png" alt="Git source sheet for ledger with the header showing a short commit SHA, accepted, and main, an Overview answering Accepted, and a stage row of Source accepted, Artifact qualified, and Runtime synced and healthy." />
</Frame>

**The file on disk.** The stack directory under your compose directory still holds ciphertext:

```bash
cut -c1-60 <compose dir>/ledger/db.env | head -3
```

```text
POSTGRES_USER=ENC[AES256_GCM,data:b49jZ86Q,iv:6L5W/KEOKX5HTq
POSTGRES_DB=ENC[AES256_GCM,data:3G9aLULh,iv:TKUCaO31Nu0SkyEK
POSTGRES_PASSWORD=ENC[AES256_GCM,data:6pfFXiF1GeuEvWX/NPx4eh
```

**The running container.** Sencho decrypted the file only for the deploy, so the container sees the real values:

```bash
docker exec ledger-db-1 printenv POSTGRES_PASSWORD
docker exec ledger-db-1 psql -U ledger -d ledger -tAc "select current_user, current_database()"
```

The first prints `ledger-demo-pw-2026` and the second prints `ledger|ledger`. SOPS protects the repository and the files on disk; the container still holds the value as an environment variable, so anyone who can run `docker inspect` on this host can read it.

## If something goes wrong

**A pull fails with "Required age identity is not available on this node."** The commit's `db.env` is encrypted to keys that this node does not hold, most often because only your own key went into `.sops.yaml` and Sencho's recipient was left out. The stack stays on its accepted commit.

<Frame>
  <img src="/images/tutorials/keep-secrets-in-git-with-sops/pull-refused-missing-identity.png" alt="Git source sheet still on the accepted commit with an error toast reading Required age identity is not available on this node." />
</Frame>

Add Sencho's recipient to the rule in `.sops.yaml`, then re-encrypt the existing file to the full list with a key that can still open it, here the recovery key:

```bash
SOPS_AGE_KEY_FILE=recovery.key sops updatekeys --yes db.env
git add .sops.yaml db.env
git commit -m "Encrypt db.env for the Sencho identity too"
git push
```

Select **Pull now** again. The plan appears as a **Modify** and applies as in step 6.
