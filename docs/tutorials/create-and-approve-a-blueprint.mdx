Every other lane in Sencho manages one Compose file on one node. A **Blueprint** is the other lane: you declare a Compose file once, point it at the nodes you want by label or by ID, and Sencho keeps those nodes in sync with that declaration going forward, deploying it where it's missing and telling you the moment a targeted node drifts from what you declared. This walks through the two-part motion every Blueprint goes through before it touches your fleet: you **create** it (author the compose, pick a target, choose how drift gets handled), then you **approve** it (review exactly what Sencho is about to place, and confirm). By the end, a small stateless service is running on a real node, deployed entirely through the Blueprint you approved rather than a manual `docker compose up`.

This tutorial does not cover stateful Blueprints (the extra confirmation step for named volumes and bind mounts), pinning a Blueprint to a specific node, moving a deployment between nodes, or Git-managed Blueprints (**Convert to Git**). **Apply now** in the steps below is the Inline path. See the [Blueprints](/features/blueprint-model) feature page for stateful workflows, [Git-managed Blueprints](/features/git-managed-blueprints) for Git-managed content, and [Move a Blueprint Deployment to a New Node](/tutorials/set-up-fleet-federation) once you've completed this one and want to relocate a deployment with Federation.

## Prerequisites

- **A role that can author and apply Blueprints.** Creating, editing, applying, and withdrawing need the stack permissions that the admin and node-admin roles carry, and tagging a node with a label needs node management on that node. Viewers and auditors can read the catalog and the detail sheet but can't act on either.
- **At least one node**, local or remote, that you can attach a label to. Blueprints are a Community-tier capability; no paid plan is required.

<Steps>
  <Step title="Author the Blueprint">
    Go to **Fleet → Blueprints** and click **New Blueprint** (**Create your first Blueprint** while the catalog is empty). Fill in:

    - **Name**: `whoami-edge`
    - **Description**: `Minimal identity endpoint for the edge tier`

    In the **Compose** editor, replace the placeholder YAML with a small, stateless HTTP service that just echoes back which container answered, useful for confirming a deploy actually landed:

    ```yaml
    services:
      app:
        image: traefik/whoami:v1.10
        restart: unless-stopped
        ports:
          - "8080:80"
    ```

    As you type, the classification banner above the editor updates. With no volumes in this compose, it settles on **Stateless · portable**: Sencho can deploy and evict this Blueprint freely, with none of the extra confirmation prompts a stateful Blueprint requires.

    <Frame caption="Name, description, and compose filled in. The classification banner reads Stateless · portable.">
      <img src="/images/tutorials/create-and-approve-a-blueprint/blueprint-editor-compose.png" alt="Blueprint editor dialog with Name whoami-edge, Description 'Minimal identity endpoint for the edge tier', and a compose YAML editor showing the traefik/whoami service. The classification banner above the editor reads Stateless · portable, no persistent volumes detected." />
    </Frame>

    Scroll down to **Targets** and leave **By node label** selected. A Blueprint targets nodes by label, and your nodes have no `edge` label yet, so create it here: click **+ Label**, type `edge`, tick the node you want this Blueprint to reach, and click **Add label**. Labels are plain lowercase strings, not key/value pairs, and a node can carry several. The `edge` pill is now selected, and the box below reads `Matches 1 node` with the node's name, plus `Tags added when you continue` listing `edge` on that node. The label is only staged: it is added to the node when you continue in the last click of this step, and the footer reminds you that **Review rollout** adds the label while **Save as draft** does not. Under **Drift policy**, leave **Suggest** selected, the middle option: Sencho will always detect drift on this Blueprint (including frozen image identity once a revision has been deployed), and Suggest additionally sends a notification when it happens, without redeploying anything on its own. (**Observe** stays silent about drift beyond the deployment row and Drift tab; **Enforce** auto-redeploys to restore a stopped container, or reapplies the frozen digest with `--pull never` when image identity disagrees. Enforce only ever restores the generation that node already acknowledged, and it holds rather than guessing when it cannot prove what that node is running, so the row can read **Repair held** instead of repairing.)

    <Frame caption="Targets set to the edge label, Suggest drift policy selected.">
      <img src="/images/tutorials/create-and-approve-a-blueprint/blueprint-editor-selector-drift.png" alt="Blueprint editor scrolled to the Targets and Drift policy sections. The edge label pill is selected with Match any chosen, Matches 1 node lists Local, and Tags added when you continue shows edge on Local. The Suggest drift policy card is selected among Observe, Suggest, and Enforce, with the Reconciler switch on." />
    </Frame>

    Click **Review rollout**.
  </Step>
  <Step title="Review and confirm the rollout">
    Sencho saves the Blueprint, adds the `edge` label to the node, and opens the rollout preview over the new Blueprint's detail sheet. (If you chose **Save as draft** instead, the sheet opens with no deployment yet; click **Apply now** to open the same preview.) The preview reads: `Safe 1 · Warnings 1 · Blockers 0`, with a warning noting `no persistent volumes detected` (informational for a stateless Blueprint, not a problem), and one line under **Changes**: `Local (local/online) · create · safe: New placement`.

    Above the change list, the **GitOps authority and evidence** block reads out the application's state as one answer: here **Rollout not executable**, with the reason that no authorized rollout is bound to the current inputs yet. Under it, a row names each stage that applies (an Inline Blueprint has no Git source or executable artifact set, so only placement and rollout appear), and a collapsed **Evidence** control opens the authority steps with a recorded grant, each decision's policy line, and anything Sencho could not prove. The summary row above the block reads **Legacy combined: pending**: the Blueprint's approval is waiting for you. The sheet's status row shows the same state as **Approval pending**, and it turns to **Approval confirmed** once you confirm. The rollout generation and the per-target observations are listed below the block. The footer notes that confirming is bound to the evidence snapshot shown; if a recorded authority fact changes first, the apply is refused as stale and the dialog refreshes.

    <Frame caption="The rollout preview for the first deploy: one safe create, one informational warning, and the recorded authority and state for the application.">
      <img src="/images/tutorials/create-and-approve-a-blueprint/rollout-preview.png" alt="Confirm rollout dialog for whoami-edge reading Safe 1, Warnings 1, Blockers 0, legacy combined: pending. A GitOps authority and evidence block shows the state Rollout not executable with its reason, a row of stages with placement 'blueprint bound' and rollout 'rollout not executable', an Evidence control, and a rollout generation of none. A Warnings section lists 'no persistent volumes detected'. A Changes section lists Local (local/online) · create · safe: New placement." />
    </Frame>

    This preview is the actual authorization step: nothing on the fleet has changed yet, and Sencho is showing you exactly what it's about to do before it does it. Click **Confirm Apply**.
  </Step>
</Steps>

## Verify it worked

Check from two places, since a single stale UI element could tell you the wrong thing.

**The Blueprints tab.** Back on **Fleet → Blueprints**, the `whoami-edge` tile now shows a green dot, the **stateless** and **inline** chips, `1/1 active · any=[edge]`, and `Drift suggest`. Open the tile: the status block reads **In sync** (`1 node running the current revision`), and the deployment table lists **Local**, status **Active**, with a **Withdraw** action now available. The stack also appears in the left sidebar's stack list like any other running stack, materialized on disk the same way a per-stack deploy would be.

**The audit log.** Open the navigation launcher and, under **Security & review**, pick **Audit** (Smart bar: **More** → **Audit**). Switch to **Table** and search `blueprints`. Each action is one row with your account, a timestamp, and a status: a `POST /api/blueprints` row with status 201 for the creation, a `POST /api/blueprints/<id>/apply` row for every time you clicked **Confirm Apply**, a `PUT /api/blueprints/<id>` row for every saved edit, and `POST /api/blueprints/analyze` rows for the compose check that runs while you edit. If you also hit and fixed a port conflict (see below), the edit and the second apply show up after the first apply.

## If something goes wrong

The most common first-time failure is a host port that's already taken. `8080` is a common default that other containers on the same node may already be bound to. If that happens, the status block at the top of the sheet turns red and names the node, the deployment row moves to **Failed**, and the notes column carries the real Docker error, ending in something like `Bind for :::8080 failed: port is already allocated` (the address format depends on the host).

<Frame caption="A failed first deploy: the notes column carries the daemon error, including the port conflict; when the log runs longer, the full output sits behind a control.">
  <img src="/images/tutorials/create-and-approve-a-blueprint/deployment-failed-port-conflict.png" alt="Blueprint detail sheet with a red Failed status block reading Deploy failed on Local with a Re-apply action. The deployment row for Local is Failed, with Re-apply and Withdraw actions and a notes column ending in 'Bind for :::8080 failed: port is already allocated' above a Full output control." />
</Frame>

To recover, click **Edit**, change the host-side port in the `ports` mapping to something free (`8091:80`, for instance), and **Save changes**. Saving bumps the revision and clears approval back to pending (the status row reads **Approval pending**), so click **Apply now** again (or **Re-apply** in the status block). The preview this time reads **Failed after change** in the status block and lists `Local · update · safe: Revision or retry deploy` instead of a create. Confirm it, and the deployment moves through **Deploying** to **Active** on the new port.
