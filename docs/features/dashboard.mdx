The **Home** tab is the first thing you see after logging in. It reads top to bottom as a triage: whether anything is wrong, what is affected, what changed, and finally how the instance is configured. The state masthead, the resource gauges, and the Stack health table come first. The operational row below them leads with **Recent alerts**, with **Fleet heartbeat** beside it on a multi-node install. **Configuration summary** closes the page.

Every card below the gauges shares the same table design as Stack health: a heading with a tracked-mono summary line, column headers, and rows that open something when they lead somewhere. Click anywhere on such a row, or press <kbd>Tab</kbd> to reach its name and open it with <kbd>Enter</kbd> or <kbd>Space</kbd>. A row that leads nowhere is plain text with no hover highlight or chevron.

## Status masthead

The masthead at the top of the dashboard is the single place to read the node's current condition.

<Frame>
  <img src="/images/dashboard/status-masthead.png" alt="Status masthead in the Healthy state with a teal left-edge accent rail, the editorial state word, the meta line 'LOCAL · 4 NODES · LAST SYNC 0S', the reasons line 'All systems nominal', the RUNNING / CPU / MEM stat tiles, and an 8-alerts counter." />
</Frame>

It carries:

- A **state word** (Healthy, Degraded, or Critical) set in the editorial display face so the reader sees it first.
- A thin **accent rail** down the card's left edge that mirrors the state color: brand teal when Healthy, amber when Degraded, rose when Critical. The rail shimmers when Healthy and glows steadily otherwise.
- A **meta line** in uppercase mono tracking with the active node's name, the number of nodes registered to this Sencho instance, and the time since the last successful poll, for example `LOCAL · 4 NODES · LAST SYNC 1S`.
- A **reasons line** that names exactly which signals moved the state away from Healthy, for example `RAM 95% · 18 unread errors`. When the state is Healthy the reasons line reads `All systems nominal`.
- Three quick stat tiles on the right edge of the bar, hidden below the `md` breakpoint: **RUNNING** (`active/total`), **CPU**, and **MEM**.
- An alerts counter pinned to the far right, showing the number of unread notifications next to a bell icon and the word `alert` or `alerts`. The bell and count tint amber while at least one alert is unread. The count covers unread entries across the whole bell feed, so it rarely matches the Recent alerts row count: the card leaves out entries that are not alerts, and it still lists alerts you have read.

The masthead's CPU stat tile tints amber once host CPU crosses 80% and stays amber even at 90% or higher. The MEM and RUNNING values stay neutral; the reasons line and the gauge strip below are where you read severity.

## Resource gauges

A single rail of four tiles shows the numbers that change minute-to-minute.

<Frame>
  <img src="/images/dashboard/resource-gauges.png" alt="Four-tile resource gauge strip: a CPU hero tile at 0.4% with the 'avg 0% last 10m · peak 0% @ 08:05 PM' caption and a 10-minute sparkline; a MEMORY tile at 15% in brand cyan with '2.4 GB / 15.6 GB' below; a DISK tile at 59% in brand cyan with '165.6 GB / 291.7 GB'; and a NETWORK tile reading '3.3 KB/s' with the rx/tx split and a rhythm sparkline." />
</Frame>

| Tile | What it shows |
|------|---------------|
| **CPU** (hero) | Current usage with the host's core count in the kicker, a 10-minute sparkline, and a caption with `avg X% last 10m · peak Y% @ HH:MM` |
| **MEMORY** | RAM usage as a percentage with a gauge bar and the exact `used / total` split below |
| **DISK** | Mount usage as a percentage with a gauge bar and the exact `used / total` split below |
| **NETWORK** | Total throughput per second with a `↓ <rx>/s · ↑ <tx>/s` breakdown and a live rhythm sparkline |

The gauge bars (and the corresponding numeric values) pick up amber at 80% and rose at 90%. The CPU sparkline uses brand cyan as the data color and does not mark the peak, since the caption already names the peak value and time. The network strip falls back to a dashed baseline when there is no traffic to plot.

While the dashboard is loading the CPU tile reads `--` and the caption shows `collecting metrics…`; bars and sparklines render once the first sample arrives.

<Note>
  **ZFS hosts:** the memory tile and host RAM alerts are ZFS ARC-aware. Reclaimable ARC cache is treated as available memory rather than used, so a large ARC does not inflate the gauge or trigger false low-memory alerts. When ARC stats are readable and the reclaimable amount is nonzero, the memory tile also shows how much raw memory is currently in use and how much of it the ARC can give back on demand. See [ZFS ARC-aware host memory](/getting-started/configuration#zfs-arc-aware-host-memory) for how to expose ARC stats to a Docker install.

  **Virtual machines:** when balloon data is present (TrueNAS/KVM, Proxmox), the memory tile's percentage, gauge bar, used/total figures, and the dashboard health banner all use the balloon-adjusted values so they agree with each other. The tile adds context lines for the memory currently retained by the VM (`Current VM Memory`), how heavily that retained memory is used (`Current pressure`), and what the hypervisor has reclaimed (`Balloon reclaimable`). Unlike ARC, ballooned pages are host-reclaimed and the guest cannot get them back on demand, so host RAM alerts continue to use the standard working-set percentage to catch a hypervisor squeezing a guest. See [VM memory ballooning](/getting-started/configuration#vm-memory-ballooning) for details.
</Note>

## Stack health

A mono table of every stack discovered on the active node by default, sorted so the stacks demanding attention sit at the top. When your inventory has more than one node, a **This node | All nodes** control appears in the card header. The last choice is remembered when you leave Home, switch nodes, or come back from another view. **All nodes** fans out the same status, metrics, and GitOps lookups to every other reachable node and merges the results as each node answers, so a slow or denied node never blocks the rest.

<Frame>
  <img src="/images/dashboard/stack-health.png" alt="Stack health table titled 'Stack health' with a This node / All nodes control, coverage subtitle, and STACK / STATE / SOURCE / NETWORKS / PORT / UP / CPU / MEM / CPU · 10m columns listing stacks with row tints and sparklines." />
</Frame>

The row itself carries the health tint (see below); there is no separate status-dot column. The columns are:

| Column | Description |
|--------|-------------|
| **STACK** | Stack name with an orange "Update available" badge when a newer image has been detected on the active node. When per-service status is known, the badge narrows to the outdated service name or a count (for example `2 updates`); hover for the full breakdown. The badge appears regardless of the sidebar indicator setting. Also carries the GitOps source-state chip when Sencho has state for the stack (see below). Sortable. |
| **NODE** | Node name. Shown only in **All nodes** so identical stack names on different nodes stay distinct. |
| **STATE** | Canonical container state: `running`, `partial`, `exited`, or `unknown`. |
| **SOURCE** | `Git` when the stack is linked to a [Git source](/features/git-sources), `Local` otherwise |
| **NETWORKS** | Runtime Docker networks attached to the stack's containers. Multiple names collapse to the first plus `+N`; hover for the full list. Reads `--` when no network membership was observed. |
| **PORT** | The stack's main published port, or `--` when it does not publish one |
| **UP** | How long the oldest running container has been up, in compact units (`s` / `m` / `h` / `d`); a stopped or never-started stack reads `--`. Sortable. |
| **CPU** | Latest aggregate CPU across the stack's containers. Sortable. Missing samples read `--`. |
| **MEM** | Latest aggregate memory across the stack's containers, formatted in MB or GB. Sortable. Missing samples read `--`. |
| **CPU · 10m** | Per-stack 10-minute sparkline tinted to match the row state; warn and error rows mark the peak with a contrasting accent color |

By default, rows sort by state (errors → warnings → healthy) and then by 10-minute peak CPU descending, so an exited stack always rises to the top and the noisiest healthy stacks float above the quiet ones (the header reads `sorted by load`). Click the **STACK**, **UP**, **CPU**, or **MEM** column header to sort by that column instead; the `sorted by load` label disappears once you do. Click the same header again to flip between ascending and descending. A row is tinted amber when its 10-minute peak CPU is at or above 80% or the stack is partially down (some but not all containers exited), or rose when the stack is fully exited or its peak CPU is at or above 90%. Click any row, or focus it and press <kbd>Enter</kbd> or <kbd>Space</kbd>, to open that stack's editor on the node that owns it. Same-name stacks on different nodes keep their identity through that jump.

The table shows the first eight rows and a **Show all N stacks** footer when there are more; **Show less** collapses again. In **All nodes**, the subtitle reports full coverage as `N stacks · M nodes`, or `N stacks · K/M nodes reporting` while some nodes are still pending, stale, denied, or offline. Retry refreshes only the nodes that need it. When every node fails to report, the card shows an unavailable state with Retry rather than an empty fleet. When the active node (or every confirmed reporter) has no stacks, the card renders an empty state with a layered-disks glyph and the message `No stacks found. Create one from the sidebar.` On narrow widths the table scrolls horizontally so columns stay readable.

The phone dashboard uses the same eight-row collapse, shared state classifier, and composite navigation. When more than one node is available it shows the same **This node | All nodes** control; **Show all** / **Show less** expand and collapse the list in place.

### GitOps state chip

A stack linked to a [Git source](/features/git-sources) carries a small chip beside its name naming its current source state: **pending update**, **review required**, **applying**, **source failed**, and so on. The wording is the same one the Git Source panel and the Drift tab use, so a stack reads the same way wherever you look at it.

The chip and the row tint answer different questions and are independent. The tint is about containers and load right now. The chip is about what Sencho has reconciled and accepted, so a healthy row can carry **pending update** (containers fine, a new commit waiting) and a red row can carry **accepted** (the current generation is the right one and something has since crashed).

Hover the chip for the full sentence. A stack with no Git source carries no chip, including one delivered by a [Blueprint](/features/blueprint-model): a Blueprint stack has no Git source of its own, so there is no source state to name. The **SOURCE** column still says where the files come from either way. The chip updates as soon as Sencho records a change, without waiting for the next refresh.

The phone dashboard shows the same chip on its stack rows, beside the node name.

## Recent alerts

The first card in the operational row answers "what needs attention". It lists the recent alerts worth acting on, newest first, whether or not you have read them (read ones are dimmed): warnings, errors, and availability notices for a stack or node update. Completion records, such as an image update that was applied, stay in the notification feed and are not repeated here, and deploys and other stack actions you ran yourself appear in the activity ticker instead. The card reads as a short list of things to do rather than a log of everything the instance did.

<Frame>
  <img src="/images/dashboard/recent-alerts.png" alt="Recent alerts table under the All nodes scope with the caption '14 alerts · 2/3 nodes reporting', eight rows with a severity icon, the alert message and its stack, the node name, and a relative time, and a footer noting that one node has no current feed beside View all alerts." />
</Frame>

The card shows the latest eight alerts and always keeps the height of a full eight-row preview, even with fewer alerts or none, so it never grows or shrinks as alerts come and go. The footer says how many more there are (`Latest 8 of 11`), unless a node in scope is silent, when it names that node instead (see below). **View all alerts** opens the notification feed, the same surface as the bell in the top bar. That feed carries every notification the card leaves out, and it is where you read history or clear entries; the Home card has no clear action of its own.

When more than one node is registered, a **This node | All nodes** control appears in the card header. **This node** is the default and always means the active node: switch nodes and the card follows. **All nodes** adds every other node's alerts and a **Node** column so identical messages from different nodes stay distinct. The choice is remembered for your browser, independently of the active node, so switching nodes or leaving Home does not reset it.

The summary line beside the title reads `<n> alerts · <node>` under **This node**, and `<n> alerts · <m> nodes` under **All nodes**. When a node in scope did not answer the latest fetch (it is offline, or its request failed), a notice names the silent node (in the footer while alerts are listed, in place of the list when there are none), and under **All nodes** the summary switches to `<k>/<m> nodes reporting`. Rows already received from that node stay visible; a silent node is never read as having no alerts. If the card would otherwise be empty, it says the node's alerts may be missing instead of showing the all-clear. Until the first fetch after sign-in settles, the card shows a loading state rather than an all-clear.

Each row shows a severity icon (info, warning, or error, also announced as text to screen readers), the message with the stack and container it concerns underneath, the node under **All nodes**, and a relative time. Rows with a deterministic destination open it:

| Alert | Opens |
|-------|-------|
| A stack alert (crash, unhealthy container, failed deploy, auto-heal, update available) | That stack on the node that raised it, with the container's logs when the alert names a container |
| A drift alert | The stack's **Drift** tab |
| A scan finding that names no stack | **Security › History** on the node that raised it |
| A node update or integration build notice | **Fleet** with its updates sheet on **Nodes** or **Changelog** |

An alert raised on another node switches the active node first, the same way opening a stack from Fleet does. The switch is real: when you come back to Home it shows the node you switched to, until you pick another one from the node switcher. Rows about the host as a whole, such as a threshold breach, and any row whose destination your role cannot open, are not clickable.

When nothing actionable is outstanding the card shows a green check and `No recent alerts.` An empty card is the healthy answer rather than a broken one, and the bell counter can still report unread entries that are not alerts.

Per-stack alert rules live on each stack's **Monitor** sheet; delivery channels and severity routing are configured in **Settings · Notifications**. See [Alerts and notifications](/features/alerts-notifications) for channel setup, per-stack rules, mute rules, and the routing engine.

## Fleet heartbeat

Beside the alerts, Fleet heartbeat answers "what is affected" at fleet scale. It appears once at least one remote node is registered, for roles that can read nodes. It always describes the whole fleet, whichever node is active. Side by side, the card has the same fixed height as the Recent alerts card, and when the fleet has more nodes than fit, its table scrolls inside the card. On a single-node install, or for a role that cannot read nodes, Recent alerts spans the full width instead.

<Frame>
  <img src="/images/dashboard/fleet-heartbeat.png" alt="Fleet heartbeat table with the caption '3 nodes · 1 offline', and Node, State, Active, and Contact columns: an offline remote first reading 'never reached', then an online remote with its latency, then the local node with its LOCAL pill." />
</Frame>

The summary line gives the node count and one clause per problem it can name, for example `3 nodes · 1 offline · 1 unknown`. Offline is counted in red and unknown in amber: a node Sencho failed to reach is not the same as one whose state it could not determine, and unknown is never folded into offline. When the mesh data plane is down, a `mesh down` clause and its banner appear alongside the counts. If a refresh fails after an earlier one succeeded, the last answer stays on screen, marked `stale` in the summary line, with a notice that names the error.

Rows are ordered so problems surface first: offline nodes, then unknown nodes, then healthy remote nodes, then the local node, each group by name.

| Column | What it shows |
|--------|---------------|
| **Node** | A status dot (green online, amber unknown, red offline), the node name, and a **LOCAL** pill on the local node |
| **State** | `online`, `unknown`, or `offline`, in words as well as color |
| **Active** | Running containers on that node, or `--` when the node did not report |
| **Contact** | Round-trip latency for an online proxy node, `tunnel` for a Pilot agent node, `--` for the local node, or how long ago the node was last reached once it stops answering (`never reached` if it never has) |

Every row opens that node's details in the Fleet view, so an offline node is one click from the connection details you need to fix it. Fleet lives on the hub, so from a remote node the row switches back to the hub first. The card refreshes every 30 seconds.

## Configuration summary

Configuration summary closes the page. It is the at-a-glance audit of the automation, alerting, and security features that can be switched on, so nothing is quietly off when you expect it to be on. It is deliberately compact: one row per domain until you ask for more.

<Frame>
  <img src="/images/dashboard/configuration-summary.png" alt="Configuration summary table with the caption '2 of 15 set up · Local', Setting, Status, Scope, and Set up columns, the Notifications and Security domains expanded into their individual settings with a Node, Account, or Instance scope each, and the Automation and Recovery & alerts domains collapsed." />
</Frame>

Each domain row carries a one-line summary, the scopes its settings span, and how many of them are set up, for example `Notifications · Discord, ntfy · 4 alert rules · no routes · 1 mute rule · 3/4`. Click a domain row, or reach its name with <kbd>Tab</kbd> and press <kbd>Enter</kbd> or <kbd>Space</kbd>, to expand its settings; do the same again to collapse. The summary line beside the title totals the whole card, for example `9 of 15 set up · edge-01`.

A setting counts as set up when it is actually in effect, not merely configured: an enabled delivery channel, at least one active policy, a scanner that is present, thresholds that are switched on. Settings for features that are not available on this instance are left out of the table and of every count.

Every setting names its **scope**, because switching the active node changes some rows and not others:

| Scope | Meaning |
|-------|---------|
| **Node** | Follows the active node: switch nodes and the value changes |
| **Account** | Belongs to you, the signed-in operator |
| **Instance** | Belongs to the Sencho instance serving the active node: the hub, or the remote itself when a remote node is active. With a remote active, rows such as Routing, Scheduled tasks, and SSO show that remote's own copy of the setting; switch to the hub to see the values that govern the fleet. |

| Domain | Setting | Scope | Opens |
|--------|---------|-------|-------|
| Notifications | **Channels**: enabled delivery channels (`Discord`, `Slack`, `Webhook`, `Apprise`, `ntfy`) | Node | Settings · Notifications |
| | **Alert rules**: per-stack alert rules on this node | Node | Settings · Notifications |
| | **Routing**: enabled routing rules | Instance | Settings · Notification Routing |
| | **Mute rules**: enabled mute rules. See [Mute Rules](/features/alerts-notifications#mute-rules). | Instance | Settings · Mute Rules |
| Automation | **Auto-heal policies**: `<enabled> / <total> active` | Node | Settings · Container Alerts |
| | **Auto-update schedules**: `<enabled> / <total> active` | Node | Auto-Update |
| | **Scheduled tasks**: active scheduled operations | Instance | Schedules |
| | **Webhooks**: active inbound deploy webhooks | Instance | Settings · Webhooks |
| Security | **MFA**: `On`, `Off`, or `Not set up` for your account | Account | Settings · Account |
| | **SSO**: the active provider (`OIDC`, `Google`, `GitHub`, `Okta`, `LDAP`) or `Off` | Instance | Settings · SSO |
| | **Trivy**: whether a scanner is installed on this node | Node | Security · Scanner |
| | **Scan policies**: enabled vulnerability scan policies | Instance | Security · Policies |
| Recovery & alerts | **Backups**: `Recovery Vault`, `Custom S3` (with `(auto)` when auto-upload is on), or `Off` | Instance | Settings · Cloud Backup |
| | **Host thresholds**: `CPU x% · RAM y% · Disk z%`, or `Off` | Node | Settings · Host Alerts |
| | **Crash detection**: global container-crash notifications | Node | Settings · Container Alerts |

Click a setting row to open where it is managed. A row whose destination your role cannot open, or that is not available from the active node (such as your account settings or Schedules while a remote node is active), stays visible but is not clickable.

The card refreshes when you come back to Home after changing a setting, when a scheduled task changes, when you add a mute rule from the notification feed, when the notification stream reconnects, and every 60 seconds as a safety net for changes made elsewhere. A response that arrives after you switched nodes is discarded, so one node's configuration never appears under another's name. If a refresh fails, the last values stay on screen and the summary line adds `stale` until the next refresh succeeds.

## How health is derived

The masthead's state word and reasons line both come from a single rule against five signals: host CPU, host RAM, host disk, exited container count, and unread `error`-level notifications.

| State | Meaning |
|-------|---------|
| **Healthy** | All five signals nominal. CPU, RAM, and disk are all under 80%, no container is in the `exited` state, and there are no unread error alerts. |
| **Degraded** | At least one of CPU, RAM, or disk is at or above 80%, OR at least one container is in the `exited` state, OR at least one unread error alert exists. |
| **Critical** | At least one of CPU, RAM, or disk is at or above 90%, OR at least one container is in the `exited` state AND at least one unread error alert is present at the same time. |

Every signal that contributes to a non-Healthy state appears in the reasons line, separated by middle dots (`·`), so you can read the cause directly without hovering anything.

## Refresh cadence

The dashboard is built from several independent polling loops so that fast-moving values stay live without flooding the API for slowly-changing ones.

| Surface | Polling cadence |
|---------|-----------------|
| Container counts and host system stats (masthead, gauges) | 5 seconds |
| Stack statuses (status dots and uptime in the table) | 10 seconds |
| Historical metrics (CPU sparklines and per-stack 10m series) | 60 seconds |
| Configuration summary | 60 seconds, plus the refresh signals described above |
| Fleet heartbeat | 30 seconds |
| Recent alerts | Pushed live over the notifications WebSocket, with a 60-second safety-net reconcile poll |

In addition, every Docker container event (start, stop, die, restart, health-status change) on the active node fires a `sencho:state-invalidate` browser event that immediately refetches container counts, system stats, and stack statuses, so the masthead, gauges, and stack health table react in well under a second instead of waiting for the next polling tick. Configuration summary ignores these container-level events, since none of them change a setting.

When you switch the active node from the node switcher, the dashboard resets every panel to its loading state and starts a new round of fetches against the new node so you never see stale data from the previous one.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Stack health is empty even though I have stacks on disk">
    The table reads from the active node's `COMPOSE_DIR`. If you mounted the compose volume to a different path inside the container, set the environment variable in your `docker-compose.yml` so it matches what is on the host. Per-node overrides live on the **Compose directory** field of the node entry; the resolution chain is `node.compose_dir` → `process.env.COMPOSE_DIR` → `/app/compose`. After fixing the mount or the field, the table populates on the next 10-second poll.
  </Accordion>
  <Accordion title="Fleet heartbeat shows a node as offline or unknown">
    The heartbeat card reads the local Sencho instance's record of its last contact with each remote node, refreshed every 30 seconds. A red dot and an **offline** count mean the local instance has not been able to reach that node, or that the long-lived API token attached to the node entry has expired or been revoked. An amber dot and an **unknown** count mark a node whose status could not be determined; those nodes are never counted as offline. Re-test the connection from **Settings · Nodes**, regenerate the token on the remote instance, paste the new value into the node form, and the heartbeat clears on the next tick. See [Multi-node management](/features/multi-node) for the full setup flow and [Pilot agent](/features/pilot-agent) when the offline node is in agent mode.
  </Accordion>
  <Accordion title="A pilot-agent node shows 'tunnel' instead of a latency">
    Pilot-agent nodes connect outbound to the primary over a reverse tunnel, so there is no synchronous request-response loop to measure. The heartbeat card uses the tunnel's last heartbeat to set the dot color, and shows `tunnel` in the **Contact** column instead of a latency. If the dot is red, check the agent container's logs for the first `[Pilot]` line and confirm the agent can reach the primary URL it is dialing. See [Pilot agent](/features/pilot-agent).
  </Accordion>
  <Accordion title="Configuration summary still shows the old value after I changed a setting">
    Settings you change in Sencho are picked up as soon as you return to Home. A change made somewhere else, such as another browser or another operator, appears within 60 seconds. If a row stays stale after a minute, reload the tab to force a fresh fetch.
  </Accordion>
  <Accordion title="The masthead shows a 'metrics stale' chip next to the node name">
    The chip appears after three consecutive failures of the live metrics endpoints (`/api/stats` or `/api/system/stats`), which usually means the Docker socket is unreachable from this Sencho instance or the metrics service has stopped. The dashboard keeps polling on every cycle; the chip describes the freshness of the visible numbers, not the polling cadence. The chip clears on the first successful response once both endpoints are within the threshold. Check the Docker daemon status on the active node first, then the Sencho container logs for `[Dashboard]` lines if the chip persists.
  </Accordion>
  <Accordion title="Recent alerts is empty but the bell shows unread notifications">
    The card is a short list of alerts to act on, not a mirror of the feed, so two filters can legitimately leave it empty while the bell still counts unread entries. The first is severity: warnings, errors, and availability notices for stack or node updates appear here, while completion records such as an applied image update stay in the feed. The second is scope: the default **This node** view shows the active node only, so an alert raised on a remote node is hidden until you choose **All nodes**. Open **View all alerts** to read the whole feed, including every alert the card leaves out, or the bell in the top bar for the same surface.
  </Accordion>
  <Accordion title="The masthead reads 'Critical' but my CPU is low">
    Critical can fire on RAM, disk, or the combination of any exited container with an unread error alert, not only on CPU. Read the reasons line right under the meta line; it lists every signal pushing the state up. Common cases: RAM at or above 90% from an oversized service, disk at or above 90% from runaway log retention, or a crashed container that no one has acknowledged in the alerts panel.
  </Accordion>
  <Accordion title="The dashboard feels sluggish on a large deployment">
    Toggle **Developer mode** under **Settings · Operations · Developer Diagnostics**. The Configuration summary endpoint then emits a `[Dashboard:debug]` line in the Sencho container logs for every request, reporting elapsed milliseconds and the node it was built for. Use the timing to tell whether the Configuration summary payload is the bottleneck. Disable developer mode when you are done to keep the log volume manageable.
  </Accordion>
</AccordionGroup>
