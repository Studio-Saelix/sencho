Sencho reads a small set of Compose labels in the reserved `io.sencho.*` namespace. Most of them describe how a service should be presented in Sencho: where its application lives, where it sits in the list, and whether it is a helper that can stay out of the way. One of them marks the service that carries Sencho's Docker connection. Two more decide what Sencho may do to a service and where its alerts go: whether an image update may touch it, and which notification routing rules its alerts reach. The namespace is stable for 1.0: the labels on this page keep their names and meaning. A later release can add labels. A key Sencho does not define is reported as **Unsupported**, and a key Sencho reserves for the containers it creates is reported as **Ignored**; neither changes anything.

These are four different things that are easy to confuse:

| Kind | Where you set it | What it does |
|------|------------------|--------------|
| **Docker and Compose labels** | `labels:` on a service | Metadata for Docker, Compose, Traefik, and other tools. Sencho shows them in the [label audit](/features/docker-label-audit) and does not use them to change how a service is presented. `com.docker.compose.*` belongs to Docker. |
| **`io.sencho.*` labels** | `labels:` on a service | Tell Sencho how to present that service, whether an update may touch it, and which notification routes its alerts reach. This page. |
| **[Stack Labels](/features/stack-labels)** | The sidebar | Tags you use to group stacks. They are not Compose labels. |
| **Node Labels** | Node settings | Tags used for Blueprint placement. They are not Compose labels. |

## The labels

Every label belongs to one service and applies to all of its replicas.

| Label | Value | Effect |
|-------|-------|--------|
| `io.sencho.url` | An `http://` or `https://` URL | The service's application link. The published-port link on the service's container card opens it instead of the generated host and port. A service with no published port, such as one behind a reverse proxy, shows it as a link on the service's card. |
| `io.sencho.url.<name>` | An `http://` or `https://` URL | An extra named link, such as `docs` or `admin`. Names use lowercase letters, digits, and hyphens, up to 32 characters; uppercase is lowercased. |
| `io.sencho.order` | A whole number | Where the service sits in lists. Lower numbers come first. |
| `io.sencho.hidden` | `true` or `false` | Collapses a helper service out of default lists. |
| `io.sencho.infrastructure` | `"true"` | Marks the service that carries this node's Docker connection, so Sencho refuses operations that would cut it. See [Updating the proxy](/operations/self-hosting#updating-the-proxy). |
| `io.sencho.update` | `auto`, `manual`, or `disabled` | Whether an image update may touch the service, and whether unattended updates may run on the stack at all. See [Update policy](#update-policy). |
| `io.sencho.notify.route` | A routing key | A name for the service's alerts that notification routing rules can match. See [Notification routing key](#notification-routing-key). |

```yaml
services:
  web:
    image: ghcr.io/example/app:1.4
    labels:
      io.sencho.url: https://app.example.com
      io.sencho.url.docs: https://docs.example.com
      io.sencho.url.admin: https://admin.example.com
      io.sencho.order: "10"
  migrate:
    image: ghcr.io/example/app:1.4
    labels:
      io.sencho.hidden: "true"
      io.sencho.order: "90"
```

Both the map form shown above and the `- key=value` list form work. Compose renders every label value as text, so quoting a number or boolean is optional.

### Links

A link is clickable only when it is a valid `http://` or `https://` address with a host. Sencho ignores a link that has another scheme, a username or password, spaces or control characters, or is not a well-formed URL, and says why in the [Compose Labels tab](/features/docker-label-audit#stack-compose-labels-tab).

A configured `io.sencho.url` replaces the generated link for that service's published port on its container card. Elsewhere, such as **Open App** and the Anatomy footer, Sencho uses it when it can tell which service owns the port, and keeps the generated link when two services could own it.

A link has one order of precedence: a valid `io.sencho.url` wins over any address Sencho discovers about the service, which in turn wins over the generated published-port link. Named links are listed after the application link, sorted by name, and never replace a port link. If two names are the same after lowercasing (for example `Docs` and `docs`), the one that sorts first is kept and the other is ignored.

A service's links show once, on its card, or on its header when it runs several replicas or has no container yet. A link that carries an interpolated secret is shown to everyone who can read the stack, so keep secrets out of link values (see [Environment guardrails](/features/environment-guardrails)).

A link is an address you chose, so Sencho opens it exactly as written. It never swaps in the host of the node that runs the stack, which is why a remote node's links stay correct.

### Order

Services with a valid `io.sencho.order` come first, from the lowest number up. Services with the same number sort by name among themselves. Services with no label, or a value that is not a whole number, follow, sorted by name. Order changes presentation only: it does not change the order Compose starts services, dependencies, health checks, or updates.

### Hidden helper services

`io.sencho.hidden: "true"` collapses a noisy helper, such as a one-shot migration job or a sidecar, out of the container list. The list shows one row, **N hidden helper services**, with a **Show** button that reveals them in place. The row calls out how many of them need attention: a hidden service with a container that is unhealthy, restarting, dead, or created but never started, one that is stopped with a failure while the rest of the stack runs, one that has only some of its replicas while the stack runs, or one with no container at all while the rest of the stack runs. A helper that finished cleanly (a one-shot job that exited with code 0), a helper that declares no replicas (so its missing container is not news), and a stack that is stopped do not count, whatever exit code stopping produced: a helper that ignores the stop signal exits 137 or 143, and that says how it was stopped, not that it failed. A healthy setup stays quiet and a failed or missing helper is never invisible.

Hidden applies to the stack's container cards and its Anatomy service chips, and to nothing else. Both surfaces collapse the helpers behind one control that reveals them in place: the **N hidden helper services** row in the container list and the **N hidden** toggle beside the Anatomy services. The reveal belongs to the stack you opened: switching to another stack, or opening the same stack on another node, shows the helpers collapsed again. Every other surface keeps every service: logs service filters, Fleet views, Resources, the Dossier, health and status totals, notifications, security, drift, updates, and lifecycle actions. Sencho never collapses every service in a stack, so a stack whose services are all marked hidden shows them all.

The stack view has no service search, so to find a hidden service use the **Show** button on the collapsed row or the **N hidden** toggle in the Anatomy services, the service filter in the [Compose Labels tab](#where-you-see-them), or the `io.sencho.hidden` label key in the Fleet [Docker Labels](/features/docker-label-audit) filter.

### The protective label

`io.sencho.infrastructure: "true"` marks the service that carries this node's Docker connection, such as a socket proxy that Sencho reaches Docker through. Sencho usually finds that container by itself; the label adds protection for the topologies it cannot detect, for example a proxy reached through a published host port. It protects the service in stack, service, and container operations, and the owner of a network, pid, or ipc namespace a labeled container runs in, in any Compose project. Any other value refuses changes to the stack until it is corrected, including on the first deployment. See [Updating the proxy](/operations/self-hosting#updating-the-proxy).

This is the one label Sencho also honors on a running container, not only in the Compose file, because a copy there can only add protection. The Compose Labels tab reports such a copy as **Active** or **Ignored** rather than **Inert**, and says that the container stays protected until it is recreated without the label.

### Update policy

`io.sencho.update` declares what may happen to a service's image. It is read from the rendered Compose model like the other labels, so a value written in an override file or produced by an interpolated variable counts as written. The value is trimmed and case-insensitive: `Manual` reads the same as `manual`.

| Value | Your own update | Unattended update |
|-------|-----------------|-------------------|
| no label | Runs | Runs |
| `auto` | Runs | Runs |
| `manual` | Runs | Skips the whole stack |
| `disabled` | Refused | Skips the whole stack |
| Anything else | Runs | Skips the whole stack |

`auto` is the explicit way to say a service may be updated without you, and behaves exactly like leaving the label off. `manual` keeps the service in your hands: the update you click still refreshes it, while every unattended update skips the stack. `disabled` takes the service out of updates entirely, yours included.

```yaml
services:
  web:
    image: ghcr.io/example/app:1.4
    labels:
      io.sencho.update: auto
  db:
    image: postgres:16
    labels:
      io.sencho.update: manual
  legacy:
    image: ghcr.io/example/legacy:2.1
    labels:
      io.sencho.update: disabled
```

**Whole-stack updates.** Updating a whole stack refreshes every service in it. When any rendered service is `disabled`, or is not eligible for the kind of update you asked for, Sencho refuses the whole update and pulls and recreates nothing. It never quietly updates only the services that are allowed. The refusal names the services that block it, and updating one of the other services on its own is how to move that one forward. Selective unattended execution is not available yet: an unattended update either covers the whole stack or skips it.

A refused update, image pull, or bulk item reports the same decision in a named message, and the action it offers opens the stack so the policy can be changed at its source.

A service declared in a Compose profile that is not active is not part of the rendered stack, so it does not block anything.

**Your own update and unattended updates.** Your own update is a click you make: the stack's **Update** verb, one service's **Update** verb, or pulling the stack's images. Everything else is unattended: scheduled operations, automatic update checks, webhook triggers, and a bulk update started from the stack list. A bulk update treats each selected stack as an unattended update, so a stack with a `manual` service is skipped by the bulk action; open that stack and update it directly.

An unattended update runs only when every rendered service is `auto` or carries no label. If any service is `manual` or `disabled`, or carries a value Sencho does not recognize, the whole stack is skipped for that run, with the reason recorded, before anything is pulled or recreated.

**A value Sencho does not recognize.** A typo such as `off`, `diabled`, or `false` is reported as ignored in the label audit and restricts unattended updates while still allowing your own update. A typo therefore never causes an automatic update.

**What it does not cover.** The label governs the image refresh only. A container that a deploy starts because its service sets `pull_policy: always`, and a container brought up by a service restart, an Auto-Heal restart, a rollback, a restore, a GitOps apply, or a blueprint deploy, is not an image refresh, and none of those actions is refused by `io.sencho.update`. Only the image-refresh operations above honor it.

**A change made during an update.** A change to the label while an update is already running is caught before containers are recreated. The update stops rather than recreate under a policy you never saw.

### Notification routing key

`io.sencho.notify.route` gives a service's alerts a routing key, a name that a routing rule in notification settings can match. The value is trimmed and lowercased, and must be 1 to 64 characters of lowercase letters, digits, dots, hyphens, and underscores, starting and ending with a letter or a digit. A value that looks like a URL or an address, meaning it contains `:`, `/`, `@`, or whitespace, is refused and reported as ignored in the label audit.

```yaml
services:
  api:
    image: ghcr.io/example/api:2.3
    labels:
      io.sencho.notify.route: production
  db:
    image: postgres:16
    labels:
      io.sencho.notify.route: database
```

A routing rule can carry one or more routing keys, and a rule with keys matches only the alerts whose keys intersect its own. A rule without keys matches every alert. A service alert carries its own service's key. A stack-level alert carries every key of the stack's services at once, so in the example above it reaches rules keyed to `production` and rules keyed to `database`. Every matching rule fires; priority only orders them. See [Alerts & Notifications](/features/alerts-notifications#notification-routing).

A container that is not part of the stack's Compose model, such as a one-off container or an orphan, carries no key, so its alert does not fan out to the stack's rules. Host and fleet alerts carry no key either.

Routing rules match on the Sencho instance that runs the stack. A rule on the control instance matches the stacks that instance runs, not the stacks on remote nodes.

Keys appear in plain text in the interface and in the activity history. They are names, not secrets: never put a credential, token, or address in one.

## What Sencho trusts

Only labels declared on a service in your Compose file, after Compose has rendered it, change how Sencho behaves. A label that comes from an image, from a running container, or from anywhere Sencho cannot place is still listed in the label audit but never acts. If Compose cannot be rendered, Sencho applies no `io.sencho.*` labels at all rather than guessing from what is running, and the Compose Labels tab says so. An image update whose policy cannot be read from the rendered model is refused rather than run unchecked, and an unattended update is skipped.

Because Sencho reads the rendered result, the usual Compose rules apply: a value from `${VARIABLE}` interpolation is resolved first, and when several Compose files set the same label, the file merged last decides the value. Labels are read on the node that owns the stack.

`io.sencho.infrastructure` is the one exception, described above: a copy on a deployed container is honored too, because it only adds protection.

## Where you see them

The **Compose Labels** tab marks every `io.sencho.*` label with its status:

| Status | Meaning |
|--------|---------|
| **Active** | Declared in the rendered Compose file and valid. |
| **Ignored** | Declared, but Sencho cannot use it, for example an invalid value, a link name that is already taken, or a key Sencho reserves for containers it creates. The reason is shown beside it. |
| **Unsupported** | A key in the `io.sencho.` namespace that Sencho does not define. |
| **Inert** | Present on the image or the running container, or the Compose file could not be rendered. Select the badge to read why. Declare it in the Compose file for it to apply. A copy of `io.sencho.infrastructure` on a container is reported as **Active** or **Ignored** instead, because Sencho honors it. |
| **Not evaluated** | Shown for `io.sencho.update` and `io.sencho.notify.route` when the node does not evaluate these labels. See [Mixed-version fleets](#mixed-version-fleets). |
| **Not reported** | The node runs a version that does not report a status for the label. |

On the stack's container list, a service with ignored labels shows a quiet count, such as **1 Sencho label ignored**, with the reasons on hover. The Fleet **Docker Labels** tab reads running containers only, so it marks a presentation label **Inert**; a container's `io.sencho.infrastructure` copy is the exception there too, because Sencho acts on it.

Sencho reads these labels from the saved Compose file, not from the running container, so they do not need a redeploy to take effect. The running container only carries a changed label after it is recreated, which the label audit shows as a difference between **Declared in Compose** and the running container.

## Labels Sencho sets

Sencho stamps three keys on the containers it creates. They are not configuration, and a Compose file cannot set them:

| Label | Where it appears |
|-------|------------------|
| `io.sencho.mesh` | A mesh sidecar Sencho runs for a node. |
| `io.sencho.helper` | A helper container Sencho runs, such as the one that recreates the Docker endpoint. |
| `io.sencho.operation` | The operation a helper container belongs to. |

On a container, these keys are reported as **Inert** with the reason that Sencho set them. Declared in a Compose file, they are **Ignored**, because they are reserved. They never change how a service is presented.

## Mixed-version fleets

A node advertises the `sencho-labels-v1` capability once it resolves these labels. A node that predates them does not apply any of them: its stacks show no named links, no order, and no hidden services, its link pencil is not offered, and the Compose Labels tab tells you to update the node when a stack declares them. Sencho never applies part of the contract on such a node. See [Node compatibility](/features/node-compatibility).

Update policy and notification routing travel under a separate capability, `sencho-label-policy-v1`. A node that does not advertise it evaluates neither label: its alerts carry no routing key, and an unattended update aimed at that node fails and says so rather than assuming the stack is allowed. A scheduled or automatic run reports the node as failed, and a bulk update to that node is refused with a message naming it. Your own single-stack and single-service updates still work there, and the stack's update readiness dialog notes that the node does not evaluate the label when the stack declares it.

## Troubleshooting

<AccordionGroup>
  <Accordion title="My link does not show up">
    Open the stack's **Compose Labels** tab and find the label. **Ignored** shows the reason, such as a missing `https://` or credentials in the address. **Inert** means the label is on the container or image but not in the Compose file. If the tab says the node does not apply `io.sencho.*` labels, update that node.
  </Accordion>
  <Accordion title="A service is missing from the container list">
    It is probably marked `io.sencho.hidden: "true"`. Use **Show** on the **hidden helper services** row, or the **N hidden** toggle beside the Anatomy services, to reveal it. Remove the label to list it by default.
  </Accordion>
  <Accordion title="The order did not change">
    The value must be a whole number such as `"10"`; `first` or `1.5` is ignored and listed as **Ignored**. Services without a valid order always sort after ordered ones.
  </Accordion>
  <Accordion title="A label shows as Unsupported">
    Sencho does not define that key. Check the spelling against the table above. Keys outside the `io.sencho.` namespace are ordinary Docker labels and are never marked.
  </Accordion>
  <Accordion title="A Sencho label shows as Ignored but the spelling looks right">
    Two cases ignore a correct-looking key. A key Sencho reserves for containers it creates (`io.sencho.mesh`, `io.sencho.helper`, `io.sencho.operation`) has no effect in a Compose file. A link name that another key already defines, after lowercasing, is also ignored; the key that sorts first wins.
  </Accordion>
  <Accordion title="An update was refused or skipped because of a service">
    Read the service's `io.sencho.update` value in the Compose Labels tab. **Ignored** beside that key means the value is not one Sencho recognizes, which blocks unattended updates while still allowing your own. A `disabled` service refuses every update that would touch it, including a whole-stack update, so update the other services on their own or remove the label. A `manual` service allows your own update and skips every unattended one, so update the stack directly instead of through a schedule or a bulk action.
  </Accordion>
  <Accordion title="An alert did not reach a routing rule that has routing keys">
    A rule with routing keys matches only the alerts whose keys intersect its own. A service alert carries its own service's key, and a stack-level alert carries every key of the stack's services. A container that is not part of the stack's Compose model carries no key, so its alert does not match a rule keyed to the stack. Check that the routing rule has keys that a service in the stack declares, and that you are editing the rule on the instance that runs the stack.
  </Accordion>
</AccordionGroup>
