---
title: Node Bootstrap Preflight
description: Inspect a Linux server over SSH before you provision it. Sencho verifies the host key, inventories both host directories, and builds a versioned, reviewable plan without changing anything on the server.
---

The node bootstrap preflight is the first half of the guided provisioning workflow for a new Linux server. It connects to the host over SSH, runs a fixed catalog of read-only commands, and reports what it found with the same pass, warning, blocked and unknown language used by the other environment checks.

**Nothing on the target is changed.** The preflight does not install packages, create directories, write files, start services or enroll an agent. Its output is an ordered plan with exact commands that you can read, copy and download. Running that plan is a separate, later step.

Use it to answer questions a manual enrollment cannot:

- Is the host running a supported operating system and architecture?
- Is Docker installed, reachable, and set to survive a reboot?
- Is the Compose directory the right one, and will existing stacks be preserved?
- Is a previous Pilot agent or an unrelated installation already in the way?
- Would the agent directory collide with anything?
- Can the target reach this Sencho instance over HTTPS?

## Before you start

- **Supported target:** Ubuntu 22.04 or 24.04 on x86_64. Other releases and architectures are reported as unsupported rather than guessed at.
- **Access:** an SSH user with a private key. Password authentication and SSH agent forwarding are not used. If the host needs administrator steps, the user needs non-interactive sudo (`sudo -n`); the preflight reports when sudo is required for the current plan.
- **Network:** the target must be reachable from this Sencho instance on its SSH port, and the target must be able to reach the hub URL over HTTPS.
- **Node name:** the name you choose is not yet used by another node in this console.
- **Key format:** an OpenSSH private key (for example `id_ed25519`) or an RSA key in PEM format. A PKCS8 ed25519 key is rejected with a message asking for the OpenSSH format.

The private key is used for the request only. It is never stored, written to a log, included in the plan, or returned in a response. Serve Sencho over HTTPS before using a real key: on a plain HTTP page the dialog warns that the key travels in cleartext.

## Open the workflow

Go to **Fleet**, then open **Node management** at the end of the Overview toolbar and choose **Bootstrap new Linux server**.

The same menu holds **Connect existing node**, which opens the manual Add node form for a node that is already running Sencho or a Pilot agent. Manual enrollment and this guided flow produce the same agent configuration; choose the one that fits what you already have.

## The three steps

### 1. Server and directories

Enter the node name, host, SSH port, SSH user, private key and, if needed, the key passphrase.

</Frame>

Two directories are part of this step. They are validated as you type and again by the server before any SSH connection is opened.

| Directory | Default | What it holds |
| --- | --- | --- |
| Compose stacks directory | `/opt/docker/sencho` | The Compose project folders Sencho manages on this host. The Pilot mounts this directory at the same path inside its container. |
| Pilot Agent installation directory | `/opt/sencho-agent` | The Pilot's `compose.yaml`, the optional hub CA, and a small bootstrap marker. It is never listed as a stack and does not hold persistent agent data. |

The Agent directory is secondary, so it lives under **Advanced configuration**, collapsed by default. When you set a custom value and collapse the section, the current path stays visible in the section header.

**Path rules.** Both paths must be absolute, at most 200 characters, and use only letters, digits, `.`, `_`, `-` and `/`. Dots and dot-dot segments, duplicate or trailing slashes, the filesystem root, and single-segment roots are rejected. Neither path may sit under a system root such as `/etc`, `/usr`, `/var/lib/docker`, `/app`, `/tmp` or `/run`, and the two paths must not be equal or nested. Spaces and non-ASCII characters are rejected with an example rather than silently quoted through every layer.

There is no data-directory field. The agent's persistent data is the fixed `sencho-agent-data` Docker volume, and that is deliberate: enrollment, self-update and recovery all depend on it.

### 2. Preflight

Select **Check host key** first. Sencho connects only far enough to read the server's host key and shows its algorithm, SHA-256 fingerprint, and the public key line you can compare on the server with:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

- **New host:** tick **I trust this host key** to proceed. The fingerprint is pinned for this host and port.
- **Known host:** a key that matches the pin proceeds without a prompt.
- **Changed key:** Sencho blocks the preflight and shows both fingerprints. Replacing the pin is a separate, explicit action, and both fingerprints are recorded in the audit log.

Once trusted, select **Run preflight**. Sencho opens one SSH connection and runs the fixed read-only catalog. The request is bounded: 15 seconds to connect, 10 seconds per command, 90 seconds overall, with output caps. A command that exceeds its limit degrades the dependent check to `unknown` instead of reporting a pass.

The result has four verdicts:

| Verdict | Meaning |
| --- | --- |
| Pass | The check ran and the host satisfies it. |
| Warning | The host can be prepared, but something is worth reading first. |
| Blocked | The plan cannot be generated until this is resolved. Every blocker names the observed fact and one specific remedy. |
| Unknown | The fact could not be read. Unknown is never treated as a pass. |

A blocked inspection is still a successful inspection: it returns the evidence, no plan, and the remediation for each blocker.

### 3. Plan

When there are no blockers, Sencho builds the plan. It contains:

- Both directories, their resolved real paths where they differ, and whether each exists or will be created.
- Directory creation commands with the exact mode (`0755` for stacks, `0700` for the agent), owner, group and privilege.
- File writes for `compose.yaml` (`0600`), the bootstrap marker (`0600`) and, when the hub uses native TLS, `sencho-hub-ca.pem` (`0644`), all under the chosen Agent directory.
- The Docker repository, package and service steps, or an explicit no-change row when they already apply.
- The exact `docker compose` start command, with the project name pinned to `sencho-agent`, an explicit project directory and file, and the environment variables that could otherwise change which project runs cleared.
- An **Expected after execution** section listing what the later execution step and readiness check will verify. This is a promise, not evidence from this run.
- A SHA-256 digest over the plan, and a digest over the evidence it was built from.

</Frame>

The plan reads **No changes have been made on this server.** Use **Copy plan** or **Download** to keep it for review. The digest is what a later approval binds to, so a plan that changes is a plan that must be approved again.

## Existing content is preserved

**The Compose directory may already hold stacks.** The preflight inventories Compose files at depth one and two, reports the count and up to fifty names, and preserves everything. When the directory exists, the plan records a skipped step with the stack count: no creation, no `chown`, no `chmod`, and no write inside it. A root-level Compose file is reported as a warning because it usually means the operator chose a single project rather than its parent.

**The Agent directory must be dedicated.** It may be missing, empty, or hold a previous bootstrap attempt for the same project and paths, identified by `sencho-bootstrap.json`. Anything else blocks the plan with a remediation. Nothing is deleted or overwritten. A marker for a different project or different directories, a compose file without a marker, or any unrelated entry always blocks.

## Permissions, symlinks, persistence and space

- A missing directory is planned with `install -d` and an explicit mode and owner, so the result does not depend on the session umask.
- An existing Compose directory is never chowned or chmodded. If the SSH user cannot write it but root can, the check warns and the plan makes no change. If neither can write it, the preflight blocks.
- A final path element that is a symlink is blocked, because it can be retargeted between approval and execution. A symlink further up the path is disclosed with the resolved real path, which enters the plan and its digest.
- Both paths must be on local persistent filesystems. `tmpfs`, `overlay`, network filesystems and similar are blockers, because the agent must come back after a reboot with its stacks and its compose file. A separate local mount that cannot be confirmed in `/etc/fstab` is a warning; a systemd mount unit can be invisible there.
- Free space is checked on the Compose path, the Agent path and the Docker root. The plan is blocked under the hard floor and warns below the comfortable level. An unreadable figure is `unknown`, never a pass.

## Path changes invalidate the plan

Editing either directory discards the preflight result and the plan and shows:

> Paths changed. The previous preflight and plan no longer apply. Run the preflight again.

The plan step stays unreachable until a new preflight succeeds, and the new digest differs. The host-key pin is a property of the host, not of a path, so trust survives a path edit; changing the host, port or user does drop it.

## Lifecycle

The plan keeps the contracts later steps depend on:

- **Enrollment:** the compose file carries the mode, hub URL, enrollment token, Compose directory, Docker socket, the `sencho-agent-data` volume and the optional CA mount.
- **Self-update:** the container's Compose labels locate the compose file, so a custom Agent directory remains self-updateable. The project name, container name and service name do not change.
- **Reboot:** both directories must be on persistent local storage, Docker is enabled at boot, and the agent uses `restart: unless-stopped`.
- **Restart and recovery:** the project is idempotent, the volume survives container recreation, and the bootstrap marker distinguishes a previous attempt from an unrelated installation.
- **Readiness:** a tunnel connection alone is not proof that the node is ready. A later readiness check inspects the running container, requires a bind mount whose source and destination both equal the chosen Compose directory, and verifies the agent can read and write it.

## Changing a directory later

After the Pilot has connected, its Compose directory is fixed in the Edit node form. The server refuses a changed value with `PILOT_COMPOSE_DIR_LOCKED`, because the running agent is bound to the old path. Relocation is a separate controlled operation with its own preview, approval and verification; it is not a settings edit.

A Pilot that has never connected can still be corrected, with a warning that an already deployed but unconnected agent will not move. Regenerate its enrollment token after saving.

The Agent installation directory has no settings field. It is chosen only here.

## Limits

- Ubuntu 22.04 and 24.04 on x86_64 only.
- IPv6 targets, SSH agent forwarding, password authentication and passworded sudo are not supported in this release.
- The preflight never changes firewall, SSH server, Docker daemon, user or group configuration.
- The plan previews the official Docker repository only. When that repository is not configured yet, package versions are shown as unresolved and are resolved from the official repository at execution time.

## Troubleshooting

| What you see | What to do |
| --- | --- |
| `HOST_KEY_MISMATCH` | The live key differs from the pinned one. Compare the fingerprints on the host before replacing the pin. |
| `HOST_KEY_UNTRUSTED` | Trust the key first, or re-run **Check host key** if it changed between the check and the preflight. |
| `SSH_AUTH_FAILED` | Check the SSH user and that the public half of the key is in the user's `authorized_keys`. |
| `SSH_KEY_PASSPHRASE_REQUIRED` | The key is encrypted. Enter its passphrase. |
| `SSH_KEY_INVALID` | Use an OpenSSH private key, or convert an RSA key to PEM. PKCS8 ed25519 keys are not accepted. |
| `SSH_UNREACHABLE` or `SSH_DNS_FAILED` | Check the address, the port and outbound connectivity from the Sencho instance. |
| `INVALID_PATH` | The response names the field and the rule. Fix that field; typing is never blocked. |
| `BOOTSTRAP_IN_PROGRESS` | Another preflight for the same host and port is running. Wait for it to finish. |
| `PREFLIGHT_TIMEOUT` | The 90-second budget expired. Check the host's load and connectivity, then run it again. |
