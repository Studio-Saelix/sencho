---
title: Compose Networking
description: Inspect how a stack is connected and exposed, classify its intended exposure, and see where the running containers disagree with the Compose file, all without opening a terminal.
---

The **Networking** tab in the right-hand **Anatomy** panel answers two questions about any stack: *how is it networked and exposed according to the Compose file*, and *does what is actually running agree with that?* It renders the effective Compose model (the fully resolved result after interpolation, includes, profiles, `.env`, and `env_file` are applied), pairs it with a live Docker snapshot when the node is reachable, and presents both as plain, scannable facts.

The tab is read-only with respect to stack deployments: it never alters a container, a Compose file, or an existing network attachment. Two write operations are available: setting the stack's *exposure intent* (stored separately so Sencho can flag mismatches over time) and creating a new Docker network on the active node, which is available to admins and covered in [Creating networks](#creating-networks) below.

This tab stays stack-scoped: it models one deployment at a time. For a node-wide inventory of every Docker network, an interactive topology graph, and cross-stack findings, see the [Networking](/features/networking) page instead. A **view node networking** link at the bottom of this tab jumps there directly.

Compose Networking reads structure: network names, service-to-network membership, published ports, network modes, and the *names* of environment variables and labels, never their values. A secret injected through `environment:` or `env_file:` never appears in the view or the logs. One caveat: a structural field assembled by interpolating a secret (a network `name:`, a published port, or an `extra_hosts` entry built from `${VAR}`) is resolved before the inspector reads it, so its value does show. Keep secrets in `environment:` or `env_file:` rather than interpolating them into structural fields. See [Environment and Secrets Guardrails](/features/environment-guardrails).

## Accessing the Networking tab

1. Click any stack in the left sidebar to open it.
2. Switch to the **Networking** tab in the Anatomy panel header.

On a phone, the same information appears under the **Compose** section of the stack detail.

The tab appears only when the active node reports that it supports Compose Networking. A node running an older version of Sencho hides the tab until it is updated.

## Effective model rendering

When you open the tab, Sencho runs `docker compose config` on the active node to produce the effective model: the Compose file with all variable substitutions resolved, any `include:` and `extends:` directives merged, profiles filtered, and `.env` and `env_file` values applied. The networking facts you see always reflect this resolved model, not the raw file text.

**Network name resolution** follows Compose rules:

- By default, Docker names a network `<project>_<key>`, where `project` is the Compose project name (the `name:` field in the file, or the stack's directory name if absent) and `key` is the network's Compose key.
- If the network block declares its own `name:` field, that exact name is used instead of the `<project>_<key>` default.
- External networks use the Compose key directly (or the `name:` field if set), because they are expected to already exist on the host rather than being created by the stack.

When the Compose key and the resolved Docker name differ, the tab shows both: the Docker name in full text and the key in parentheses beside it.

If `docker compose config` cannot produce a model (usually a YAML error, an unresolved variable, or a broken `include`), the tab shows the error message and cannot display any facts. Fix the Compose file and reopen the tab to continue.

## Exposure intent

<Frame>
  <img
    src="/images/compose-networking/networking-exposure-intent.png"
    alt="The exposure intent section showing a stack row with REVERSE-PROXY highlighted and a swag service row with INHERIT highlighted and an arrow indicator reading 'reverse-proxy', with a detected line above the service pills reading 'detected: host-published' and a 'broad bind alongside reverse-proxy' note chip"
  />
</Frame>

Exposure intent is how you tell Sencho what a stack *should* be reachable from, so it can warn you when the runtime says otherwise. Set one intent for the whole stack, or override it per service when individual services have different exposure profiles.

| Intent | Meaning |
|--------|---------|
| **internal** | Not reachable from the host at all. Containers communicate only within Docker networks. |
| **same-node** | Reachable only from the host itself, through loopback-bound ports. |
| **lan** | Published for the local network. |
| **reverse-proxy** | Reached through a reverse proxy; no direct host port exposure expected. |
| **public** | Intentionally reachable from the internet. |
| **temporary** | A short-lived exposure (a label for tracking only, not a functional configuration). |
| **unknown** | Not yet classified. |

The intent is what you *want*; Sencho also reads what the stack actually says and shows that beside it. See [Detected exposure](#detected-exposure) below.

**How inheritance works:** the stack row's pill options end in **unset**, which clears the stack-level classification entirely. The per-service row's pills end in **inherit** instead: a service with no override of its own takes on the stack's intent, shown by an arrow indicator next to the inherit pill (for example, `→ reverse-proxy`). Selecting inherit on a service clears its override; selecting unset on the stack clears the stack's classification.

**Permissions:** editing the intent requires stack edit access. With read-only access you can see the current classification but not change it.

**How Doctor uses it:** Sencho stores the intent separately from the computed networking facts. When the two drift apart (a service classified `internal` that is publishing a host port or sits behind a tunnel, for example), the **Doctor** tab flags the mismatch. See [Compose Doctor](/features/compose-doctor) for the full list of exposure-aware findings.

**Tunnel-exposed services:** a service behind a Cloudflare Tunnel publishes no host port but is reachable from the internet, so classify it **public** (or **reverse-proxy** when the tunnel points at your proxy). A service reached over Tailscale or WireGuard is reachable only by the peers of that private network; **lan** is the closest intent. A service that only shares a network with a connector you know does not route to it, or that shares a network namespace with a cloudflared connector, can stay **internal**: Doctor asks you to confirm that, and Security takes the intent at your word. See [Tunnels and private overlays](#tunnels-and-private-overlays).

## Detected exposure

Every service row in the exposure-intent section also shows one quiet line: **detected:** the exposure Sencho can actually see, worked out from the rendered Compose model, the tunnel connectors in it, and, when Docker is reachable, the running containers. It is read-only: nothing is written unless you choose an intent, and Sencho never sets one for you.

| Detected answer | What Sencho saw |
|-----------------|-----------------|
| **public edge** | A Cloudflare Tunnel connector in the stack reaches this service. Always marked **unverified**: Cloudflare's ingress rules choose which origin a request reaches, and Sencho cannot read them. |
| **private overlay** | A Tailscale or WireGuard connector reaches this service. A shared network namespace is marked certain, because the peers address the connector directly; a shared or host network is unverified, because Serve, ACLs and AllowedIPs decide the routing. Peer authorization is never claimed. |
| **host-published** | The service publishes a host port, uses the host network, or shares the namespace of a service that does. When the bind is on every interface it is described as broad, never as reachable from the internet. |
| **same host only** | The only publish is a loopback-bound port (`127.0.0.1` / `::1`). |
| **no known exposure path** | Sencho found no path at all. This is absence of evidence, not a safety claim: it never means internal, isolated or safe. A service on an external network carries the caveat that a connector in another stack on that network could reach it. |
| **could not be determined** | The reach is hidden: the service shares a network namespace with a container from outside this stack, a connector runs in another container's namespace, a running container is attached to a network the stack does not declare, or a running container publishes ports the Compose file does not. |

When the reach is only partly known, the known paths stay listed and the answer ends in **partly undetermined**; the proof line in the services card names the reason. The same line names the namespace a shared host path comes from, the external networks a connector of another stack could reach over, and **runtime not checked** when Docker was unavailable or the service has no running container. A missing runtime is never shown as a clean result.

**What Sencho never claims:** internet reachability, verified Cloudflare or tailnet routing, peer authorization, or that a service is safe. An unrenderable Compose model shows the render error instead of a detection.

**Auto (detected).** When neither the service nor the stack has an intent, the picker reads **→ auto (detected)** and the answer line shows what Sencho sees. This is presentation only. A declared **unknown** is still a declaration: it shows the answer but offers no adoption.

**Conflicts.** When a declared intent contradicts the facts, one small chip follows the answer:

| Chip | When |
|------|------|
| **conflicts with internal: published port** | The service is classified `internal` or `same-node` but publishes a host port on a non-loopback interface. `internal` also flags a loopback-only port, the way Compose Doctor reads it. The chip names the intent you declared. |
| **conflicts with internal: host network** | The intent is `internal` or `same-node` and the service uses the host network. |
| **conflicts with internal: tunnel** | The intent is `internal` or `same-node` and a tunnel reaches the service with certainty, such as a Tailscale shared namespace whose peers address it directly. |
| **may conflict with internal: tunnel** | The intent is `internal` or `same-node` and a tunnel could route here, but its routing is configured outside the Compose file. |
| **broad bind alongside reverse-proxy** (or **temporary**) | The intent is `reverse-proxy` or `temporary` and the service binds on every interface or uses the host network. This is a note, not a contradiction: those intents may deliberately bind broadly. |
| **shared namespace with …**, **host network through …** | The service reaches the host only through another service's namespace. This stays a note, because no other Sencho engine counts it. |

A chip names the class of fact, never the port numbers; the services card below is the proof. The panel does not read Compose Doctor acknowledgements, so a **may conflict** chip stays until the intent changes or the tunnel goes away.

**Use same-node.** When nothing is declared and every path is an own loopback-only publication, the runtime was read, the service has a running container, there is no external network and no other doubt, the row offers **Use same-node**. One click writes that service's intent through the same control as the picker, and **inherit** on the picker clears it again. No other adoption is offered: a Cloudflare Tunnel could mean `public` or `reverse-proxy`, and an overlay could be `lan` or `internal`.

**Older nodes** do not report detection, and the line says so instead of guessing. If the intent list itself cannot be read, the section says so instead of showing **auto (detected)** or offering an adoption.

**Three meanings of "unknown".** The `unknown` *intent* is a declaration that you have not classified the service. The Fleet filter *unknown exposure* counts stacks that publish something without any intent. A detected **could not be determined** is about the evidence, not about you: Sencho saw the service but cannot establish its reach.

## Networks

  <img
    src="/images/compose-networking/networking-networks.png"

The Networks section lists every network the effective model declares:

| Element | What it shows |
|---------|--------------|
| **Name** | The resolved Docker network name Compose will use. |
| **Key** | The Compose key in parentheses, when it differs from the resolved name. |
| **external** badge | The network is expected to already exist on the host. The stack does not create or remove it on deploy. |
| **internal** badge | The network has no outbound connectivity; containers on it cannot reach the internet or the host network. |
| **created by stack** badge | Deploying the stack will create this network; it is absent until then. |

When a stack declares no explicit networks, the section shows **default network only**: all services share the implicit Docker bridge that Compose creates automatically.

External networks that do not exist on the node are detected before Compose runs. Interactive deploy opens a guided dialog so you can create safe bridge networks, copy a terminal create command, cancel, or open the Networking view. Automatic creation of those safe networks is optional under Settings → Stacks. Unsupported drivers or options are never created silently; the deploy stays blocked until you fix the Compose declaration or create the network yourself. Compose Doctor also flags missing external networks before you apply a change.

## Services

<Frame>
  <img
    src="/images/compose-networking/networking-services.png"
    alt="The services section showing a card for the 'swag' service with network membership on 'arr-net', two published ports (443/tcp and 80/tcp), each with an amber 'all interfaces' badge indicating they are bound to 0.0.0.0"
  />
</Frame>

Each service gets a card that summarises its networking configuration as Compose will actually apply it.

### Network membership and aliases

The card lists the networks each service belongs to. When a service declares `aliases:` for a network, those names appear in parentheses after the network key. Aliases are additional DNS names the service is reachable by within that network: any other service on the same network can connect to this one using the alias as a hostname, in addition to the default service name.

### Port bindings

Published ports appear with a badge indicating which interface they are bound to on the host:

| Badge | Colour | What it means |
|-------|--------|---------------|
| **all interfaces** | Amber | The port is bound to `0.0.0.0` (or `::` for IPv6), making it reachable from every network the host is attached to. |
| **loopback** | Green | The port is bound to `127.0.0.1` (or `::1`), reachable only from the host itself. |
| *Specific IP* | Neutral | The port is bound to the address shown. |

Port ranges appear as `startPort-endPort/protocol`, for example `8000-8002/tcp`.

A port with no host port number, such as `51820/udp`, `127.0.0.1::51820/udp`, or a host port of `0`, is published on a port Docker picks when the container starts. It appears as `auto-assigned/protocol` with the same badges and counts as a published port for exposure. It is left out of the Doctor's port-conflict and documented-URL checks because no number is known. Drift matches each auto-assigned declaration to the running container port it names, so the number Docker picked is not reported as drift. A fixed host number on that container port is treated as the number Docker picked, so a change from a fixed number to an auto-assigned one is not reported until the stack is redeployed. For these declarations, drift reports a target the container does not publish, a published port on a container port the service does not declare, a binding on a different interface than the file asks for, and two declarations that share one binding. A port listed only under `expose:` is not published and is not shown.

### Network modes

When a service uses `network_mode:` instead of individual network attachments, the mode appears as an amber badge beside the service name:

- **`network_mode: host`**: the service shares the host network stack entirely. Every container port is accessible directly on the host, even without any `ports:` entries. The card shows **all container ports / host-exposed** to make this explicit. Docker discards any `ports:` bindings in this mode, so Stack Drift does not compare the declared ports with the container's.
- **`network_mode: none`**: the service has no network connectivity at all.
- **`network_mode: service:<name>`** or **`network_mode: container:<name>`**: the service shares another container's network namespace.

### Tunnels and private overlays

Tunnels publish no host ports, so the port badges alone would make a tunnel-exposed service look internal. Sencho recognizes three kinds of tunnel connector in the effective model:

| Connector | Scope | How Sencho recognizes it |
|-----------|-------|--------------------------|
| **Cloudflare Tunnel** | Public edge: anyone on the internet through Cloudflare, unless Cloudflare Access restricts it | A `cloudflared` image, or a `TUNNEL_TOKEN` or `TUNNEL_TOKEN_FILE` variable |
| **Tailscale** | Private overlay: devices on the tailnet | A `tailscale` image, or a `TS_AUTHKEY` or `TS_AUTH_KEY` variable |
| **WireGuard** | Private overlay: WireGuard peers | A `wg-easy` image, a `WG_HOST` variable, or a `wireguard` image running as a server (`PEERS`, `SERVERURL`, `SERVERPORT`, `WG_HOST`, or a published UDP port) |

Sencho reads image names, variable *names*, `cap_add`, `devices`, mount targets, `network_mode`, network membership, whether a service publishes ports and on which protocol, whether `command` or `entrypoint` names the cloudflared `tunnel`, `proxy-dns`, or `access` subcommand, and whether `TS_EXTRA_ARGS` turns on `--advertise-routes` or `--advertise-exit-node` (in single- or double-dash form). A tunnel token, auth key, password, or other environment value is never retained in a finding or log. The node summary reads the variable names a service's `env_file` and `environment` set, and the one `TS_EXTRA_ARGS` value, the way Compose does: a name written with no value (`TUNNEL_TOKEN`, or `TUNNEL_TOKEN:`) counts only when the environment Compose runs in sets it, and left unset it removes the same name from an `env_file`; a `format: raw` env file keeps quotes and `$` literally and trims leading Unicode whitespace from each line, such as a no-break space or U+0085, as Compose does. The project `.env` and process environment are read only to interpolate and answer those names; the summary keeps none of them. An `env_file` in a format other than `raw`, or a name or reference it cannot answer without that environment, makes the stack count as unknown exposure. Containers that only connect outward are not reported: a WireGuard or other VPN client (a VPN for your torrent client, for example), a cloudflared DNS proxy (`proxy-dns` or `TUNNEL_DNS_*` settings), and a cloudflared `access` client. An explicit `proxy-dns` or `access` subcommand outweighs a mounted cloudflared config or a token. A connector with `network_mode: none` has no network and is not reported either.

The connector's card shows a badge such as **Cloudflare Tunnel connector · public edge**. Each service the connector reaches shows **via Cloudflare Tunnel (cloudflared) · public edge** (amber for a public edge, neutral for a private overlay):

- **Shares the connector's network namespace** (`network_mode: service:<connector>`, or the connector runs in the service's namespace): the service listens on the connector's own address. For Tailscale and WireGuard, overlay peers reach it directly, so Sencho counts the reach as certain. A cloudflared sidecar reaches it on `localhost`, but Cloudflare's ingress still decides which origin and port each incoming request reaches, so that path shows **routing unverified** like a shared network.
- **Shares a network with the connector**, or, when the connector uses `network_mode: host`, **publishes a host port or also uses the host network**: the connector can reach the service, but which services it actually routes to is configured outside the Compose file (Cloudflare ingress rules, Tailscale Serve and ACLs, WireGuard AllowedIPs). These services also show a **routing unverified** badge.

Sencho treats a Tailscale container on the stack's networks as forwarding beyond its own namespace only when `TS_ROUTES`, `TS_SERVE_CONFIG`, or `TS_DEST_IP` is set, or `TS_EXTRA_ARGS` advertises routes or an exit node (or its value cannot be read, for example a `${VAR}` or a key with no value when Sencho cannot read the environment Compose runs in, or a template Compose refuses; a key with no value that this environment does not set is unset and forwards nothing); when a flag is repeated, the last occurrence decides, as in Tailscale's own parser, whatever other flags sit between the repeats (a token after a value flag such as `--hostname` is that flag's value, not a repeat; after a flag Sencho does not recognize, a following repeat may be a flag or that flag's value, so an enabling repeat counts and a disabling one does not switch an earlier occurrence off); otherwise tailnet peers reach the Tailscale node itself. A Tailscale container on the host network makes the host itself a tailnet node, so it reaches every service that publishes a host port or uses the host network. A connector that runs in another container's namespace (`network_mode: container:<name>`) is reported with its reach unknown. A service with `network_mode: bridge` (or `default`) joins Docker's default bridge rather than the stack's networks, so it shares no network with a connector on those networks; two `network_mode: bridge` services share the default bridge with each other.

Reach is worked out within one stack. A connector on an external network may also reach services of other stacks on that network, and a connector on the Sencho Mesh network (declared in Compose, or added because the stack is opted into Mesh) may route to services on other nodes through Mesh aliases. Sencho cannot see those routes from the Compose file, so those services are not marked; the connector's Doctor finding names the networks instead. Tunnel detection never changes Mesh routing.

### Extra hosts

When a service declares `extra_hosts:`, the resolved hostname-to-IP mappings are listed at the bottom of the card. These entries are injected into the container's `/etc/hosts` file at startup.

## Runtime drift

<Frame>
  <img
    src="/images/compose-networking/networking-runtime-matches.png"
    alt="The runtime drift section showing a green card with a globe icon and the text 'runtime matches compose' in uppercase"
  />
</Frame>

When the node is reachable, the tab compares the declared effective model against the live Docker state and reports where they disagree. Four types of drift are detected:

| Finding | What it means |
|---------|---------------|
| **Attached to undeclared network** | A running container is connected to a network the Compose file does not declare for that service. Common after a manual `docker network connect` or a Compose file change that has not been applied yet. |
| **Foreign network attachment** | A container from this stack is connected to a network owned by a different stack. Cross-stack networking the file does not account for. |
| **Declared but unused** | A network is declared in the Compose file but no currently running service is connected to it. Often seen when a service is stopped or removed without `docker compose down`. |
| **Missing from runtime** | A network is declared but does not exist in Docker. The stack may not have been deployed, or the network was deleted externally. |

System-managed networks (`bridge`, `host`, `none`) and Docker's implicit default bridge are excluded from all drift findings. Attachments to `sencho_mesh` are also excluded when Sencho verifies that the container is its own instance or that the stack is opted into Sencho Mesh. A manual attachment from an opted-out stack remains visible as drift.

When the runtime matches the Compose file, the section shows a green **runtime matches compose** card.

When Docker is not reachable, the section shows **runtime unavailable, showing the declared model only**. The networks, ports, and exposure facts are still accurate; drift comparison resumes once the node is reachable.

**Relationship to the Drift tab:** the runtime drift shown here uses the same comparison logic as the [Drift Detection](/features/stack-drift) tab. The difference is history: the Drift tab records findings over time and shows when drift first appeared and when it cleared. The Networking tab always shows the current live state.

## Doctor findings

When Compose Doctor is available on the active node, a prompt at the bottom of the Networking tab directs you to the Doctor tab for deploy and security checks. The Doctor tab reads the same effective model and adds these exposure-aware findings on top of its standard checks:

1. A service classified **internal** or **same-node** that publishes a host port.
2. A service classified **internal** or **same-node** that a tunnel connector reaches.
3. A database or admin image published on all interfaces.
4. A tunnel connector, with its provider, scope, the services it reaches, and what Sencho cannot verify.
5. A stack that publishes ports or is reachable through a tunnel but has no exposure intent set.
6. A published port that the Stack Dossier's documented access URLs do not mention.
7. Reverse-proxy labels with no documented URL or reverse-proxy intent set.

See [Compose Doctor](/features/compose-doctor) for the complete check set and severity levels.

A **view node networking** link near the bottom of the tab opens the [Networking](/features/networking) operator page for the active node, scoped to node-wide inventory, topology, and findings rather than this one stack, for when you want to see this stack's networks in the context of every other stack sharing them.

## Creating networks

<Frame>
  <img
    src="/images/compose-networking/networking-create-dialog.png"
    alt="The Create network dialog showing a Name field, a Driver dropdown set to bridge, optional Subnet and Gateway inputs, and Internal and Attachable toggles"
  />

Admins can create a new Docker network directly from the Networking tab using the **create network** button in the panel header. This is the same dialog available from the node-wide [Networking](/features/networking) operator page.

| Field | Required | Description |
|-------|----------|-------------|
| **Name** | Yes | The Docker network name. Must be unique on the node. |
| **Driver** | Yes (default: bridge) | `bridge` for isolated single-host networks; `overlay` for multi-host Swarm networks; `macvlan` to assign MAC addresses; `host` or `none` for special cases. |
| **Subnet** | No | CIDR notation, e.g. `172.20.0.0/16`. Docker chooses a subnet automatically when left blank. |
| **Gateway** | No | Gateway IP for the subnet, e.g. `172.20.0.1`. |
| **Internal** | No | Prevents outbound connectivity from containers on this network. |
| **Attachable** | No | Allows containers outside Compose to connect to the network manually. |

After the network is created, the Networking tab refreshes automatically. The network appears in the Networks section of any stack that declares it as `external:`.

<Note>
  Creating a network here does not attach it to the current stack. To use the new network in a stack, add it to the Compose file under `networks:` with `external: true` (since Sencho created it, not the stack) and redeploy.
</Note>

## Limitations

- **No modify or delete from the stack tab.** Sencho can create networks (via the create network dialog on the stack tab or the operator Networking page) but never modifies or deletes existing networks from the stack tab. Cleanup is handled by `docker compose down`, the operator [Networking](/features/networking) page for inventory, or Resources prune actions.
- **Structural fields only.** Environment variable values and label values are never returned. Secrets interpolated into structural fields (network `name:`, ports, `extra_hosts`) are resolved and do appear.
- **Runtime drift requires Docker reachability.** When the node is not reachable, the tab shows the declared model but cannot compare against the live state.
- **Capability-gated tab.** The Networking tab only appears when the active node reports that it supports Compose Networking. Older nodes hide the tab until they are updated.
- **Render failure blocks all facts.** If `docker compose config` fails, the tab cannot show any networking information until the model can be rendered. The error message is shown, but raw Docker output is redacted.

## Troubleshooting

<AccordionGroup>
  <Accordion title="The Networking tab is not there">
    The tab appears once the active node advertises support for it. A node running an older version of Sencho hides the tab until it is updated.
  </Accordion>
  <Accordion title="The view says the runtime is unavailable">
    Sencho could not reach Docker on that node, so it shows the declared Compose model only and skips runtime drift. The networks, ports, and exposure facts are still accurate; the live comparison resumes once the node is reachable.
  </Accordion>
  <Accordion title="It says the model cannot render">
    `docker compose config` could not produce an effective model, usually a YAML error, an unresolved include or merge, or a required variable with no value. Fix the reported problem in the Compose file and reopen the tab.
  </Accordion>
  <Accordion title="I cannot change the exposure intent">
    Editing the intent requires stack edit access. With read-only access you can see the current classification but not change it.
  </Accordion>
  <Accordion title="The runtime matches compose but I changed the Compose file">
    The drift comparison compares the declared model against what is currently running in Docker, not against what Docker would run if you deployed now. The runtime reflects the last deploy. Deploy the updated file to bring the runtime in line with the file, at which point the comparison clears.
  </Accordion>
  <Accordion title="I see a foreign network attachment I did not configure">
    A foreign network attachment means a container from this stack is connected to a network owned by a different stack. This can happen when two stacks share a network by each declaring it as `external:`, when you ran `docker network connect` manually, or when a previously external network changed ownership. Check the Compose files for both stacks and compare against what the Docker daemon shows with `docker network ls` and `docker network inspect`.
  </Accordion>
  <Accordion title="A service shows no network membership">
    A service with no explicit `networks:` block attaches to the stack's implicit default network, which Docker creates automatically. The service card shows no named network membership in that case. Services on the same default network can still communicate with each other using the service name as a hostname.
  </Accordion>
</AccordionGroup>
