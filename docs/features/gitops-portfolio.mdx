---
title: GitOps Portfolio
description: A hub-wide workplace listing every Git-managed application, its canonical source/rollout/runtime evidence, and a triage queue of everything waiting on an operator.
---

The GitOps portfolio answers one question for the whole control plane: what is GitOps doing across every node right now, and what needs attention. It aggregates Direct Git sources and Blueprint-managed applications into a single hub-owned view, so reconciliation failures, pending reviews, drift, and unreachable targets surface in one place without visiting each node or stack.

The terms used on this page, such as the stages, the authority steps, and the answer, path, and evidence block, are defined in the [GitOps overview](/features/gitops-overview).

<Note>
  The GitOps portfolio is available on every tier, including Community.
</Note>

## Open it

Select **GitOps** in the main navigation (next to Fleet), or navigate to `/nodes/local/gitops`. The page lives on the hub: the active-node switcher does not change what it covers, and the entry is hidden while a remote node is selected.

The masthead leads with the portfolio's verdict, followed by counts for applications, pending (in progress), drifted, converged, and attention-required applications. Its meta line says how many nodes are reporting and when the data was last updated, and reads `refreshing` while a refresh is in flight.

| Verdict | When it appears |
|---|---|
| **Needs action** | At least one application has failed |
| **Needs attention** | Nothing failed, and something waits on an operator |
| **In progress** | Work is in flight and nothing else needs you |
| **Partially known** | Some applications are unknown, or some nodes could not be read |
| **Converged** | Every application provably converged |
| **Converged · qualified** | Every application converged, but none could be proven exact |
| **Unknown** | Nothing could be read, because every node failed to answer |
| **No applications** | Nothing is connected to Git yet |

Qualified convergence counts separately from exact convergence. An application whose runtime matches its intent but whose executable artifact could not be proven bit-identical is shown as `Converged · qualified`, never as fully exact.

The application list shows, per application:

- the name and target (**Direct** node, or **Blueprint** with its target count)
- the repository host and path and the configured ref (credentials never appear)
- the canonical source, placement and rollout, runtime, and health states, in the same words as the Git Source sheet
- confirmed drift, with its class
- the freshest activity timestamp Sencho holds for it

Rows with pending or failed items are tinted so the list reads as a signal. The reasons are in the **Attention required** list above it, and for a row beyond that list's cap, on hovering the state dot and in the application's own sheet. A status that arrived from a node running a newer Sencho build is shown with its raw state and flagged as unknown evidence, not reinterpreted.

Each row's activity timestamp comes from the GitOps history. The retention window is set under **Settings → GitOps** (see [Settings reference](/reference/settings#history)). A shorter window never changes what an application is running.

## The attention queue

Above the list, **Attention required** lists everything currently waiting: failed reconciliations, pending reviews or authorizations, preflight blocks such as an unready private registry, partial or paused rollouts, drift, stale or unreachable targets, and recovery states. Each application appears once, with its most urgent reason on a line of its own and a count of any others. Failure-toned entries sort ahead of pending decisions.

Each entry carries the step that resolves it, and the step happens where you are:

| Entry | Action |
|---|---|
| A source that failed to fetch | **Retry**, in place |
| A suspended source | **Resume**, in place |
| An update waiting for review | **Review update**, which opens that stack's Git Source sheet over the portfolio, pulled and showing the diff |
| A failed deploy or health check on a stack | **Open stack** |
| A hub-local Git-managed Blueprint | **Review**, which opens the Blueprint's own sheet where accept, approve, and authorize live |
| A node-scoped remote Blueprint | **Inspect** |

When your account cannot retry or resume a source, the entry opens the Git Source sheet instead of offering a button that would be refused.

A stack whose health check failed stops asking for you while that same version is deployed again and Sencho watches the replacement start. The reading ends once that redeploy's own health check settles, whichever way it went, so a redeploy that cannot confirm anything leaves the earlier failure standing. On a stack deployed straight from a Git source, the earlier failure shows again for a brief moment between the deploy finishing and that check opening.

## One application

Selecting an application, from the list or the attention queue, opens it over the portfolio, which stays where it was underneath. A Direct application is its stack's Git source, so it opens that stack's Git Source sheet. A Blueprint application opens its own sheet:

  <img src="/images/gitops-portfolio/application-view.png" alt="A Blueprint application sheet opened over the portfolio: a toolbar with Open Blueprint, an identity card, an application state block with its stage row and an Evidence control, a next authority step row offering Pull source and Review and approve placement, a Rollout controls row, and a target card" />
</Frame>

- **Identity.** The target, the repository and ref, the desired and fetched commits, the candidate and accepted source generations, and for a Blueprint the rollout generation.
- **Application state.** The [answer, path, and evidence block](/features/gitops-overview#reading-a-status-answer-path-evidence). For a Git-managed Blueprint the outstanding step appears here as an action: **Accept source**, **Review and approve placement**, or **Authorize rollout**. A live rollout also offers **Pause rollout** or **Resume rollout**, with replan, supersede, and rollback in the overflow menu beside the rollout authorization policy. The placement policy sits beside **Review and approve placement**.
- **Targets.** One card per node with its runtime state, health, connectivity, last known good state, deployed generation, and the artifact identity observed there. A target is never folded into an aggregate, and a node reporting a state this build does not recognize still gets a card that says so.
- **Drift.** Each confirmed divergence, expected versus observed, by class. Work that is merely in progress is not drift. See [GitOps drift](/features/gitops-drift-model).

When some targets could not be reached, a notice names them so their cards are not read as current. The sheet's URL carries the application, so it can be bookmarked or shared, and closing it (or the browser's Back button) returns to the list with its filters and scroll intact. If the owning node reports an application without evidence this hub can read yet, the sheet says evidence is unavailable and offers **Retry** instead of reporting the application as missing.

To act on a Blueprint application, use the outstanding action in the state section, or **Open Blueprint** in the toolbar, which replaces the sheet with the Blueprint's own detail sheet.

## Getting to related pages

Clicking anywhere on a row opens it. Every row also ends in a menu. A Direct row offers **Open Git source** (in place over the portfolio) and **Open stack**. A Blueprint row offers **Open application** for its sheet, and, for a hub-level Blueprint application, **Open Blueprint** for the Blueprint's detail sheet when your account can open Fleet. Next to the filters, **Connect a stack to Git** opens the Create Stack dialog on its **From Git** tab, and **New Blueprint** opens the Blueprint create dialog over the portfolio. An empty portfolio offers the same two actions.

The way back works too. A stack's Git source panel and a Blueprint's detail each have an **Open in GitOps portfolio** link that opens the portfolio narrowed to that application, and a Fleet node card shows a **GitOps · N attention** chip that opens the applications needing attention on that node.

## Filtering and search

Search matches application names, repositories, and refs. The **Filters** button opens one popover grouped into Attention, Target, Node, Drift, and Evidence, and shows a count of the filters in use. Together they narrow the list to applications requiring attention, to a target mode (Direct or Blueprint), or to a node, drift class, or evidence state (stale, unreachable, unknown). The node filter means involvement: a Blueprint application spans every node it targets and stays visible under each of them.

A stack connected to Git that has no GitOps application behind it still appears, with every state reading **unknown**, so its Git indicator never leads to a portfolio without it.

Filter state is part of the URL, so a narrowed view can be bookmarked or shared. **Clear filters** resets every filter at once, including ones that arrived through a shared link.

The Git indicator on a stack (the pending icon in the sidebar, or the source badge in the dashboard's Stack Health table) opens the portfolio narrowed to that one stack on its node, shown as a stack chip in the filter row. The portfolio lives on the hub, so an indicator clicked while a remote node is active switches to the hub first.

## Freshness and honesty

The portfolio refreshes on GitOps transitions, not on a timer. When a node cannot be reached, a coverage banner names it and its applications stay absent from the list rather than being reported with evidence Sencho does not hold. When a refresh fails after a good read, the page keeps the previous data and says it is showing last-known evidence and when it came from.

## Limits

- **Hub only.** The portfolio covers every node but is opened on the hub. It is hidden while a remote node is selected.
- **Row menus navigate.** Accepting, approving, and authorizing happen on the application's own sheet or the Git Source sheet, where the permission check and confirmation live. Only **Retry** and **Resume** run from the attention queue.
- **Unreachable nodes are absent, not guessed.** A Direct application on a node that does not answer is missing until the node answers. A Blueprint application with an unreachable target stays listed and is flagged as partial.

## What it is for

- An operator's daily sweep: open GitOps, read the verdict, and work the attention queue top to bottom. [Clear Your GitOps Attention Queue From One Page](/tutorials/work-the-gitops-portfolio) walks through one.
- Verifying a rollout or webhook pipeline end to end, across stacks and nodes.
- Finding drift concentrated on a node or in one class, for example all runtime drift across the fleet.

A Git-managed Blueprint application can be acted on in place from its sheet: the outstanding authority step, the rollout lifecycle controls, and rollout rollback. Everything else keeps its home on the owning stack or Blueprint surface, and the sheet links there instead of duplicating it.
