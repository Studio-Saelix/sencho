---
title: GitOps Portfolio
description: A hub-wide workplace listing every Git-managed application, its canonical source/rollout/runtime evidence, and a triage queue of everything waiting on an operator.
---

The GitOps portfolio answers one question for the whole control plane: what is GitOps doing across every node right now, and what needs attention. It aggregates Direct Git sources and Blueprint-managed applications into a single hub-owned view, so reconciliation failures, pending reviews, drift, and unreachable targets surface in one place without visiting each node or stack.

<Note>
  The GitOps portfolio is available on every tier, including Community.
</Note>

## Open it

Select **GitOps** in the main navigation (next to Fleet), or navigate to `/nodes/local/gitops`. The page lives on the hub: the active-node switcher does not change what it covers, and the entry is hidden while a remote node is selected.

## Reading the page

The masthead leads with the portfolio's verdict (`Converged`, `In progress`, `Needs attention`, `Needs action`, or `Unknown` when evidence is missing), followed by counts for applications, pending (in-progress), drifted, converged, and attention-required applications. Its meta line says how many nodes are reporting and when the data was last updated, and reads `refreshing` while a refresh is in flight. Qualified convergence counts separately from exact convergence: an application whose runtime matches its intent but whose executable artifact could not be proven bit-identical is shown as `Converged · qualified`, never as fully exact.

The application list shows, per application:

- the application name and target (**Direct** node or **Blueprint** with its target count)
- the repository host/path and configured ref (secret-safe; credentials never appear)
- canonical source, placement/rollout, runtime, and health states, using the same words as the Git Source sheet everywhere else in Sencho
- confirmed drift, with its class (source, runtime, placement, and so on)
- the freshest activity timestamp Sencho holds for it

Rows with pending or failed items are tinted so the list reads as a signal, not a spreadsheet; the reasons are in the **Attention required** list above it (and, for a row beyond the list's cap, on hovering the state dot and in the application's own sheet). Statuses that arrived from a node running a newer Sencho build are shown with their raw state and flagged as unknown evidence rather than being reinterpreted as something else.

## The attention queue

Above the list, the **Attention required** section lists everything currently waiting: failed reconciliations, pending reviews or authorizations, preflight blocks like an unready private registry, partial or paused rollouts, drift, stale or unreachable targets, and recovery states. Each application appears once, with its most urgent reason in a line of its own (so it is readable without hovering anything) and a count of any others. Each entry carries the step that resolves it, and the step happens where you are: **Retry** for a source that failed to fetch and **Resume** for a suspended one run right there, **Review update** opens that stack's Git Source sheet over the portfolio, pulled and showing the diff when an update is waiting, so you can apply it without leaving GitOps, **Open stack** takes you to a failed deploy or health check on a stack, and **Review** opens a hub-local Git-managed Blueprint's own sheet, where the accept, approve, and authorize actions live. A node-scoped remote Blueprint offers **Inspect** instead. When your account cannot retry or resume a source, the entry opens the Git Source sheet instead of offering a button that would be refused.

Failure-toned entries (failures, unreachable targets, failed rollbacks or recovery) sort ahead of pending decisions.

A stack whose health check failed stops asking for you while that same version is deployed again and while Sencho watches the replacement start. The reading ends once that redeploy's own health check settles, whichever way it went, so a redeploy that cannot confirm anything leaves the earlier failure standing. On a stack deployed straight from a Git source there is a brief moment between the deploy finishing and that check opening where the earlier failure shows again.

## One application

Selecting an application, from the list or the attention queue, opens it over the portfolio, which stays where it was underneath. A Direct application is its stack's Git source, so it opens that stack's Git Source sheet; a Blueprint application opens its own sheet, which shows, in order:

<Frame>
  <img src="/images/gitops-portfolio/application-view.png" alt="A Blueprint application sheet opened over the portfolio: a toolbar with Open Blueprint, an identity card, and an application state block with its stage row and an Evidence control" />
</Frame>

- **Identity**: the target (Direct node or Blueprint), the repository and ref, the desired and fetched commits, the candidate and accepted source generations, and for a Blueprint application the rollout generation.
- **Application state**: one status block. It leads with the application's overall state and the reason that needs an operator first, with a count of any others, and flags when the evidence behind it is partial or part of it could not be proven. Beneath it a single row names each stage that applies (source, artifact, placement, rollout, runtime) with its state; a stage that is blocking says why in a line of its own, and a stage that does not apply to this application is left out. **Evidence** opens what backs the answer: the authority steps with a recorded grant (source accepted, placement approved, rollout authorized, plus a legacy combined approval when one was recorded), the settled stages, each decision's policy line, and everything Sencho could not prove. A policy line says who is configured to decide that stage and what the policy actually did; a recorded decline also says when the policy recorded it, so a reason kept from an earlier moment reads as a fact about that moment rather than about now; when a rollout is in flight it also says which value it was decided under, because every rollout freezes the policy it executes. For a Git-managed Blueprint application, the step that is outstanding appears here as an action: **Accept source**, **Review and approve placement**, or **Authorize rollout**. A live rollout also offers **Pause rollout** or **Resume rollout**, with replan, supersede, and rollback in the overflow menu, alongside the rollout authorization policy. The placement policy sits beside **Review and approve placement**. A policy is offered only to a session that may act on what it governs, and is absent rather than disabled when it may not.
- **Targets**: one card per node, with its runtime state, health, connectivity, last known good state, the deployed generation, and the artifact identity observed running there. A target is never folded into an aggregate; a node reporting a state this Sencho build does not recognize still gets a card that says so.
- **Drift**: each confirmed divergence, expected versus observed, classified by class. Work that is merely in progress (a staged candidate, a queued rollout, a deployed target still awaiting its health verdict) is not drift. The classes, what each is measured against, and where each one appears are documented in [the drift model](/features/gitops-drift-model).
- Anything Sencho could not prove about the state shown is under **Evidence** in the application state, and the status block says how many items there are.

When some targets could not be reached, a notice names them so their cards are not read as current. The sheet's URL carries the application, so it can be bookmarked or shared, and closing the sheet (or the browser's Back button) returns to the list with its filters and scroll intact. If the owning node reports an application without evidence this hub can read yet, the sheet says evidence is unavailable and offers **Retry** instead of reporting the application as missing.

To act on a Blueprint application, use the outstanding authority action in the state section when one is offered, or **Open Blueprint** in the sheet's toolbar, which replaces the sheet with the Blueprint's own detail sheet over the portfolio.

## Getting to related pages

Clicking anywhere on a row opens it. Every row also ends in a menu that opens its stack or its Git source (the Git Source sheet opens in place over the portfolio) or, for a Blueprint application, its sheet; a Blueprint row also opens that Blueprint's detail sheet over the portfolio. Next to the filters, **Connect a stack to Git** opens the Create Stack dialog on its **From Git** tab, and **New Blueprint** opens the Blueprint create dialog over the portfolio; an empty portfolio offers the same two actions.

The way back works too: a stack's Git source panel and a Blueprint's detail each have an **Open in GitOps portfolio** link that opens the portfolio narrowed to that application, and a Fleet node card shows a **GitOps · N attention** chip that opens the applications needing attention on that node.

## Filtering and search

Search matches application names, repositories, and refs. Filter chips narrow the list to applications requiring attention, to a target mode (Direct or Blueprint), or combine with a node, drift class, or evidence-state filter (stale, unreachable, unknown). The node filter means involvement: a Blueprint application spans every node it targets and stays visible under each of them.

A stack connected to Git that has no GitOps application behind it (for example, one connected before GitOps tracking existed) still appears, with every state reading **unknown**, so its Git indicator never leads to a portfolio without it.

Filter state is part of the URL, so a narrowed view can be bookmarked or shared.

The Git indicator on a stack (the pending icon in the sidebar, or the source badge in the dashboard's Stack Health table) opens the portfolio narrowed to that one stack on its node. The narrowing shows as a stack chip in the filter row; remove the chip, or use **Clear filters**, to return to the whole portfolio. The portfolio lives on the hub, so an indicator clicked while a remote node is active switches to the hub first and opens the portfolio there. **Clear filters** resets every filter at once, including ones that arrived through a shared link.

## Freshness and honesty

The portfolio refreshes on GitOps transitions, not on a timer. When a node cannot be reached, it is named in a coverage banner and its applications stay absent from the list rather than being reported with evidence Sencho does not hold. When a refresh fails after a good read, the page keeps the previous data and says it is showing last-known evidence and when it came from.

## What it is for

- An operator's daily sweep: open GitOps, read the masthead verdict, and work the attention queue top to bottom.
- Verifying a rollout or webhook pipeline end to end, across stacks and nodes.
- Finding drift concentrated on a node or in one class, for example all runtime drift across the fleet at once.

A Git-managed Blueprint application can be acted on in place from its sheet's state section: the outstanding authority step, the rollout lifecycle controls, and rollout rollback. Everything else keeps its home on the owning stack or Blueprint surface, and the sheet links there instead of duplicating it.
