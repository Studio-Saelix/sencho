title: Git Sources
description: Link a stack to a Git repository, choose how far Sencho goes after each fetch, and review a classified change plan before files change on disk.
---

Git Sources turn a stack into a GitOps target. Point Sencho at a repository and ref (branch, tag, or commit SHA), choose one or more compose files to merge in order, pull updates on demand, on a schedule, or from a push event, and review a classified change plan before applying files to disk. Optional sibling `.env` sync keeps configuration consistent too.

<Note>
  Git Sources are available on every tier, including Community.
</Note>

New to GitOps in Sencho? [GitOps overview](/features/gitops-overview) defines the source states, policies, and status words used here. To run one repository across several nodes, see [Git-managed Blueprints](/features/git-managed-blueprints).

## How it works

1. Open a stack and click the **Git Source** button in the editor toolbar. From the [GitOps portfolio](/features/gitops-portfolio), **Connect a stack to Git** opens the same form as a new stack, and a row's menu opens an existing source over the portfolio.
2. Fill in the repository URL and ref, then choose the compose files. Use **Browse** to pick them from the repository tree, or type a path and press Enter. Add credentials if the repository is private; see [Git hosts and authentication](/features/git-authentication).
3. Click **Pull now** to fetch the latest commit. Sencho opens a classified change plan: adds, modifications, removals, and any local conflicts.
4. Click **Apply** to write the incoming files to disk. Apply stays disabled while local file conflicts are present. A Compose invocation change (for example a `.env` file added or removed outside Git) is shown in the plan and does not disable Apply. Applying records the incoming invocation as the new baseline and leaves unmanaged files on disk. Tick **Deploy after apply** in the same dialog to redeploy in one step.

Writes land in the stack's existing directory, using the same storage as the in-browser editor.

## Anatomy of the sheet

Git Source opens as a right-side sheet from the editor toolbar. It has a crumb (`Stack › {name} › Git source`, or `GitOps › {name} › Git source` when opened from the portfolio), a one-line summary of the linked ref, a toolbar, tabs, and a freshness line in the footer. A stack with no source yet has no tabs; the sheet opens on the form.

The toolbar offers **Pull now** when a source is linked and not suspended, **Detach** when a source is linked, **Save** for a stack with no source yet, and **Update** for a linked source only while something differs from what is stored. Confirmations open as separate dialogs on top of the sheet.

A linked source groups the sheet into tabs:

- **Overview.** The source's state with the commit it concerns, and the action that resolves it right there (**Review update**, **Retry**, or **Resume**, each when offered). A row beneath names each stage that applies, and **Evidence** opens the recorded authority and anything Sencho could not prove. **Open in GitOps portfolio** at the bottom jumps to the application's row. The header shows the last-applied commit (or **never applied**), the state, and the ref.
- **Source.** The repository, ref, compose files, project directory, sibling `.env` sync, authentication, and custom CA as a summary, with the managed-project manifest summary below it. **Edit** opens the form, and **Cancel** puts it back. A live Direct source can **Adopt onto Blueprint** from here.
- **Automation.** The apply behavior (changing it also offers **Update**), **Suspend** or **Resume**, and the provider hooks described in [Git webhooks](/features/git-webhooks).
- **Secrets.** Age identities and the encrypted-source policy; see [Repository secrets](/features/git-secrets).
- **Drift.** Only while the application has drift: each confirmed divergence, expected versus observed. See [GitOps drift](/features/gitops-drift-model).

When the source belongs to a Git-managed Blueprint, the sheet withholds **Save** and **Detach** and fetches through the Blueprint instead. See [Git-managed Blueprints](/features/git-managed-blueprints#convert-a-git-source).

Polling interval lives in **Settings → GitOps**. There is no per-source interval control.

## Create a stack from a Git repository

Click **Create Stack** in the sidebar, switch to the **From Git** tab, and fill in the same fields the Git Source sheet uses.

<Frame>
  <img src="/images/git-sources/create-from-git-tab.png" alt="New stack dialog with the From Git tab selected, showing stack name, repository URL, ref, an ordered compose files list with Browse, project directory, sibling .env toggle, authentication options, apply behavior radio group, and a Deploy after create checkbox" />
</Frame>

Sencho fetches the compose files, validates the merged result with `docker compose config`, writes them to a fresh stack directory, and links the source in one step. The last-applied commit is seeded from the fetch, so the first pull starts from a clean plan. Tick **Deploy after create** to run `docker compose up -d` straight away.

| Situation | What happens |
|-----------|--------------|
| Stack name already exists | Sencho returns **409** with "Stack already exists" and changes nothing. Pick a different name or remove the existing stack. |
| Repository unreachable or auth failed | The fetch fails before anything is created. The form stays open with an error describing the cause. |
| Fetched compose fails validation | No stack directory and no Git source row are created. The error shows the `docker compose config` message. |
| Fetch and validation succeed, optional deploy fails | The stack and source are kept. The toast reads "Stack created, but deploy failed: ..." and you retry the deploy from the editor. |

## Configure a source

| Field | Description |
|-------|-------------|
| **Repository URL** | HTTPS (`https://github.com/your-org/your-repo.git`) or SSH (`git@github.com:your-org/your-repo.git`, or `ssh://git@host:port/path` for a nonstandard port) |
| **Ref** | Branch, tag, or full commit SHA to track (for example `main`, `v1.0`, or a 40-character SHA) |
| **Compose files** | One or more paths in the repository, merged in the listed order. The first file is the primary. Reorder by dragging (or the arrows on a phone) and remove with **×**. |
| **Project directory** | Optional path passed to `docker compose --project-directory`, so relative build contexts, bind mounts, and `env_file` references resolve from that base. Blank uses the stack root. |
| **Also sync sibling `.env` file** | Also pulls the `.env` next to the primary compose file. The form shows the resolved path inline. |
| **Authentication** | **Public (no auth)**, **Personal Access Token**, or **Deploy key (SSH)**. See [Git hosts and authentication](/features/git-authentication). |
| **Apply behavior** | How far Sencho goes after a fetch. See below. |

Private hosts on your LAN or VPN are supported. Sencho refuses repository targets that resolve to loopback, link-local, multicast, or selected special-use addresses.

Saving runs a reachability check. If the URL is wrong, the credentials are invalid, the ref does not exist, or a file is missing, Sencho shows the error inline and persists nothing.

<Note>
  Changing the repository, the ref, the compose files, the project directory, or the `.env` sync clears any staged commit, because the plan was built against the settings you just replaced. Pull again to rebuild it. The state moves to **Reconcile required** if a commit had already been accepted, and to **Never reconciled** if none ever was. Changing only the token, deploy key, host-key trust, or the apply behavior leaves a staged commit alone, since none of them changes what would be materialized.
</Note>

### Multiple compose files

List the files in the order you want them merged and Sencho deploys with `docker compose -f base.yaml -f prod.yaml ...`, applying each later file on top of the earlier ones exactly as the Compose CLI does. The same ordered set is used for every action on the stack: deploy, update, restart, stop, and teardown.

On disk, the primary file lands as the stack's `compose.yaml` and each additional file keeps its repository-relative path inside the stack directory, so you can still browse and edit them in the file explorer.

### Apply behavior

| Mode | What Sencho does after a fetch |
|------|-----------|
| **Manual** | Nothing on its own. The source is not polled and never retries automatically. A pull you start, or a webhook delivery, still fetches the commit and stages the change plan, and nothing is written until you apply it. |
| **Review only** | Fetches and validates the incoming commit and marks the stack as having a pending update. You review the change plan and apply. |
| **Auto-write files** | Writes the new compose and env files to disk but does not redeploy. Use it when another process handles rollout. |
| **Auto-deploy** | Writes the files and runs `docker compose up -d`. |

Auto-deploy implies Auto-write. Whatever the mode, a **Deploy after apply** checkbox in the change plan lets you deploy on the spot.

**Manual** is the absence of the schedule, not a lighter review: the other three modes poll and retry on their own, and differ in who applies what they find. A manual source still answers when you ask. **Pull now** on a stack-owned source only fetches. **Suspend** pauses one source temporarily, webhooks included; **Manual** keeps it off the polling schedule until you change it back.

Automatic modes carry one safety check. When the incoming commit withdraws or renames a service that persists data (named volumes or bind mounts), or Sencho cannot prove it does not, the change is held for review and the stack shows **stateful change blocked**. The hold clears when you accept the change explicitly, dismiss it, or a newer commit is staged. Nothing is written or redeployed while it is held.

Git sources apply to stacks you link from the editor. An Inline Blueprint never evaluates a Git source; a Git-managed Blueprint takes its content from one.

## Polling

Unattended fetches use one interval per node, set under **Settings → GitOps** in the **Git sources** section (labelled *this node*). It applies to the node you have selected, so each node in a fleet keeps its own.

| Control | What it does |
|---|---|
| **Poll Git sources** | Turns scheduled fetches on or off. Off by default. Turning it on starts at 5 minutes. |
| **Poll interval** | Minutes between fetches, from 1 to 10080 (one week). Shown while polling is on. |

With polling off, sources still pull on demand, on a webhook, and on retry. Changing the setting reschedules every linked source that polls at once.

Every linked source inherits the interval, and there is no per-source interval. **Manual** sources are never polled. **Review only** sources fetch on the schedule and stage a plan for review. **Auto-write files** and **Auto-deploy** sources fetch and then follow their apply behavior.

## Suspend, resume, and retry

**Suspend** pauses reconciliation for one source: polling, webhooks, and automatic apply stop until you resume. **Suspend** and **Resume** are on the **Automation** tab, and **Resume** is also in the **Overview** while the source is suspended. An optional reason is stored with the suspension. **Resume** re-evaluates the source immediately rather than waiting for the next poll.

**Retry** is offered when the last attempt failed, a retry is already scheduled, or the deployed commit failed its health check, and not while the source is suspended. When a newer commit is waiting, the Overview offers **Review update** instead. It is stage-aware: a failed fetch refetches, and a failed apply or deploy continues from the evidence already on disk. Permanent failures, such as a missing ref, schedule no automatic retry, and neither does a **Manual** source; use **Retry** after you fix the cause.

## Pulling and reviewing changes

Click **Pull now** to fetch the latest commit on the configured branch, tag, or commit.

<Frame>
  <img src="/images/git-sources/diff-dialog.png" alt="GIT · CHANGE PLAN dialog for the demo-app stack, listing a modified compose.yaml and a count of unchanged files, with a Deploy after apply checkbox and Dismiss and Apply buttons in the footer" />
</Frame>

The change plan shows:

- The `GIT · CHANGE PLAN` kicker and the stack name.
- One row per classified operation: add, modify, remove, rename, a Compose invocation change, or a local conflict. Unchanged files collapse to a count.
- An **Incoming compose failed validation** banner when the incoming compose fails `docker compose config`. Apply stays disabled until validation passes.
- A **Local conflicts block apply** banner when a managed file was edited or removed on disk, or an unmanaged file sits in the way. Sencho does not overwrite them.
- A **Live Compose invocation changed** banner when the Compose command line on disk no longer matches the last applied generation. Apply stays enabled.

Secret-bearing paths appear as "secret-bearing managed path" instead of a filename. Click **Dismiss** to discard a pending update without applying it.

### Pending updates

While a fetched commit is staged, whatever the apply behavior, the stack gets a Git branch icon in the sidebar and a pulsing dot on the **Git Source** button. Hovering the icon names the state, and clicking it opens the [GitOps portfolio](/features/gitops-portfolio) on that stack. The **Git Source** button opens the sheet, where **Review update** on the **Overview** re-fetches the commit and opens the change plan. **Review update** in the portfolio does the same from there. If the stack also has an image update, the image-update dot takes priority in the sidebar, and the pending source is still shown on the **Git Source** button.

## Local edits vs Git

Sencho classifies every managed path against the last applied generation and the live disk.

- **Matches the last applied content.** Applying writes files Sencho itself last wrote.
- **Modified, missing, type-changed, or colliding unmanaged files.** The plan is blocked. Resolve them on disk, or commit them back to the repository, then pull again. A local edit blocks even when the live bytes already match the incoming commit, because classification compares disk to the last applied generation.
- **Compose invocation drift** (for example a root `.env` added or removed outside Git). The plan shows the change and stays applicable, and applying records it as the new baseline. Webhook auto-apply still refuses until you review that plan.

The in-browser editor and the Git Source sheet write the same files, so you can always fall back to editing locally. Pulls, applies, and create-from-git operations on one stack are serialized by a per-stack lock, so a webhook that fires mid-apply waits instead of racing it.

## What a pull materializes

Every repository-local input the project needs is materialized: the ordered compose files, implicit `compose.override.*` files, recursive `include:` and `extends.file` dependencies, service env files, file-backed configs and secrets, label files, and build contexts with `.dockerignore` semantics. The set is recorded in a versioned managed-project manifest, and each pull stages a candidate validated with the exact deployment invocation before anything on disk changes.

Inputs that cannot be reproduced safely fail the pull with a message naming the path and the reason: URL includes, Git LFS pointers, submodule contents, symbolic links, oversized build contexts, and `include` or `extends` declarations that point outside the repository or use dynamic `${VAR}` paths. Nothing is applied until the declaration is fixed. Absolute host paths, host bind mounts, external resources, and dynamic `${VAR}` data paths are recorded as unmanaged, never claimed as covered.

The project is bounded by file count, total bytes, per-file size, path depth, and build-context size, each adjustable with a `GITSOURCE_*` variable (see [Configuration](/getting-started/configuration)). Crossing a bound refuses the pull with the counts so far. Which Git features are supported at all is listed in [Git transport support](/features/git-transport-support).

## Failure, rollback, and detach

If apply is interrupted, Sencho completes the accepted generation or restores the previous one. If files were edited during the interruption and match neither, Sencho preserves them and requires manual recovery.

Git apply captures a recovery generation before it promotes files. If promotion fails mid-flight, Sencho restores the prior files. If apply-with-deploy fails after promotion, the applied files stay on disk and the generation remains available for manual rollback; Sencho does not compensate the failed deploy automatically. Rollback restores the managed authored inventory, not named volumes or bind-mounted application data.

**Detach** renders the effective compose model into a single `compose.yaml`, keeps the remaining materialized files, removes auto-discovered override files so the exported model is final, and removes Git tracking. Resolved environment values are baked into the exported file. If removal is interrupted, Sencho restores the original files.

Some read-only views, such as the dependency graph, drift snapshot, and networking inspector, summarize the primary compose file, so a service declared only in an override may not appear there. Deploy, update, image-update checks, and mesh attachment use the full merged set.

## Common setups

| Goal | Apply behavior | What triggers a fetch |
|---|---|---|
| Keep a homelab stack on `main` with no clicks | **Auto-deploy** | [Polling](#polling) or a [provider hook](/features/git-webhooks) |
| Review every change, then apply it | **Review only** | Polling or a provider hook, then **Review update** |
| Let Sencho write the files while another tool restarts the stack | **Auto-write files** | Polling or a provider hook |
| Change only when you decide | **Manual** | **Pull now** |

## What Git Sources do not do

- **They only read.** Sencho never commits or pushes. A file you edit in the editor stays local and shows as a local conflict on the next pull.
- **One source links one stack on one node.** To run one repository on several nodes, use a [Git-managed Blueprint](/features/git-managed-blueprints).
- **They do not delete what they do not manage.** Applying leaves unmanaged files on disk, and a rollback never touches named volumes or bind-mounted data.
- **A commit SHA never moves.** A source whose ref is a full SHA changes only when you edit the ref.
- **Not every Git feature is reproduced.** LFS pointers, submodule contents, symbolic links, and URL includes are refused; see [What a pull materializes](#what-a-pull-materializes).

## Troubleshooting

<AccordionGroup>
  <Accordion title="Branch or tag not found">
    The configured branch or tag is case-sensitive and must exist on the remote. Confirm it with `git ls-remote <url>` from a shell that has access. A full commit SHA never produces this error: it resolves to itself, so a SHA the host refuses to serve reports as "Commit not reachable on this host".
  </Accordion>

  <Accordion title="Branch or tag deleted or force-pushed">
    The ref previously resolved to a commit but no longer matches that history: it was deleted, renamed, superseded by a same-named tag, or force-pushed. Point the source at a current branch, tag, or commit, or restore the ref upstream, then save again.
  </Accordion>

  <Accordion title="Commit not reachable on this host">
    Hosts only serve commit SHAs they advertise. A commit that is not on a branch or tag tip, or a host that blocks unadvertised object fetch, returns this. Use a branch or tag, or a commit the host advertises.
  </Accordion>

  <Accordion title="File not found">
    Each compose path is relative to the repository root and must point at a file, not its parent directory. Every file in the list must exist on the tracked ref; if one is missing, the save or pull fails and names the path. If a file moved, update its path and save.
  </Accordion>

  <Accordion title="Compose validation failed">
    Sencho runs `docker compose config` against the incoming content before letting you apply. Common causes: unresolved `${VAR}` interpolation (commit a `.env` next to the compose file and enable sibling `.env` sync), invalid `include:` paths, or schema issues from a recent change. When the candidate includes a decrypted secret file, the banner shows a fixed message instead of the Compose diagnostic. Validation has a 10-second budget, so an unusually large compose may need splitting.
  </Accordion>

  <Accordion title="Local conflicts block apply">
    A managed file was edited or removed on disk, or an unmanaged file sits on a path the incoming commit wants to add. Restore or relocate the local copy, or commit the change back to the repository, then pull again.
  </Accordion>

  <Accordion title="Live Compose invocation changed">
    The Compose command line on disk no longer matches the last applied generation, most often because a root `.env` was added or removed outside Git. This is not a file conflict: Apply stays enabled, and applying records the incoming invocation as the new baseline. Webhook auto-apply will not write until you review that plan.
  </Accordion>

  <Accordion title="Pending commit has changed since this pull was fetched">
    You opened a change plan, then a webhook replaced the pending commit before you clicked **Apply**. Close the dialog and reopen the sheet; **Review** fetches the newer commit.
  </Accordion>

  <Accordion title="Applied but deploy failed">
    The files were written, but `docker compose up -d` did not complete. The toast names the reason, such as an image pull failure or a port conflict. The stack is already on the new content, so fix the cause and redeploy from the editor's **Deploy** button without re-pulling.
  </Accordion>

  <Accordion title="Network timeout">
    The clone did not finish within 30 seconds. Check that the Sencho host can reach the repository host (proxies, firewalls, DNS) and try again. For a genuinely large repository, pin a smaller compose subpath or mirror it closer to the host.
  </Accordion>

  <Accordion title="Repository too large">
    A clone is capped on the size of its temporary workspace (100 MB by default), and individual compose and env files are capped on read. Hitting either usually means the branch carries large binaries. Point the source at a repository or branch that holds only your compose and `.env` files, or have an operator raise the ceiling with `GITSOURCE_MAX_CLONE_BYTES`.
  </Accordion>

  <Accordion title="Stack contents look wrong or appear empty">
    If a compose file is tracked via Git LFS, Sencho refuses the link and reports an LFS error rather than write a pointer stub as real content. Commit the plain file, or replace the LFS pointer in place, then retry.
  </Accordion>

  <Accordion title="A build context or volume points at an empty folder">
    Git submodule contents are not cloned. Sencho warns when `.gitmodules` is present and refuses inputs and build contexts that reference submodule contents. Inline the files into the main repository or flatten the submodule.
  </Accordion>

  <Accordion title="An additional file named compose.yaml is rejected">
    The first file in the list is always written to the stack's root `compose.yaml`, so an additional file with that repository path is rejected. Rename it in the repository, or move it to the top of the list to make it the primary.
  </Accordion>

  <Accordion title="A relative build context or extends target is missing">
    The pull materializes the complete project, including recursive `include:` and `extends.file` dependencies. If a referenced file is still missing, the pull refused it and the message names the path and the reason (out-of-bound path, Git LFS pointer, submodule, symlink, or a size cap). Fix the declaration and pull again.
  </Accordion>
</AccordionGroup>

Authentication, host key, webhook, and SOPS problems are covered on [Git hosts and authentication](/features/git-authentication#troubleshooting), [Git webhooks](/features/git-webhooks#troubleshooting), and [Repository secrets](/features/git-secrets#troubleshooting).
