A **Blueprint** bundles Compose YAML with a node selector and a drift policy. You declare a stack once; Sencho handles the distribution and the reconciliation loop. A Blueprint's compose is either **Inline** (edited here) or **Git-managed** (bound to one live Git source). For an Inline Blueprint, every minute Sencho compares the live state on each targeted node against the desired revision, and either reports the drift, dispatches a notification, or auto-corrects, depending on the mode you picked. Git-managed Blueprints take content from an accepted Git generation: fleet place runs only after that generation is authorized for rollout, and never from the frozen detach snapshot stored on the Blueprint row.

Blueprints live under **Fleet · Blueprints**.

<Note>
  Blueprints are Sencho's Compose-first orchestration model. Creating, editing, withdrawing, and applying blueprints requires an admin role; operators and viewers can read the catalog and the detail sheet. Pinning a blueprint to a specific node lives under **Fleet · Federation** (admin role required).
</Note>

## Mental model

Four moving parts cooperate per blueprint.

1. **The declared spec.** A blueprint is a row in Sencho's database. It carries the compose YAML (or a frozen detach snapshot when Git-managed), the selector (labels or explicit node IDs), the drift policy, and a monotonic revision number. The revision auto-increments every time the Inline compose changes.
2. **Approvals.** Fleet mutation is gated on three distinct approvals, not a single combined fingerprint:
   - **Source acceptance** proves a specific accepted generation (Git SHA and materialization) is the content to run.
   - **Placement approval** freezes the node place/remove blast the operator confirmed (selector, pin, cordon outcomes).
   - **Rollout authorization** binds that accepted generation, its artifact set, and the current placement, and opens an immutable rollout generation before any place runs.
   Inline Confirm Apply writes placement approval (and an Inline rollout generation). Git-managed place additionally requires source acceptance and rollout authorization for the accepted generation, and each step is a separate action: **Accept source**, **Review and approve placement**, and **Authorize rollout** appear on the Blueprint sheet's GitOps section and on the application's page in GitOps, while that step is outstanding.
   Git-managed place also runs registry preflight before rollout authorization; a blocked result appears on the detail sheet until you fix registry readiness and authorize again.
3. **The reconciler.** A background loop on the controlling Sencho ticks every 60 seconds (with a 5-second initial delay after startup) and on demand after **Confirm Apply**. Each tick only mutates the fleet when the live placement approval still matches the resolved targets. The tick resolves the selector, compares every desired-vs-live node, and runs only the place or remove outcomes already approved.
4. **The executor.** Per-node deploy and withdraw run against the local Docker socket on local nodes, and through the authenticated proxy to `/api/blueprints/apply-local` and `/api/blueprints/withdraw-local` on remote nodes (older remotes fail closed until upgraded). Every blueprint deployment writes a `.blueprint.json` marker into the stack directory; the marker carries the blueprint ID, the revision, the last-applied timestamp, and, when Git-managed, the application and binding revision that produced the place.

The marker is the trust root. If a directory by the blueprint's name already exists on a node and does not carry a matching marker, the reconciler refuses to touch it and surfaces a **Name conflict** on the deployment row. A Blueprint named `nginx` will never overwrite an existing user-authored `nginx` stack on any node.

<Note>
  The revision number counts compose edits. It is a label on the spec, not a statement about the fleet: two nodes can both sit at revision 7 with one of them still deploying it. What Sencho has established per node is reported separately: the **Deployments** table on the detail sheet for each node's status, and the stack's Drift tab for its GitOps state. Where the two seem to disagree, the established state is the one that has been proven. The **GitOps** section of the detail sheet is narrower than either: it appears only when something about this Blueprint's own state could not be read or could not be proven.
</Note>

Statelessness vs statefulness is decided at author time by parsing the compose file. Stateless blueprints (no persistent volumes, or only `tmpfs` mounts) deploy and evict freely. Stateful blueprints (named volumes or bind mounts) get explicit operator-confirmation prompts on the first deploy to a fresh node and on eviction from any node. Blueprints with `external: true` volumes are classified as **unknown** and treated as stateful for safety.

Drift detection runs on every tick for every Active deployment regardless of policy. The policy only governs what Sencho does next: surface the drift silently, notify, or auto-redeploy.

## Key capabilities

**One declaration covers many nodes.** Pick nodes by label or by node ID. The selector set is re-resolved on every reconciliation tick. When a new node matches after a label change, the catalog shows **reapproval required** until you confirm the updated blast radius. Removing a label, removing a node, or shrinking the selector likewise needs confirmation before withdraw outcomes run (subject to the stateful-eviction safety rail).

**Drift detection always on.** Each tick compares the marker's revision against the live containers and the blueprint's current revision, then checks that all containers labeled with the compose project name are running. Drift is recorded on the deployment row whatever the policy is. **Observe** records it silently, **Suggest** also dispatches a notification, **Enforce** also redeploys.

**Stateful safety rails.** Stateful and state-unknown blueprints enter **Awaiting confirmation** on every fresh node before the first deploy, and **Evict blocked** when a node falls out of the selector while still hosting a stateful deployment. The reconciler never deploys empty volumes or destroys named volumes without a human acknowledging the action.

**Pin override and cordon respect.** Admins can pin a blueprint to a single node from **Fleet · Federation**. A pin replaces the selector entirely, deploys only to the pinned node, and overrides the cordon flag on that node. Cordoning a node otherwise prevents the reconciler from picking it for new placements; existing deployments on a cordoned node keep running and stay drift-checked.

**Vulnerability-policy participation.** Local blueprint deploys evaluate against the same pre-deploy policy gate that the per-stack deploy lane uses. If an enabled policy blocks one of the blueprint's image references, the deployment row moves to **Failed** and the stack is never written to disk. Remote blueprint deploys are routed through the remote node's stack deploy endpoint, so policy enforcement runs on the remote instance with that node's credentials and scanner state.

**Per-node, per-revision marker ownership.** Every blueprint deployment writes a `.blueprint.json` marker carrying the blueprint ID, revision, and last-applied timestamp. The reconciler refuses to touch any directory whose marker does not match its blueprint ID, so user-authored stacks and other blueprints can coexist on the same node without collision.

## Prerequisites

| Requirement | Detail |
|---|---|
| User role | **Admin** to create, edit, withdraw, accept, and apply. Operators and viewers can read the catalog and the detail sheet. Pinning requires admin. |
| Nodes | At least one node that the selector resolves to. Remote nodes need a healthy proxy connection; see [Multi-node management](/features/multi-node) and [Pilot Agent](/features/pilot-agent) for enrollment. |
| Compose YAML | Valid Compose YAML, 96 KiB or fewer. |
| Blueprint name | 1 to 64 characters matching `^[a-z0-9][a-z0-9_-]*$`. The name doubles as the stack directory on every targeted node. Rename is blocked while any non-withdrawn deployment or guard exists. |
| Selector | A `labels` or `nodes` selector with up to 200 entries per side. An empty resolved set is allowed but produces no deployments. |
| Compose directory | Per-node compose directory must be writable. Remote nodes must accept the controlling instance's bearer token; this is the same channel the rest of the fleet management already uses. |

## Anatomy of a Blueprint

| Field | Purpose |
|---|---|
| **Name** | Used as the stack directory on every targeted node (`<COMPOSE_DIR>/<blueprint-name>/`). Lowercase letters, digits, hyphens, and underscores only. Rename is allowed only when every deployment is withdrawn (or there are none); live placements and guards block rename. |
| **Description** | Short prose for the catalog tile and the detail header. |
| **Compose** | Standard Compose YAML. The same content ships to every targeted node as `compose.yaml`. Sencho parses it on save and classifies the blueprint as stateless, stateful, or unknown. The YAML must parse successfully and stay under 96 KiB. On a Git-managed Blueprint this editor is read-only: Git is the content authority, and the stored YAML is a frozen snapshot used only if you detach. |
| **Content origin** | **Inline** (the editor is the source) or **Git-managed** (one live Git source is the source). Convert moves that Git source onto the Blueprint; Detach restores Inline editing from the frozen snapshot. Credentials stay with the Git source. |
| **Selector** | Either label expressions (any-of plus all-of) or a list of node IDs picked by hand. |
| **Drift policy** | Observe, Suggest, or Enforce. Drift detection always runs; only the response differs. |
| **Reconciler enabled** | Toggle the reconciliation loop without deleting the blueprint. The **Disable** button on the detail sheet flips this toggle off; **Enable** turns it back on. Useful when you want to pause auto-deploys without losing the configuration. |

Sencho writes a `.blueprint.json` marker into each targeted node's stack directory. The marker carries the blueprint ID, revision, and the timestamp of the last apply. The reconciler refuses to touch any directory that does not carry a matching marker, so a Blueprint named `nginx` will never overwrite an existing user-authored `nginx` stack on any node. When the directory exists without a matching marker, the deployment row enters the **Name conflict** status until you rename one of the two.

Before a local Blueprint deploy starts, Sencho applies the same pre-deploy [vulnerability scan](/features/vulnerability-scanning) policy gate used by standard stack deploys. If an enabled policy blocks one of the Blueprint's image references, the deployment row moves to **Failed** and the stack is not written to disk. Successful local Blueprint deploys also trigger the normal post-deploy scan. Remote Blueprint deploys are routed through the remote node's stack deploy endpoint, so policy enforcement runs on the remote instance with that node's credentials and scanner state.

### Classification banner

The banner above the YAML editor shows what Sencho found when it parsed your compose file:

- **Stateless · portable** when no persistent volumes were detected, or only `tmpfs` mounts. Sencho can deploy and evict the blueprint freely on any node.
- **Stateful · pins to data** when named volumes or bind mounts were detected. Each node holds its own data; Sencho does not replicate volumes between nodes.
- **State unknown** when `external: true` volumes were detected. Sencho cannot prove portability and treats the blueprint as stateful for safety.

Click the signals toggle on the right of the banner (`1 SIGNAL`, `2 SIGNALS`, etc.) to expand the list of reasons Sencho classified the way it did, line by line.

### Selector

**By node label** shows one row of label pills for every label that exists on a node. Select the labels you want, then choose **Match any** (a node needs at least one selected label) or **Match all** (a node needs every selected label). Below the pills, the dialog lists the nodes the selection reaches now ("Matches 2 nodes"), so you can see the blast radius before you save.

If the label you need does not exist yet, click **+ Label** beside the pills. Type the label name, tick the nodes that should carry it, and click **Add label**. The label is selected for you and the match list includes the tagged nodes straight away, but nothing is written to the nodes until you continue: **Review rollout** (or **Create blueprint** where a rollout cannot be reviewed) adds the labels to the nodes, then opens the plan. The pending tags are listed under the match list and can be removed one by one. **Save as draft** stores the Blueprint only and does not add the new labels. Adding a label can move other Blueprints that already select it; Sencho reports how many were re-placed when the labels are written.

A Blueprint saved with both an any-of list and an all-of list keeps showing two rows when you edit it: nodes with any of the first row, and also all of the second.

**Specific nodes** picks nodes by name with a pill for each node. Use it for a one-off blueprint that runs only on a known node.

You can also manage labels from **Settings · Infrastructure · Nodes**. Each node row carries a Labels column with a `+` button.

### Drift policy

The three policy cards in the editor map exactly to the three modes the reconciler runs against every tick:

| Card label | Reconciler behavior |
|---|---|
| **Observe** · Detect & display, shown here, no alerts | Drift surfaces in the deployment table; no notification, no auto-fix. |
| **Suggest** · Detect & notify, you are alerted and decide | Sencho dispatches a `blueprint_drift_detected` notification through your notification routes, if any. |
| **Enforce** · Detect & auto-fix, redeployed to match, quietly | Sencho re-deploys the blueprint silently when drift is detected, and retries on each following tick for as long as the row stays **Drifted**. A `blueprint_drift_correction_failed` notification fires when an auto-fix attempt fails, once for that reason rather than on every retry, and a `blueprint_drift_repair_held` notification fires when auto-fix is declined. |

Even **Observe** keeps Sencho honest about what it found: the deployment row shows "drifted 3h ago: service caddy exited code 1". Silence would forfeit Sencho's authority over your fleet.

Enforce's auto-fix restores the exact generation and image identity the target already acknowledged, and nothing else. If a newer generation has been rolled out while a target is still on an older one, Sencho does not quietly put the older one back: the newer rollout has taken ownership of that target, so auto-fix is declined and the row reads **Repair held** until the newer rollout brings the target forward. Container-level drift (a stopped or crashed container) uses the ordinary deploy path. Frozen image-digest disagreement uses a digest-pinned overlay with `--pull never`, so authored tags on disk stay unchanged. For a remote target, Sencho freezes and repairs against that node's own rendered Compose model and Docker platform (fetched over the authenticated proxy), not the controlling instance's local filesystem. That repair also needs the target node to run a Sencho release that honors digest pins. A node that predates them would drop the pins and redeploy by tag, so the repair is refused and the node is reported as needing an upgrade instead, and the same applies when the node cannot be reached to confirm. The deployment row for that target ends in **Failed** with the reason, and a `blueprint_drift_correction_failed` notification fires. Upgrade the node, then trigger a deploy as you would for any other failed deployment; other drift modes are unaffected. A compose edit never reaches that auto-fix path on a stateful or state-unknown blueprint: any revision change re-enters **Awaiting confirmation** on every targeted node first, regardless of drift mode, so a human always signs off before a new revision touches existing data. See [Lifecycle: status transitions](#lifecycle-status-transitions).

### When a repair is held

Some drift cannot be repaired safely, and Sencho says so instead of trying. The deployment row ends in **Repair held**, the reason is on the row, and a `blueprint_drift_repair_held` notification fires. The workload is left exactly as it is, and the drift is still drift: a held target is not reported as up to date.

Holding only ever applies to **Enforce**, because it is a decision about auto-repair, and it is re-decided on every tick. In **Observe** and **Suggest** the drift is detected and reported normally, including for a stateful Blueprint, and Suggest still sends its notification. A hold also never hides drift: Sencho still checks the node and still reports what is running, it just declines to overwrite it.

The reason on a held row is the reason the repair was declined, not the drift itself, so the Drift panel is where you read what is actually running. A row held under Enforce also keeps reading **Repair held** if you switch to Observe or Suggest while the drift cannot be classified, until the cause clears.

Changing the drift mode does not re-open placement approval, so you can switch a Blueprint to Enforce and have it act on the generation it already acknowledged. On an **Inline** Blueprint a mode change is still treated as an edit to the Blueprint, so it re-enters **Awaiting confirmation** on every targeted node before the new mode takes effect.

A repair is held when:

- **The Blueprint is stateful, or Sencho cannot classify it.** Auto-fix is declined rather than risk volumes Sencho cannot prove are safe.
- **The rollout that owned the target has moved on.** The rollout replacing it advances the target instead.
- **Sencho cannot prove what the node is running.** The on-node marker names no generation, or names a different one than the target acknowledged.
- **The target's own evidence is not usable.** It is unreachable, its connectivity evidence is stale, an earlier change to it was interrupted, or a recovery or rollback owns it.
- **The generation and its approved image identity disagree.** The rollout froze a different pair than the target expects, so neither can be called current.

Most holds are a state rather than a block. Sencho keeps checking the target, so once the cause clears, for example a node comes back, the next reconciliation repairs the drift normally. To resolve one sooner, deploy explicitly as you would for any other target.

A hold whose cause is the rollout moving on is the exception: it stays until a later rollout covers that target. Superseding does not reverse, so Sencho will not reopen that rollout by itself, and a Git-managed Blueprint has no manual redeploy to fall back on, so the rollout is the only way out.

### Digest drift

A compose file names images by tag, and a tag is a promise rather than an identity: `nginx:alpine` can point at different content on different days, on different nodes, and at different times. Digest drift is the case where what a node actually runs no longer matches the image Sencho approved for that blueprint, compared per service and per platform. [GitOps Drift](/features/gitops-drift-model) is the reference for that comparison and for the states Sencho reports when it cannot compare; the per-service view is on the stack's [Drift tab](/features/stack-drift).

**What Enforce does with it.** The repair redeploys the blueprint against the approved digests, using a digest-pinned overlay and `--pull never`, so the approved content comes back, the tag in your compose file is left exactly as you wrote it, and nothing is pulled from a registry to make the repair. For a remote target, the freeze and the repair both use that node's own rendered Compose model and its own Docker platform, fetched over the authenticated proxy.

**What unverified means.** Sometimes Sencho cannot compare, and says so rather than guessing: the node was unreachable, the observation carried no per-service digest evidence, the approved set carried none, or the node's platform has no approved child for it. Unverified never becomes matched, and it never triggers a repair.

## The detail sheet

Click any tile in the catalog to open the blueprint detail sheet on the right. The sheet header shows the name, the meta line (`<selector> · <drift mode> · rev <n>`), and the action bar. For an Inline Blueprint, one status block below it answers whether the Blueprint is in sync and, when it is not, names the nodes and offers the verb that resolves it (**Re-apply**, **Review rollout**, **Review state**, **Evict**, or **Enable**); a quiet row under it shows approval and how many nodes are active. A Git-managed Blueprint shows its GitOps status block instead. After the status come the Inline or Git-managed badge with its conversion actions, the pin note when the Blueprint is pinned, the description, the deployment table, and a collapsible compose source. The action bar offers **Apply now**, **Edit**, **Disable** (or **Enable**), and **Delete**. **Convert to Git** sits beside the Inline badge; for a Git-managed Blueprint **Detach Git** and **Retire to Direct** (when no live deployments remain) sit beside its badge, and the sheet's GitOps section carries the outstanding authority action. **Apply now** is withheld because place for Git-managed content runs from an authorized accepted generation, not from Confirm Apply on the detach snapshot. **Delete** waits until you Detach Git or Retire to Direct, because the Git source still belongs to this Blueprint.

The deployment table lists every node currently in the blueprint's resolved selector set. Each row carries the node name, the deployment status, the last-activity timestamp, a notes column (drift summary or the last error message), and the action available for that row.

Possible status values:

| Status | Meaning |
|---|---|
| **Pending** | The reconciler has acquired the deployment lock and is about to start. |
| **Awaiting confirmation** | A stateful blueprint reached a new node. The reconciler refuses to deploy until you click **Confirm deploy** in the action column. |
| **Deploying** | The compose action is in flight on this node. |
| **Active** | The deployment is placed and its containers are running for this blueprint revision. Exact image identity is a separate GitOps / Drift proof; a row can read Active while Drift shows runtime artifact disagreement. |
| **Drifted** | The reconciler detected a difference between the live state and the desired one (marker, revision, container health, or frozen image digest). Under **Enforce** the next tick tries to repair it, and tries again for as long as the row stays in this state. Drift that is held or blocked instead does not come back here, because **Repair held** and **Name conflict** are waiting on you, not on the reconciler. |
| **Correcting** | An Enforce-mode auto-fix is in flight. An attempt that reports back without finishing leaves the row on **Drifted** with the reason in the notes column, for the next tick to try again. A row that stays here means the attempt never reported back at all, which a restart during a repair can cause, and it will not pick itself up. |
| **Repair held** | Drift was found and auto-fix was declined, with the reason on the row. Nothing was changed. |
| **Failed** | The deployment or withdrawal errored. The notes column carries the message. |
| **Withdrawing** | A withdraw is in flight. |
| **Withdrawn** | The deployment was successfully removed; the row is about to be cleared. |
| **Evict blocked** | A node left the selector while a stateful deployment was active. The reconciler refuses to evict until you choose an explicit mode. |
| **Name conflict** | A directory by the blueprint's name already exists on the node and does not carry a matching `.blueprint.json` (missing, malformed, or another blueprint ID). The reconciler will not touch it. |

## Lifecycle: status transitions

The common paths through the status enum.

- **Stateless first deploy.** No row → **Pending** → **Deploying** → **Active**. Drift detected later on Enforce flips to **Drifted** → **Correcting** → **Active**. Drift that cannot be repaired safely goes to **Repair held** instead and stays there until the cause clears. An auto-fix that fails goes back to **Drifted** with the reason in the notes column, and the next tick tries again, so a repair that fails once is not the end of it.
- **Stateful first deploy.** No row → **Awaiting confirmation**. Operator clicks **Confirm deploy** and picks **Deploy fresh** → **Deploying** → **Active**.
- **Compose change on a stateless deployment.** **Active** → **Deploying** on the next tick → **Active**.
- **Compose change on a stateful or unknown deployment.** **Active** → **Awaiting confirmation** on every targeted node so the operator can decide whether the new revision is safe for that node's local data. Operator confirms → **Deploying** → **Active**.
- **Node leaves a stateless selector.** **Active** → **Withdrawing** → **Withdrawn** and the row clears.
- **Node leaves a stateful selector.** **Active** → **Evict blocked**. Operator chooses **Snapshot, then evict** or **Evict and destroy data** → **Withdrawing** → **Withdrawn**.
- **Pre-existing stack collision.** New row → **Name conflict**. No further action without operator rename of the user-authored stack or of the blueprint itself.
- **Deploy or withdraw error.** Any in-flight status → **Failed** with the message in the notes column. The row stays put until the next tick or until the operator clicks **Apply now** to retry.

## Working with Blueprints

### Create

1. Go to **Fleet · Blueprints**.
2. Click **New Blueprint**.
3. Fill in the name, description, compose YAML, selector, and drift policy.
4. Watch the classification banner update as you type. It tells you whether the blueprint is portable or pinned to data.
5. Click **Review rollout**. Sencho saves the Blueprint, adds any labels you created in the dialog to their nodes, and opens the rollout preview. The blueprint starts with approval **pending**, and no fleet mutation runs until you confirm the preview. Choose **Save as draft** instead to store the Blueprint without a preview.

If the YAML is malformed or larger than 96 KiB, Sencho rejects the save before creating a Blueprint row.

### Apply on demand

The reconciler runs every minute, but only for Inline blueprints whose live placement approval still matches the resolved targets. To authorize or re-authorize a placement, click **Apply now** on the detail sheet (or **Re-apply** on a failed row or in the status block). Sencho opens a rollout preview that lists place and remove outcomes, requirements, and health notes. **Confirm Apply** stores that placement approval and runs the confirmed executor actions. If some nodes fail (for example a remote host is unreachable) or an unmanaged same-name stack blocks placement, Confirm still records approval, but the response and toast report those per-node outcomes instead of a clean success. Changing the compose, selector, name, pin, drift mode, or enabled flag clears placement approval back to pending. Catalog tiles show **pending** or **reapproval required** when confirmation is needed again (for example after a label change adds a new target node).

The preview also reads out the application's recorded GitOps authority: a single status block with the application's state and a row of the stages that apply, and under **Evidence** the **Source accepted**, **Placement approved**, and **Rollout authorized** steps that have a recorded grant, with the settled stages and anything Sencho could not prove. The source, ref, and commits and the per-target observations are listed below the status block. An approval recorded as a single combined decision rather than as separate authority steps is labelled a legacy combined approval and is never merged into those steps. An Inline Blueprint has no Git source or executable artifact set, so those two facets are omitted as not applicable while placement and rollout still report what is on record. Confirming binds to the evidence shown: if any recorded authority fact changes before the confirmation is stored, the apply is refused as stale and the dialog refreshes with the new evidence.

Raw `POST /api/blueprints/:id/apply` clients must send `{ planFingerprint, gitopsFingerprint, actions }` from a fresh `GET .../preview`. `gitopsFingerprint` is the evidence digest carried by that preview, and it is `null` only when there is no application evidence to bind. Both fingerprints must still match when the apply is processed; a body whose values no longer match, or that omits `gitopsFingerprint` when the preview carried one, is rejected.

### Edit

Click **Edit** on the detail sheet. On an Inline Blueprint, editing the compose bumps the revision. Stateless blueprints redeploy on the next reconciliation tick. Stateful and state-unknown blueprints re-enter **Awaiting confirmation** on every targeted node so the operator can decide whether the new revision is safe for each node's local data, whether or not the change actually touches a volume. On a Git-managed Blueprint the compose editor is read-only; selector, drift policy, and enabled still save.

### Convert to Git-managed content

**Convert to Git** moves an existing live Git source onto this Blueprint. Pick the source, review the preview, and confirm. The Blueprint becomes Git-managed: Git is the content authority, and the previous YAML is stored as a frozen detach snapshot only. Place never runs from that snapshot. When an accepted generation is ready, Sencho authorizes a rollout generation and places the materialized project from that generation onto the approved targets. Credentials stay with the Git source. Conversion also returns placement approval to pending.

The Git Source sheet for that stack becomes read-only until you **Detach Git** or **Retire to Direct**. Save, Detach, and Pull now are blocked there.

One repository backs at most one Git-managed Blueprint. Sencho matches repositories across the forms a Git URL can take, so the HTTPS URL and the SSH URL for the same clone count as one repository, whatever the port, with or without a `.git` suffix, and whatever the host casing. Converting a second Git source that points at a repository already claimed by a Git-managed Blueprint is refused; pick a different source, or **Retire to Direct** or **Detach Git** on the Blueprint that holds the claim first.

### Accept source, approve placement, authorize rollout

A Git-managed Blueprint takes each authority step as its own action. The GitOps section of the Blueprint detail sheet, and the application's page in GitOps, offer the step that is outstanding; once every step is recorded they offer nothing.

- **Accept source** records that a fetched candidate generation is the content to run. It appears when the source policy holds a candidate for review, which is always the case for a source whose policy is not automatic.
- **Review and approve placement** opens the rollout preview, the same reviewed plan the Inline flow shows: every node to place or remove, with its reachability. Confirming records the placement approval and freezes that blast for the current intent, so a later edit or roster change requires a fresh review. The button appears once source is accepted and the current candidate has no placement approval.
- **Authorize rollout** evaluates registry preflight, records the rollout authorization, and starts the sequential rollout across the approved targets. It appears while the rollout is not authorized or while the recorded authorization was granted against earlier inputs. Authorization needs resolved executable artifact evidence for the accepted generation, which the artifact card reports: while that evidence is unresolved or unavailable, the authorization is refused with the artifact identity as the reason, and a blocked registry preflight refuses it with the registry reason. When a target cannot start, the authorization is recorded and the surface reports what stopped the rollout.

### What a new commit does

A Git-managed Blueprint keeps tracking its source. When the source fetches a newer commit, that commit becomes a new candidate generation and the authority chain runs again for it:

- **Accept source** takes the new generation. Accepting it materializes the generation and attempts to resolve its executable artifact identity; if resolution cannot complete, the reconciler retries it before the next authorization.
- **Placement stays approved.** A content change does not move the target set, so the recorded placement approval still applies. A selector or roster change is what requires a fresh review.
- **Authorize rollout** records the authorization for the new generation and starts the sequential rollout across the approved targets. Under **Authorizes without an operator** the system attempts authorization after acceptance; when the artifact identity or registry preflight is not ready yet, the reconciler retries the preparation and authorizes once it resolves. A dispatch refused after authorization is held with the reason, and **Resume rollout** answers it.

If an authorized dispatch is refused, Sencho holds the rollout with the reason instead of leaving it reading as queued. The hold appears as a pause with that reason; **Resume rollout** answers it, and a resume whose dispatch is refused again records the new reason.

A generation whose approved compose the artifact resolver cannot model is refused rather than resolved from a guess. That covers an interpolated image reference, `profiles`, `extends`, `include`, and YAML merge keys. The reason is recorded on the Blueprint and shown with its evidence, and that generation waits for a later commit whose compose the resolver can read.

### Who decides each step

Each of the three steps answers the same question at a different point, so each has its own setting. They are independent: one does not imply or satisfy another, and changing one leaves the other two alone.

| Setting | Options | What it governs |
|---------|---------|-----------------|
| **Source policy** | Manual, Review, Applies without an operator | Which fetched source revisions apply on their own. |
| **Placement policy** | Operator approves each change, One stateless change at a time | Which placement changes are approved without you. |
| **Rollout authorization policy** | Operator authorizes each rollout, Authorizes without an operator | Which rollouts start without you. |

The source policy is set on the Git source, in its apply behavior. The placement policy sits beside **Review and approve placement**, and the rollout authorization policy is in the rollout overflow next to the health rollout policy, because both answer the same question about a rollout: what the system may do on its own, and what it should do when one fails.

**One stateless change at a time** is the whole of what the placement policy may do without you, and it is deliberately narrow. Sencho approves a placement change on its own only when the change adds exactly one node, or removes exactly one, and only when the workload it would run is stateless. Everything else falls back to you with the reason shown on the placement card:

- a change that both adds and removes nodes, or that moves more than one node either way
- a workload that carries data, or whose contents Sencho could not establish, which is treated as data
- a first placement that spans more than one node
- a node that is cordoned, gone, or was last seen unreachable
- a change that would leave the application with nothing running it
- an operation already in flight, for the application or for a node in the plan

Cordoning is a statement about where work may not go, not a decision to take work away, so a node you cordon is never withdrawn automatically. The withdrawal it would have caused falls back to you with that stated, and the workload keeps running where it is. Uncordon the node, or approve the move yourself.

Under **Evidence**, each decision carries its own policy line, saying who is configured to decide that stage and what the policy actually did. When the policy declined, the line also says when it recorded that reason. A reason is recorded the moment the policy runs, and Sencho re-decides only when something changes, so a reason recorded because an operation was in flight is still what is recorded after that operation finishes. Showing when it was recorded keeps it a fact about the moment the policy looked, rather than a claim about now.

When a rollout is already in flight the line also says which value it was decided under, because every rollout freezes the policy it executes: changing a setting changes what the next decision may do and leaves work already approved exactly where it is.

A disabled Blueprint withholds placement approval and rollout authorization until you enable it again, the same way **Apply now** waits for an Inline Blueprint to be enabled. Accepting source stays available while a Blueprint is disabled, because reviewing content changes nothing on the fleet.

The **Apply now** flow stays Inline-only. For a Git-managed Blueprint the rollout preview is a placement review: its confirm writes the placement approval instead of applying the frozen snapshot.

### Pause, resume, replan, or supersede a rollout

A live rollout also offers lifecycle controls on the same GitOps section, on the **Rollout controls** row:

- **Pause rollout** stops the rollout from advancing and asks for a reason. Nodes keep running what they already deployed, and a paused rollout never reads as converged.
- **Resume rollout** clears the pause and continues the sequential rollout when it is still authorized. If the authorization is no longer live, the surface says so instead of starting anything. If the dispatch is refused again, the rollout is held again with the new reason rather than left queued without one.
- **Replan placement** re-derives the Blueprint's target nodes and opens a fresh placement review, which withdraws the existing placement approval and rollout authorization. It appears in the overflow menu and refuses when the current placement already matches the Blueprint, so a review that is still accurate is not invalidated for nothing.
- **Supersede rollout** withdraws the rollout authorization and marks that rollout generation superseded. Nodes that already received it keep running it; the rollout reads as superseded until you authorize a new one.

Rollout authorization needs resolved executable artifact evidence for the accepted generation. While that evidence is unresolved, the authorization is refused with the artifact identity as the reason, and the lifecycle controls do not work around it.

### Roll back a rollout

Every Git-managed rollout deploy captures the node's previous project as a recovery generation before it applies anything, which is what a later rollback restores from. **Roll back rollout** lists the application's earlier generations, newest first, and asks for the scope: one target, the targets recorded as failed, unreachable, or stale, or every changed target in the rollout. A target already running the selected generation is skipped.

Each node in the scope must hold a recovery generation that names the selected application generation. A node keeps the generation captured immediately before its latest rollout, so an older selection has no recovery generation to restore from and is reported as a failed target; the rollout then reads as a partially failed rollback rather than a completion.

Rollback restores the authored project. It does not restore application data, and a locally built image is rebuilt from its authored inputs unless the node's recovery generation still holds the previous image. The per-target result states what actually happened.

A Blueprint with drift mode **enforce** keeps enforcing its current revision, so it will re-apply the accepted generation on the next reconciliation after a rollback. Switch that Blueprint to observe or suggest while a rollback should stand.

### Detach Git-managed content

**Detach Git** restores Inline editing from the frozen snapshot. Later Git commits are not written back. Detach is refused when that snapshot is empty (no generation exists to restore as Inline content). After detach, **Apply now** and compose editing return.

### Retire to Direct

**Retire to Direct** restores Direct GitOps targeting on the original source stack once every non-withdrawn deployment is gone. Credentials and the Git Source sheet return to that stack. Retire is refused while deployments are still active; withdraw them first, then retire. After retire, the Blueprint is Inline again (with no bound application), and the original stack's Git Source sheet is editable.

Click **Confirm deploy** in the action column to open the state review dialog. **Deploy fresh** creates empty named volumes on the target node and starts the stack with the default state from each container image. **Restore from snapshot** is reserved for the future Volume Migration feature and is currently disabled.

Click **Delete** on the detail sheet, then type the blueprint's name to confirm. ## Cordoned nodes

Cordoning a node prevents the reconciler from selecting it for **new** placements and skips state-review provisioning on it. Existing deployments on a cordoned node keep running, and drift checks continue normally. Pin policy overrides cordon, so a blueprint pinned to a cordoned node still deploys.

## Notifications

Two notification events fire from the reconciler:

- `blueprint_drift_detected` (warning severity), in Observe and Suggest modes when drift is detected. In Observe the row updates silently in the table; in Suggest the notification is also dispatched through your notification routes.
- `blueprint_drift_correction_failed` (error severity), in Enforce mode when an auto-fix attempt fails.
- `blueprint_drift_repair_held` (warning severity), in Enforce mode when a repair is declined. The deployment row reads **Repair held** with the reason.

Both events route through the standard alert pipeline. Configure delivery channels under [Notification routing](/features/alerts-notifications#notification-routing).

GitOps authority and rollout lifecycle decisions are also recorded in the notification history as they happen:

- source acceptance and rollout authorization for a Git-managed Blueprint, and placement approval for any Blueprint, including an Inline apply;
- rollout pause (with the reason you entered), resume, and supersede, including the automatic supersede of the previous rollout generation when a new one is authorized;
- rollout rollback start, completion, and partial failure;
- a stateful deployment held for its first-deploy confirmation, or for confirmation of a stateful revision change.

Each entry names the Blueprint and records the GitOps operation it came from. These categories are history-only: they appear in the bell, and they are not sent to your configured delivery channels.

## Security and trust boundaries

**Who can do what.** The user role determines the available actions. Reading the catalog, the detail sheet, and the deployment status is open to every role. Creating, editing, withdrawing, accepting a stateful deploy, and applying on demand require the admin role. Pinning a blueprint requires the admin role.

**The marker file is the trust root.** The reconciler will only deploy into, modify, or withdraw a directory that carries a `.blueprint.json` marker whose blueprint ID matches. A pre-existing directory with no marker, or a marker referencing a different blueprint, surfaces as **Name conflict** and is never modified.

**Local vs remote policy enforcement.** Local blueprint deploys evaluate the pre-deploy vulnerability policy gate against the local scanner state and credentials before the compose file is written to disk. Remote blueprint deploys are routed through the remote node's standard `/api/stacks` and `/api/stacks/<name>/deploy` endpoints over the proxy, so the remote node enforces its own policy with its own scanner state. The controlling instance does not bypass remote policy.

**Remote-node call path.** Sencho's controlling instance reaches remote nodes through the same authenticated proxy used by the rest of the fleet management surfaces, carrying the remote node's bearer token. Remote nodes do not need to accept any inbound connection beyond the one they already accept for fleet operations.

**Audit.** Blueprint create, edit, delete, pin, withdraw, accept, convert, and detach are administrative actions and are recorded through the standard [Audit log](/features/audit-log) pipeline along with the rest of the admin surface.

## Limitations and non-goals

By design, Blueprints do not include:

- A distributed storage layer (no CSI, no Longhorn-style replication).
- Automatic volume migration between nodes.
- Per-node parameter overrides or templating (one compose, all nodes).
- Staged or canary rollouts.
- Versioning history with one-click rollback. To revert, paste the prior compose into the editor and save.

Concrete operational constraints:

- **Reconciler cadence.** The tick interval is 60 seconds (5-second initial delay after startup). Approved blueprints reconcile on that cadence. Use **Apply now** and **Confirm Apply** after a change that clears approval.
- **Compose size.** YAML must be 96 KiB or fewer. Split very large compose files into smaller blueprints, or move generated content out of the compose body.
- **Selector size.** A selector accepts up to 200 entries per side (200 `nodes.ids`, or up to 200 each in `labels.any` and `labels.all`).
- **Name.** 1 to 64 characters matching `^[a-z0-9][a-z0-9_-]*$`. Rename is allowed only when every deployment is withdrawn (or there are none). Live placements and guards must be resolved first; rename clears approval back to pending.
- **Snapshot semantics.** **Snapshot, then evict** captures the compose YAML only. Volume bytes are removed by `docker compose down` just as with **Evict and destroy data**.
- **Restore from snapshot.** Reserved for the future Volume Migration feature and currently disabled in the state review dialog.

These omissions keep Blueprints honest: a compose-native fleet primitive that distributes the file you already have to the nodes you choose.

## Migrating stateful data between nodes (manual)

Sencho's compose-native lane does not include automatic volume shipping. **Snapshot, then evict** is a compose-only safety net: it preserves the YAML so you can redeploy elsewhere, but it does not move data. To relocate a stateful Blueprint's data from node A to node B, do it by hand before withdrawing:

1. Stop the Blueprint deployment on node A from the deployment table. Use **Snapshot, then evict** so the compose YAML is parked in [Fleet · Snapshots](/features/fleet-backups) while you handle volumes.
2. Use your host tooling (`docker run --rm -v <volume>:/data busybox tar -czf - /data > snapshot.tar.gz`, or app-aware tooling such as `pg_basebackup`, `mysqldump`, or `mongodump`) to capture the volume on node A.
3. Transfer the artifact to node B and restore it into the named volume there.
4. Update the Blueprint's selector to include node B; click **Apply now**, review the preview, and **Confirm Apply**.

A future Volume Migration feature will automate this with app-aware backup tooling.

## Practical workflows

**Multi-node identical reverse proxy.** A stateless `caddy-edge` blueprint with a labels selector matching `any=[edge]` and drift mode **Enforce**. Adding a new edge node deploys the proxy automatically within one tick. Editing the compose to bump the Caddy image redeploys every edge node on the next tick without operator intervention. Drift caused by a manual `docker compose down` on one edge node is corrected silently within a minute.

**Single-node managed Postgres.** A stateful `pg-fleet` blueprint with a `nodes` selector pointing at one database node and drift mode **Suggest**. The first deploy enters **Awaiting confirmation** so the operator chooses **Deploy fresh**. Subsequent compose changes (image bump, config change) re-enter **Awaiting confirmation** on the same node so the operator can decide whether the new revision is safe for the existing volume. Drift on the running container fires a `blueprint_drift_detected` notification but never auto-redeploys.

**Pin a blueprint to a specific node despite the selector.** Open **Fleet · Federation**, find the blueprint in the pin policy table, and pick the target node from the **Pinned to** dropdown. The pin saves immediately but also clears approval, so nothing moves until you open the blueprint here in Blueprints, click **Apply now**, and **Confirm Apply**. Once confirmed, the pin overrides the selector for that blueprint, deploys only to the pinned node, and also overrides cordon on that node. Useful for relocating a stateful service to a specific host without rewriting the selector. Clear the pin (and confirm again) to restore selector-driven placement.

**Observe-only audit blueprint.** A stateless monitoring stack (Vector, Promtail, a Prometheus exporter) with drift mode **Observe**. Drift is recorded silently in the deployment table; no notification fires and no auto-fix runs. Useful when you want Sencho to track placement and detect divergence on a low-signal stack without paging anyone.

## Troubleshooting

<AccordionGroup>
  <Accordion title="A deployment row shows 'Name conflict' and refuses to deploy">
    A directory by the blueprint's name already exists on that node without a matching `.blueprint.json` marker (missing, malformed, or owned by another blueprint). The most likely cause is a manually created stack with the same name. Resolution: rename either the existing stack or the blueprint, then click **Apply now** on the detail sheet to retry.
  </Accordion>
  <Accordion title="A stateful deployment is stuck in 'Awaiting confirmation'">
    The reconciler will not auto-deploy a stateful blueprint to a node it has never run on. Click **Confirm deploy** on the row, then choose **Deploy fresh** in the dialog. Sencho will create empty named volumes and start the stack.
  </Accordion>
  <Accordion title="A deploy was blocked by vulnerability policy">
    Open the **Security** page and review the active scan policies for the target node on the **Policies** tab. The Blueprint deployment row records the blocking policy and affected image count. Either fix the image, relax the policy, or deploy through an explicit admin-approved bypass on the stack surface. Blueprints do not silently bypass deploy enforcement.
  </Accordion>
  <Accordion title="Compose content was rejected on save">
    Sencho accepts valid YAML up to 96 KiB. Split very large compose files into smaller blueprints or move generated content out of the Blueprint. Do not paste secrets into the compose body; use environment files or [Fleet Secrets](/features/fleet-secrets) where appropriate.
  </Accordion>
  <Accordion title="A remote node is offline or disconnected during apply">
    The row moves to **Failed** with the remote error. Reconnect the node (see [Pilot Agent](/features/pilot-agent) and [Multi-node management](/features/multi-node)), verify whether the stack directory contains `compose.yaml` and `.blueprint.json`, then click **Apply now**. If the directory exists without a matching marker, Sencho treats it as a name conflict until you rename or remove the remote stack manually.
  </Accordion>
  <Accordion title="Remote apply or withdraw fails asking for an upgrade">
    Blueprint apply and withdraw on a remote node require that node's Sencho build to expose the atomic node-local endpoints (`/api/blueprints/apply-local` and `/api/blueprints/withdraw-local`). Older remotes refuse the mutation with a failed deployment row rather than writing files without ownership checks. Upgrade the remote instance to a matching Sencho release, then retry **Apply now** or withdraw.
  </Accordion>
  <Accordion title="A Docker daemon or registry failure surfaced during apply">
    The deployment row moves to **Failed** and records the Docker or registry error. Resolve the daemon, socket, registry credentials, rate limit, disk, or volume-permission issue on the affected node, then click **Apply now**. Watch that node's stack activity and security scan status after retry.
  </Accordion>
  <Accordion title="Drift is reported but never gets corrected">
    Confirm the drift policy is **Enforce** and that **Reconciler enabled** is on. Open the detail sheet to check the row's status and the most recent drift summary. If the row is sitting in **Awaiting confirmation** instead of **Drifted**, that is expected: a compose edit on a stateful or state-unknown blueprint never auto-corrects under any drift mode, including Enforce. It always waits for an explicit **Confirm deploy** so a human signs off before the new revision touches that node's data. Enforce's auto-fix applies to container-level drift (a stopped or crashed container) and to frozen image-digest disagreement on a deployment that is already **Active**. Unreachable nodes and missing digest evidence stay unverified and never auto-correct.

    When an auto-fix cannot finish, the row returns to **Drifted** with the reason in the notes column and the next tick tries again, so the reason there is what to fix: an unreachable node, a node running a Sencho release too old to honor digest pins, or a registry that cannot resolve the approved image. A row left reading **Correcting** is different: it means the attempt never reported back at all, which a restart in the middle of a repair can cause. Such a row does not retry on its own and Confirm does not act on it either, so treat it as needing your decision rather than as work in progress.
  </Accordion>
  <Accordion title="'Apply now' is greyed out">
    **Apply now** requires the blueprint to be enabled and Inline. Open the detail sheet, click **Enable** to flip the reconciler back on, then click **Apply now**. The button is also disabled while the detail sheet is in edit mode; save or cancel the edit first. Git-managed Blueprints do not offer Apply now: content comes from Git, and place runs from an authorized accepted generation rather than from the editor or the detach snapshot. Use **Detach Git** if you need Inline editing and Confirm Apply again.
  </Accordion>
  <Accordion title="Disabling a blueprint is rejected">
    Blueprints with active or drifted deployments refuse to disable, because doing so would orphan the running containers without a follow-up plan. Withdraw each affected deployment first, then disable the blueprint.
  </Accordion>
  <Accordion title="The data is gone after 'Snapshot, then evict'">
    Both eviction modes run `docker compose down`, which removes the named volumes managed by the stack on the target node. The snapshot stored in **Fleet · Snapshots** captures the compose definition only; the volume bytes are not included. To preserve data, capture the volume by hand before withdrawing (see *Migrating stateful data between nodes*). Bind mounts on the host filesystem are left in place by both eviction modes.
  </Accordion>
  <Accordion title="Eviction was aborted with 'Failed to capture compose snapshot before eviction'">
    Sencho aborted the eviction because the pre-eviction compose snapshot could not be written to the database. The deployment is still in place; nothing was destroyed. Check that the database is reachable, then retry the eviction. If you accept data loss and want to evict regardless, use **Evict and destroy data** instead.
  </Accordion>
  <Accordion title="A pinned blueprint did not deploy to nodes in its selector">
    By design. A pin replaces the selector entirely with the single pinned node, even if the selector resolves to other nodes. Either clear the pin in the Federation tab to restore selector-driven placement, or move the pin to a different node.
  </Accordion>
  <Accordion title="The reconciler took a minute to react to a change I just made">
    The reconciler tick interval is one minute for approved blueprints. After editing the selector, the compose, or the drift policy, click **Apply now**, review the rollout preview, and **Confirm Apply**. The same path recovers a row in **Failed** status.
  </Accordion>
</AccordionGroup>

## Common questions

<AccordionGroup>
  <Accordion title="Do Blueprints replace my existing stacks?">
    No. Stacks created in the per-stack lane (the **Stacks** sidebar) and Blueprints (the **Blueprints** tab) coexist on every node. A Blueprint is identified by its `.blueprint.json` marker; the reconciler refuses to touch any directory that does not carry one with a matching blueprint ID, so user-authored stacks are safe from blueprint actions.
  </Accordion>
  <Accordion title="Is a Blueprint the same as a Stack?">
    A Blueprint is a fleet-wide declaration: one compose YAML targeting a set of nodes. Each node where the blueprint resolves materializes as a Stack on that node, in the same compose directory layout the rest of the per-stack lane uses, with a `.blueprint.json` marker added. You can browse the materialized stack in the per-node Stacks view; the Blueprint is the source of truth that drives it.
  </Accordion>
  <Accordion title="How fast does drift get noticed?">
    After you confirm the updated rollout, the next reconciler tick (or the Confirm Apply execution itself) places or removes as approved. The reconciler ticks every 60 seconds with a 5-second initial delay after startup. Within Enforce mode, drift correction for an already-approved place outcome begins on the same tick that detects the drift, and a row that is still **Drifted** is checked and repaired again on each tick after that, so a repair that could not complete is retried rather than left in place.
  </Accordion>
  <Accordion title="Can I roll back to a previous revision?">
    Not through a one-click history. Blueprints intentionally do not keep a versioned revision history. To revert an Inline Blueprint, paste the prior compose into the editor and save; the reconciler treats the change as a new revision and redeploys. Git-managed Blueprints place from an authorized accepted generation, not from the detach snapshot. Detach Git first if you need Inline paste-and-apply.
  </Accordion>
  <Accordion title="Can a Git-managed Blueprint deploy?">
    Yes, from an authorized accepted Git generation. Accept the source, approve the placement, then authorize the rollout; each step is its own action on the Blueprint sheet's GitOps section and on the application's page in GitOps. Authorization requires resolved executable artifact evidence for the accepted generation, so the artifact card decides whether the rollout can be authorized; place never uses the frozen detach snapshot on the Blueprint row. Convert and Adopt bind the live Git source; Detach restores Inline editing when a snapshot exists.
  </Accordion>
  <Accordion title="Does the snapshot in 'Snapshot, then evict' contain my database?">
    No. The snapshot captures the compose YAML only, so you can redeploy the same definition elsewhere. Volume bytes (the database files, the cached state, the uploads directory) are removed by `docker compose down` along with the named volumes. To preserve data across an eviction, capture the volume by hand before withdrawing.
  </Accordion>
  <Accordion title="Why doesn't Sencho move volumes between nodes for me?">
    Volume migration is app-aware. A Postgres datadir is not the same kind of artifact as a Redis RDB file or a MinIO bucket, and a generic `tar` of the volume is rarely safe while the container is running. A future Volume Migration feature will integrate app-aware backup tooling. Until then, the manual workflow in *Migrating stateful data between nodes* is the supported path.
  </Accordion>
  <Accordion title="If I cordon a node, does that uninstall the Blueprints on it?">
    No. Cordoning only blocks new placements and skips state-review provisioning. Existing deployments on the cordoned node keep running and continue drift-checking. To uninstall a deployment from a cordoned node, withdraw it explicitly from the deployment table.
  </Accordion>
  <Accordion title="Can a Pilot-attached node host a Blueprint deployment?">
    Yes. The reconciler dispatches deploys to remote nodes through the standard proxy regardless of whether the remote runs in Pilot Agent or Distributed API Proxy mode. The remote node enforces its own vulnerability policy and writes its own marker file, the same way a local deploy does.
  </Accordion>
</AccordionGroup>
