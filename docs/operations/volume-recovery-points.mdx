title: Volume Recovery Points

A volume recovery point is a snapshot of the bytes inside one named Docker volume, stored in a recovery repository on the node that holds that volume. Sencho creates points, checks their integrity, and restores them into a new volume. This page covers the storage rules behind those actions and the HTTP calls that drive them.

<Note>
  Volume recovery points are managed through Sencho's API. The examples on this page use an API token created in **Settings > API Tokens**. See [API Overview](/api-reference/overview) for the token scopes, the base URL, and node routing. Reading status, points, and operations passes the scope check for a Read Only, Deploy Only, or Full Admin token; the role the token maps to still decides which records it may read. Every call that changes something (provision the repository, capture, verify, restore, cancel, release a lock) needs a **Full Admin** token: a Read Only or Deploy Only token is refused with `403 SCOPE_DENIED`. An Observe Only token is refused every recovery call.
</Note>

## Configuration recovery and data recovery are separate

Sencho recovers two different kinds of thing, and neither one restores the other:

- **Configuration recovery** brings back compose files. [Fleet Snapshots](/features/fleet-backups), their [Snapshot Vault](/features/fleet-backups#snapshot-vault) copies, and the recovery generations behind [Atomic Deployments](/features/atomic-deployments) rollback all restore authored files.
- **A volume recovery point** brings back the bytes inside one named volume: database files, uploads, queue state, and anything else the application wrote there.

Restoring compose files does not refill a database, and restoring a volume does not bring back a compose edit. A working recovery plan covers both.

## Points live on the same node as the data

<Warning>
  Recovery points live on this node, in a Docker volume on the same host as the data they protect. They are not an off-host copy: losing this host loses both.
</Warning>

The repository survives a container mistake, a bad deploy, and an accidental `docker compose down -v`, which is what it is for: the volume is gone, but its points are still listed, verified, and restored, with no need to recreate the volume first. The volume listing only shows volumes Docker still has, so keep the `storageId` and `pointId` of the capture operation (or read them from `GET /api/recovery/operations/{id}`) to address a point after its volume is gone. Take a separate off-host copy as well; [Backup & Restore](/operations/backup) covers the files, including the key material described below.

## Which volumes can be protected

A volume qualifies when all three are true:

- It is a named Docker volume.
- It uses the `local` driver.
- It declares no driver options.

Within the set it considers (a stack's declared volumes, or every volume on the node), Sencho lists each volume as eligible or refused, with the reason for a refusal, rather than quietly omitting it: for an operator, not listed and listed as refused mean different things.

| Volume | Why it is refused |
|--------|-------------------|
| A volume with driver options, which covers bind mounts, NFS, and tmpfs | This volume has driver options (a bind, NFS or tmpfs mount), which this release does not capture. |
| A volume on any driver other than `local` | Only volumes using the local driver can be protected. |
| An anonymous volume | This is an anonymous volume with no stable identity. Docker names these with a 64-character container id, and the name changes with the container. |
| One of Sencho's own volumes | This volume belongs to Sencho itself. |
| The recovery repository volume | This volume holds a recovery repository. |
| A volume whose name starts with `sencho-recovery-` | Sencho reserves this name for its own recovery infrastructure. |

A named volume that Docker does not have yet is not storage, so a stack that declares a volume before it exists is not listed until the volume exists.

Shared storage is one volume with several stacks behind it, not one volume per stack. Coverage and points follow the volume, and every stack that uses it is part of the access check. For a volume that no longer exists, the stacks Sencho recorded for it at its last capture stand in for the ones it can no longer see.

Locks do not follow the volume. Every operation takes the node's repository lock, so one capture, verification, or restore runs at a time on a node, whichever volumes are involved. Replacing the repository takes the same lock for as long as it builds the new repository, so a replacement cannot start while a capture, verification, or restore runs, and none of them can start while it builds. A second request answers `409 lock_held` ("Another recovery operation is running on this node") and is not recorded, so the same request with the same idempotency key can be sent again once the first one ends. A capture also takes a lock for its volume.

## What "Protected" means

A volume is Protected when one point satisfies all of the following:

- It is a root point: a capture of the whole volume, not of a single path.
- It belongs to the volume's current generation. A volume deleted and recreated under the same name is a new generation, and points of the old bytes stop counting. Reading coverage compares Docker's creation time for the volume with the one the generation was recorded with, so a recreated volume stops reading Protected right away, with reason `older_generation`, and does not wait for the next capture. A volume recreated within the same second keeps its creation time; the next capture reads the volume's root inode and opens the new generation.
- It completed. A point that skipped files or left files out is stored as `partial` and never counts.
- Its most recent verification says verified. Verification is a repository-wide check, described below.
- It finished within the last 7 days. Older points remain as evidence and are never deleted because they aged; they simply stop counting.
- The node reports volume protection as available: the helper image is present, the repository is provisioned, its stored key can be read, and startup finished.

Path points, which cover one path rather than a whole volume, never count toward Protected. They are never evidence that a volume is protected.

A check that fails writes a result against every point in that repository, so a mismatch makes every root in that repository read unverified (reason `integrity_mismatch`) until a later check passes. A check that could not run is recorded as an error, which also leaves points unverified (reason `unverified`).

A volume's coverage reason says precisely why it is not Protected: `no_point`, `in_progress`, `completion_unknown`, `stale`, `partial_point`, `failed_only`, `unverified`, `integrity_mismatch`, `older_generation`, `unsupported`, `inaccessible`, `identity_unknown`, or `evidence_inconsistent`. Sencho reports unknown evidence as unknown, never as green.

The aggregate verdict for a set of volumes is one of:

| Verdict | Meaning |
|---------|---------|
| `protected` | Every qualifying volume is Protected. |
| `partially_protected` | Some volumes are Protected and some are not. |
| `unprotected` | None are Protected. |
| `unknown` | Volume protection is not ready, or the evidence is incomplete. This includes a volume the caller may not read, which counts against the verdict on purpose. |

## Consistency labels

Every point carries one label describing what was observed while it was captured. The label is a statement about the capture, not about the application.

| Label | Meaning |
|-------|---------|
| `crash_consistent_live` | A container was running, paused, or restarting with the volume mounted at the start or the end of the capture, so files may have been mid-write. |
| `crash_consistent_stopped` | Nothing was observed using the volume at either check. Sencho stopped no container. An application that was simply idle may still have held unflushed state. |
| `unknown` | Sencho could not observe the volume before and after the capture, so it does not claim either label. |

Sencho never stops a container to make a capture quieter, and it makes no application-consistency claim. If you need a quiet database capture, stop the workload yourself, take the point, and restart it.

## Create a point

Creating a point is a root capture of the whole volume. Everything except the capture itself happens before Sencho answers: eligibility, readiness, the stacks that depend on the volume, the access check, a generation probe, the operation record, and the locks. That is why a held lock is a real `409` at request time rather than a background failure.

```bash
curl -X POST https://your-sencho-instance:1852/api/recovery/storage/points \
  -H "Authorization: Bearer $SENCHO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "volumeName": "web_data",
    "idempotencyKey": "point-web-data-2026-10-31"
  }'
```

A new request answers `202` with the admitted operation. Repeating the same request with the same idempotency key answers `200` with the operation it already created, so a retry after a dropped connection is safe.

```json
{
  "operation": {
    "id": "8f5f0a52-3a3e-4d78-9d55-5db0fbf0f0c7",
    "kind": "create_point",
    "state": "running",
    "storageId": "d0b4e4c2-6a2e-4d31-9f3b-3f1d7a3c1b11",
    "pointId": null,
    "actor": "operator",
    "transport": "local",
    "createdAt": 1761900000000,
    "completedAt": null
  },
  "failureDomain": "same_failure_domain",
  "warning": "Recovery points live on this node, in a Docker volume on the same host as the data they protect. They are not an off-host copy: losing this host loses both."
}
```

The capture itself runs in the background, in a helper container with no network and a read-only root filesystem. restic stages temporary pack files in the helper's scratch space before it writes them to the repository, so a capture gets a 512 MiB scratch and 2 GiB of memory; the size of the volume does not change what it needs. If the helper still cannot finish, the operation ends `failed` with `node_error`, not `repository_unavailable`. After the bytes are read, Sencho reads the volume's generation again. If the volume was recreated during the capture, the point is refused as `identity_unknown` rather than labelled with bytes that no longer exist. A successful capture is followed by a repository-wide metadata check before the operation ends.

Poll the operation to follow it:

```bash
curl https://your-sencho-instance:1852/api/recovery/operations/8f5f0a52-3a3e-4d78-9d55-5db0fbf0f0c7 \
  -H "Authorization: Bearer $SENCHO_TOKEN"
```

```json
{
  "operation": {
    "id": "8f5f0a52-3a3e-4d78-9d55-5db0fbf0f0c7",
    "kind": "create_point",
    "state": "succeeded",
    "errorClass": null,
    "completedAt": 1761900004821
  },
  "progress": null,
  "result": {
    "point": {
      "id": "5b1c8b7e-2f60-4a63-8f38-0f7f1d2c3a44",
      "kind": "root",
      "status": "succeeded",
      "consistency": "crash_consistent_live",
      "capture": { "fileCount": 1284, "byteCount": 91234567, "skippedCount": 0 },
      "completedAt": 1761900004821
    }
  }
}
```

A request refused at admission with `409` is not recorded as an operation. A node with no repository answers `503` with `errorClass: "capability_unavailable"` and `reason: "repository_not_initialized"`; provision one first.

An operation ends in `succeeded`, `partial`, `failed`, `cancelled`, or `completion_unknown`. A `partial` capture still produced a point, and that point never counts toward Protected. `completion_unknown` means Sencho lost the process mid-run; it is neither success nor a silent retry. You can stop a running capture with `POST /api/recovery/operations/{id}/cancel`, which settles the point as failed before it settles the operation. A repository provisioning operation cannot be cancelled.

## Verify a point

Verification runs a restic check over the whole repository, so its result covers every point in it, not just the one you name. The default method checks metadata; `engine_check_read_data` also reads every pack file back, which takes much longer and costs real disk reads.

```bash
curl -X POST https://your-sencho-instance:1852/api/recovery/points/5b1c8b7e-2f60-4a63-8f38-0f7f1d2c3a44/verify \
  -H "Authorization: Bearer $SENCHO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "idempotencyKey": "verify-web-data-2026-10-31",
    "method": "engine_check_read_data"
  }'
```

The request answers `202` with an operation. The result is appended as a verification record on every point in the repository, and a new check never rewrites an older one. A check that could not run is recorded as an error, which is not a pass. A check that finds damage ends the operation `failed` with `integrity_mismatch`: the check ran, and what it found is that the repository is not intact.

## Restore to a new volume

A restore always writes into a volume Sencho creates for the purpose. It never overwrites the source volume, and it never writes into a volume that already exists.

The target name must satisfy all of these:

- It is a name Docker accepts for a volume: at least two characters, starting with a letter or digit, then letters, digits, `_`, `.`, or `-`. Any other name answers `400 invalid_request` before anything is recorded.
- The volume does not exist yet.
- The name is not one of Sencho's own volumes.
- The name does not start with `sencho-recovery-`.
- If the name starts with a known stack's name followed by an underscore, you need the same access that changing that stack does.

Any other `targetMode` is refused as an invalid request. Restoring over a point's own volume is a separate operation with its own confirmation, described in [Restore over the existing volume](#restore-over-the-existing-volume). Restoring to a host path is not available.

```bash
curl -X POST https://your-sencho-instance:1852/api/recovery/points/5b1c8b7e-2f60-4a63-8f38-0f7f1d2c3a44/restore \
  -H "Authorization: Bearer $SENCHO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "targetVolumeName": "web_data_restore_20261031",
    "idempotencyKey": "restore-web-data-2026-10-31"
  }'
```

Sencho records a restore intent before any byte moves, creates the target with that intent's label, and re-inspects it to prove the volume it is about to write is the one it created. Docker returns an existing volume silently, so the label and the creation time are the proof. The restore then runs with verification, so every restored file is read back after it is written.

If the restore fails, Sencho removes only the volume it created, and only when it still carries the intent's label and no container mounts it. A volume that something started using is left in place and the operation ends `completion_unknown` rather than deleting data under a workload. The same reconciliation runs at startup, so a crash mid-restore is settled the same way.

Some extended attributes cannot be applied: file capabilities (`security.capability`) and SELinux labels are the usual cases. When those are the only failures, the operation reports `partial` with `errorClass: "attributes_not_restored"`, the restore result carries an `xattrWarnings` count, and the volume is kept, because the files are there and only part of their metadata is not.

A restore only works against the active repository. A point in a repository that has been replaced answers `503` with `errorClass: "repository_unavailable"` and `reason: "repository_replaced"`. Restore it before replacing, or take a new point.

## Restore over the existing volume

Restoring a point over its own volume puts the captured bytes back on the volume the data came from. The data stays on the same volume, so every stack that mounts it keeps its mount and its Compose file, and the volume keeps its name, its driver and its labels.

This is the destructive recovery path. Restoring to a new volume is the safer option: it never touches the running data, and it is the right choice when you can move a stack to a new volume. Use an overwrite when the data has to stay where it is.

### What the preview tells you before anything stops

Ask for the preview first. It writes nothing, changes nothing, and answers every fact the decision needs:

- the point: when it was taken, its consistency, and whether it is still the volume's current generation;
- the node the volume and the point live on, and how the request reaches it;
- the target volume with its storage generation, and whether it can be overwritten at all;
- every stack and container that mounts the volume, whether each is running, and the restart policy each has;
- whether anything is using the volume right now;
- how the swap is done, and that it is not one atomic step;
- an estimate of the space the restored copy needs, and the free space the helper could see;
- the fact that a point is taken before the overwrite starts, with the workloads stopped;
- the warnings that apply, and a confirmation token bound to exactly this state.

```bash
curl -X POST https://your-sencho-instance:1852/api/recovery/points/5b1c8b7e-2f60-4a63-8f38-0f7f1d2c3a44/overwrite/preview \
  -H "Authorization: Bearer $SENCHO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{}'
```

An answer looks like this, shortened:

```json
{
  "point": { "id": "5b1c8b7e-...", "consistency": "crash_consistent_live", "generation": 3, "isCurrentGeneration": true },
  "node": { "id": 1, "name": "docker-01", "transport": "local" },
  "target": { "volumeName": "web_data", "generation": 3, "generationToken": "...", "eligible": true, "ineligibleReason": null },
  "dependents": {
    "stacks": ["web"],
    "containers": [{ "id": "c1...", "name": "web-db-1", "stack": "web", "running": true, "restartPolicy": { "Name": "always" } }]
  },
  "inUse": true,
  "swap": { "method": "fenced_rename", "atomic": false, "supported": true, "reason": null },
  "space": { "requiredBytes": 734003200, "freeBytes": 5368709120, "sufficient": true },
  "preRestorePoint": { "required": true, "consistency": "crash_consistent_stopped" },
  "warnings": ["..."],
  "confirmation": { "token": "9f2c...64 hex characters" }
}
```

The token changes whenever the state does. A container that starts using the volume, a stack that starts or stops, the volume being recreated, or the recovery repository being replaced all produce a different token, so the token you confirmed can only ever describe what you actually saw.

### Confirm the overwrite

Send the token back with the volume name typed out. Both must match the current state, and you need the access that restoring a point from the volume's stacks requires.

```bash
curl -X POST https://your-sencho-instance:1852/api/recovery/points/5b1c8b7e-2f60-4a63-8f38-0f7f1d2c3a44/overwrite \
  -H "Authorization: Bearer $SENCHO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "confirmationToken": "9f2c0f5e8a1d4b7c6e3a2f9b8d5c4e1a7b0f3d6c9e2a5b8f1c4d7e0a3b6c9f2d",
    "confirmVolumeName": "web_data",
    "idempotencyKey": "overwrite-web-data-2026-11-03"
  }'
```

The answer is `202` with the operation. A refused admission writes no row, so the same idempotency key can be sent again once you have previewed and confirmed again.

### What happens, in order

1. **Stage and prove the point.** The point is restored and verified into a separate staging volume. A wrong key, a missing or damaged file in the repository, a full disk, or metadata that could not be restored all fail here. The live volume is untouched and no container has been stopped.
2. **Fence the workloads.** Every container that mounts the volume, running or stopped, is recorded, its restart policy is set to `no`, and then it is stopped. Setting the policy first means a Docker daemon restart after a power cut cannot bring a container back on data that is half swapped.
3. **Take a point of the current data.** With the workloads stopped, Sencho takes a root point of the volume as it is now. That point is held for the life of the operation. An overwrite without a complete pre-restore point is refused, and there is no option to continue anyway.
4. **Copy the point inside the volume.** The same snapshot is restored and verified again, into a hidden directory inside the target volume. The live files are still untouched.
5. **Swap by renames.** The original top-level entries are moved into that hidden directory, then the restored entries are moved up to the volume root, and then the captured root's owner, mode and modification time are applied. Every rename is atomic and the set of them is not.
6. **Delete the originals, then restart.** The hidden directory holds the originals, and it is removed before any workload starts, because some engines treat an unknown directory in their data root as data. Only after that do the restart policies come back and the containers that were running start again.

From then on the previous data is recoverable through the pre-restore point, which is held until the operation settles.

### The window that is not atomic

Docker cannot rename a volume or exchange two volumes, so there is no atomic replacement of a named volume. The swap above is a journaled series of renames instead:

- the workloads are stopped for the whole window, so nothing reads the volume while it is between states;
- each step is written to a journal before it happens, and the state is read back from the volume's own contents plus that journal, so a crash at any point can be resumed;
- before the swap completes, the direction is rollback, and the originals are put back;
- after it completes, the direction is roll forward, and the clean-up finishes.

The volume root itself is briefly in a state that is neither the old data nor the new data. That is why the workloads are stopped and why the operation is durable rather than a sequence of best-effort calls.

### After a crash

Startup settles every overwrite a previous process left open, and the operation reports where it ended. The rule is that a workload restarts only when the volume is proven to hold either the original entries or the complete new set:

| What the journal says | Result |
| --- | --- |
| the point was still being staged, nothing live moved | rolled back |
| the workloads were fenced but the swap had not started | rolled back, fence released, workloads restarted |
| the swap started and did not complete | originals restored from the journal, then rolled back and restarted |
| every entry moved but the journal did not record the commit | finished forward: the root metadata is applied and the commit recorded, then cleaned up and restarted |
| the swap completed | rolled forward, cleaned up, restarted |
| the journal or the volume cannot be read | left unsettled, fence kept held, `completion_unknown` |

An operation that ends `completion_unknown` keeps its restart policies pinned and its points held. Nothing starts until you decide.

### Resolve a restore that did not settle

Two actions, both explicit and both recorded in the audit log:

- `retry` runs the same reconciliation again. It is safe to repeat, and it is what you use after fixing whatever blocked it, such as a Docker daemon that was not reachable.
- `release_fence` accepts the volume as it now is. It restores every recorded restart policy, starts nothing, and leaves the operation `completion_unknown`, because accepting the fence does not prove what the data is.

```bash
curl -X POST https://your-sencho-instance:1852/api/recovery/restores/3f4a9c1e-7b2d-4e6a-8c5f-1d0e2b3a4c5d/resolve \
  -H "Authorization: Bearer $SENCHO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "action": "retry" }'
```

Both actions need the same access as the overwrite itself, and both are refused while the operation is still running.

### While the overwrite runs

The volume belongs to the restore until it settles. For as long as the fence is held:

- every Compose lifecycle action on a stack that mounts the volume is refused with `409` and the conflict action is `data_restore`;
- a container that mounts the volume cannot be started or restarted, including by auto-heal and by the scheduler;
- the Files & Volumes browser refuses the volume, for reading as well as writing;
- a second restore into the same volume is refused, and a capture of it is refused by the storage lock.

Deploying to a dependent stack during the overwrite is refused rather than queued. Wait for the operation to settle, or resolve it.

### Limits

- A container started outside Sencho, for example with the Docker CLI on the host, is not fenced. Sencho checks again just before the swap starts and refuses if one is running, but a container started in the moment between that check and the swap is not stopped.
- The restored data is crash consistent, not application consistent. A database may need to recover, replay or check its files on the next start. Nothing quiesces the application first.
- Your Compose files and environment files are not changed. Only the contents of the volume change.
- The recovery repository is a Docker volume on this host. Losing the host loses both the data and the points that protect it.
- An overwrite is only admitted when the target can be restored into. The recovery repository's own volume, Sencho's own volumes, reserved names, an anonymous volume, a volume using a driver other than `local`, a volume with driver options, and any volume mounted by the container that runs the Docker endpoint are refused.
- While the fence is held, a container's restart policy differs from its Compose model, so drift observation may report it. Enforcement redeploys are refused by the fence.
- If Sencho cannot read its own recovery records, for example after a downgrade to an older build, the fence checks cannot answer. Sencho then refuses nothing on that basis and logs one warning, so a manual start or a deploy is not blocked by the record; the containers' restart policies are still pinned to `no`, so a Docker daemon restart does not bring them back. Fix the build mismatch and restart Sencho before resolving the restore.
- Cancelling is accepted until the swap starts. From that point the answer is `409` with `errorClass: "not_cancellable"`, because the originals have begun to move and the only safe endings are roll forward or reconciliation.

### Operation result

`GET /api/recovery/operations/:id` for an overwrite adds a `restore` block to the intent: `mode`, `phase`, `fenceState`, `preRestorePointId`, `stagedVerified`, `filesRestored`, `bytesRestored` and `outcomeClass`. It names volumes and counts, never a host path or the contents of a file.

The outcomes are distinct: `succeeded`, `failed` with an error class, `cancelled` only before the swap starts, `partial` with `errorClass: "cleanup_failed"` when the data is committed but the work directory could not be removed, and `completion_unknown` when the state could not be proven.

## The recovery repository

Each node writes points to one active recovery repository: a dedicated Docker volume with a restic repository in it, on the same Docker engine. Provisioning is explicit and idempotent, so the same request can be repeated after a crash at any step and continues instead of starting over.

```bash
curl -X POST https://your-sencho-instance:1852/api/recovery/repository \
  -H "Authorization: Bearer $SENCHO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "idempotencyKey": "provision-repository-2026-10-31" }'
```

The repository password is generated once, encrypted with the instance key in `DATA_DIR`, and never shown by any response. Sencho reads it only for the duration of one helper run.

<Warning>
  Losing `sencho.db` or `encryption.key` makes the repository unreadable. There is no recovery path for a point whose key is gone. The points still exist in the repository volume, and nothing can open them. Back up both files together; see [Backup & Restore](/operations/backup).
</Warning>

Repeating the request on a node whose repository was already made (it has a fingerprint) opens that repository and compares it with the one on record, pulling the helper image first if it is missing. The operation ends `succeeded` only when the repository opens. If the repository volume is gone or empty, or the volume opens with this key but holds a different repository, the operation ends `failed` with `errorClass: "repository_unavailable"` and repairs nothing, so sending it again without `replace` gives the same answer until the volume is restored. A key that no longer opens the repository ends `failed` with `repository_key_unavailable`, and a helper image that cannot be pulled ends `failed` with `capability_unavailable`. The check only reads, so it runs while a capture is running. If a replacement is moving the active repository at the same moment, the request answers `lock_held` as an operation; send it again. Start a fresh repository when the old one cannot be opened:

```bash
curl -X POST https://your-sencho-instance:1852/api/recovery/repository \
  -H "Authorization: Bearer $SENCHO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "idempotencyKey": "replace-repository-2026-10-31", "replace": true }'
```

A replacement answers `409 lock_held` and is not recorded while a capture, verification, restore, or another replacement is running, so wait for it to end and send the same request again. It answers `409 lock_stale` while an interrupted operation's repository lock is still held; release that lock first, as described under [Release a stale lock](#release-a-stale-lock). A replacement creates a new repository volume and moves the active pointer to it. The previous repository and every point in it are kept, and its access key is not overwritten. Its points are no longer covered by new checks, and they stop counting when they age out of the 7-day window. A point in a repository that is no longer active cannot be restored through the API, so restore anything you still need before replacing.

Read the repository's state:

```bash
curl https://your-sencho-instance:1852/api/recovery/repository \
  -H "Authorization: Bearer $SENCHO_TOKEN"
```

```json
{
  "health": "available",
  "reason": "engine_registered",
  "failureDomain": "same_failure_domain",
  "warning": "Recovery points live on this node, in a Docker volume on the same host as the data they protect. They are not an off-host copy: losing this host loses both.",
  "initialized": true,
  "repository": {
```

## The helper image

Every recovery action runs in a small helper container built from a pinned restic. The Sencho image carries the digest of the helper built from the same commit, and starts only that digest. A tag is refused on purpose: a tag can be repointed at different bytes after the pairing was sealed.

Normally there is nothing to configure. The Sencho image sets `SENCHO_RECOVERY_HELPER_IMAGE` to `repository@sha256:...`, and provisioning pulls it once when it is missing. Status reads never pull.

On an air-gapped host, load the helper image with `docker load`. That drops the repository digests, leaving only an image id, so set the variable to the id:

```yaml
environment:
  - SENCHO_RECOVERY_HELPER_IMAGE=sha256:3f7c1b9d0a2e4f6a8b0c1d2e3f4a5b6c7d8e9f0a1b2c3d4e5f6a7b8c9d0e1f2a
```

A tag in that variable is refused and the node reports `helper_unavailable`, which is the truthful answer: Sencho cannot prove which bytes it would run. Accepted forms are a digest reference (`name@sha256:...`) or an image id (`sha256:...`).

## Docker socket proxies

If Sencho reaches Docker through a socket proxy, that proxy must allow the calls recovery needs.

- **Container creation refused:** recovery cannot start a helper. A capture or restore request fails with `capability_unavailable`, or a running operation ends `failed` with that class, and no point is recorded as protected. Nothing reports success.
- **Volume creation refused:** provisioning the repository, or creating a restore target, fails with `capability_unavailable`, and no point is recorded as protected.

A node whose recovery actions fail this way keeps its last known status, which can read `available` if the image is present and the repository opens. Treat a `capability_unavailable` answer as the authority on the action that failed, and fix the proxy before retrying.

See [Docker socket proxy](/operations/self-hosting#docker-socket-proxy) for the API groups a proxy needs to allow.

## Growth and retention

Nothing removes points, and nothing prunes the repository. Every point you create adds packs to the repository volume, and every restore leaves a new volume behind until you remove it. Plan disk for both:

- Keep an eye on the repository volume's size. There is no automatic cleanup.
- After you have checked a restored volume, remove it with `docker volume rm` like any other volume you no longer need.
- A replacement repository starts empty but keeps the old volume, so a replace does not reclaim space by itself.

Sencho never removes a repository volume. The volume remove route, the prune plan, the managed sweep, and the fleet prune skip it. Stack removal cannot skip one volume, so it refuses outright: taking a stack down with volumes removed, or deleting it with volumes pruned, answers `423` with `code: "recovery_volume_protected"` when the stack's compose file declares a volume under the `sencho-recovery-` prefix (or one Sencho records as a repository volume, external or not), or when the stack's volumes cannot be read, for example because its compose file does not render or an env file it names is missing. Nothing is stopped or removed. Take the stack down, or delete it, without removing volumes, or remove that volume from the compose file first.

## Remote nodes

A recovery request for a remote node runs on that node. The control instance forwards the call, the owning node authorizes it and does its own work, and only metadata comes back; the volume's bytes never pass through the control instance. Target a node with the `x-node-id` header or the `?nodeId=` query parameter.

A role assigned on the node itself covers every volume on that node, including a volume shared by several stacks and a volume no stack declares, whether the request runs on that node directly or is relayed by the control instance. A role assigned on a single stack covers only a volume that stack alone uses, and only when the request runs on that node directly: a stack-scoped grant is refused over a relay, so give the operator a node-wide grant to use recovery on a remote node.

Reading points requires read access to the stacks that use the volume. Capturing and restoring require edit access to those stacks. Provisioning or replacing the repository, and releasing the repository lock, are administrator actions.

## The HTTP surface

Every request below takes a Bearer token and, for a remote node, the usual node routing. The `GET` calls accept a Read Only, Deploy Only, or Full Admin token; the `POST` calls (repository, capture, verify, restore, overwrite, cancel, resolve, and lock release) need a Full Admin token, and any other scope, Observe Only included, gets `403 SCOPE_DENIED` before the request reaches the route. The capture, verify, restore, overwrite, and repository calls require an `idempotencyKey` of 1 to 200 characters. A new request answers `202`; a replay of the same key answers `200` with the operation it already created. Reusing a key for a different request is refused.

### Read this node's recovery status

```bash
curl https://your-sencho-instance:1852/api/recovery/node \
  -H "Authorization: Bearer $SENCHO_TOKEN"
```

```json
{
  "contractVersion": 1,
  "volumeProtection": {
    "capability": "volume-protection-v1",
    "version": 1,
    "state": "available",
    "reason": "engine_registered"
  },
  "operationId": null
}
```

`state` is `available`, `unavailable`, `update_required`, or `unknown`. An `unavailable` node names why: `engine_not_installed`, `schema_newer_than_build`, `recovery_store_unavailable`, `engine_starting`, `helper_unavailable`, `repository_not_initialized`, `repository_unavailable`, or `repository_key_unavailable`. `operationId` echoes the dispatch id when a control instance relays the read, and is null for a direct call.

### Release a stale lock

A stale lock means an interrupted operation may have left a restore half written. Releasing a storage lock is a reviewed act, so it is never automatic. Startup releases the repository lock of interrupted work, as described below. A live lock belongs to its owner and cannot be released here.

```bash
curl -X POST https://your-sencho-instance:1852/api/recovery/locks/release \
  -H "Authorization: Bearer $SENCHO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "scope": "storage",
    "resourceKey": "7d1e9c0b2a4f6e8d0c1b3a5f7e9d2c4b6a8f0e1d3c5b7a9f2e4d6c8b0a1f3e5d"
  }'
```

```json
{
  "released": {
    "scope": "storage",
    "resourceKey": "7d1e9c0b2a4f6e8d0c1b3a5f7e9d2c4b6a8f0e1d3c5b7a9f2e4d6c8b0a1f3e5d",
    "ownerOperationId": "8f5f0a52-3a3e-4d78-9d55-5db0fbf0f0c7",
    "processEpoch": "3a7b1c2d-4e5f-4a6b-8c7d-9e0f1a2b3c4d",
    "acquiredAt": 1761900000000,
    "staleSince": 1761900030000
  }
}
```

Use `scope: "repository"` with the repository id to release the repository lock. Review the interrupted operation before releasing its lock: check the operation, its point, and any target volume it left behind. The route answers `lock_held` when the lock is still owned by a live operation. A volume whose source no longer exists can still have its storage lock released.

A restart does not leave the node closed. When Sencho starts it removes the helpers a previous process left and clears restic's own locks. Once no helper of the previous process remains, it releases the repository lock of an interrupted provisioning, because the next provision request continues it, and, if restic's locks were cleared, the repository lock of any capture, verification, or restore that was interrupted, because none of them leaves anything in the repository to review. The volume that was being captured keeps its storage lock until you release it. If a helper could not be removed, or restic's locks could not be cleared, the repository lock stays stale and an administrator releases it.

### Preview, confirm and resolve an overwrite

| Route | Body | Answers |
| --- | --- | --- |
| `POST /api/recovery/points/:pointId/overwrite/preview` | none | `200` with the facts and the confirmation token. Writes no row and changes nothing. |
| `POST /api/recovery/points/:pointId/overwrite` | `idempotencyKey`, `confirmationToken`, `confirmVolumeName` | `202` with the operation, or `200` on a replay. A refusal writes no row. |
| `POST /api/recovery/restores/:intentId/resolve` | `action`, either `retry` or `release_fence` | `200` with the outcome the reconciler reached. |

The preview needs the access that restoring the volume's stacks requires, and the overwrite and resolve need the same. A target that is not eligible answers `400 invalid_request`. A token that no longer matches the state answers `409 precondition_failed`. A target without room for the restored copy answers `507 insufficient_space`. A restore whose operation is still running in this process answers `409 lock_held`. The walkthrough, including what stops, the non-atomic window, and the crash table, is in [Restore over the existing volume](#restore-over-the-existing-volume).

### Error responses

Every error from these routes has the same shape, except the `403 SCOPE_DENIED` that an API token of the wrong scope gets before the request reaches a route: that body carries `error` and `code` only, with no `errorClass`. `code` is the upper-cased error class, so a client can switch on one field. A refusal can also carry a `reason`, a stable token for the specific cause: `engine_starting`, `repository_not_initialized`, `repository_replaced`, `not_cancellable`, `generation_changed`, `dependents_changed`, or `wrong_route`.

```json
{
  "error": "Another recovery operation is running on this node.",
  "errorClass": "lock_held",
  "code": "LOCK_HELD"
}
```

| Status | Error classes |
|--------|---------------|
| `400` | `invalid_request` |
| `403` | `permission_denied` |
| `409` | `update_required`, `identity_unknown`, `lock_held`, `lock_stale`, `integrity_mismatch`, `interrupted`, `precondition_failed`, `dependents_changed`, `not_cancellable` |
| `422` | `source_unreadable`, `attributes_not_restored`, `pre_restore_failed` (these end an operation; they are not request errors) |
| `500` | `internal`, `cleanup_failed` (only as the class of a `partial` operation) |
| `503` | `capability_unavailable`, `schema_unsupported`, `repository_unavailable`, `repository_key_unavailable`, `transport_unreachable`, `node_refused`, `node_error`, `fence_unavailable` |
| `507` | `insufficient_space` |

A remote node whose status answer the control instance cannot read answers `503` with `errorClass: "internal"` and `code: "NODE_DESCRIPTOR_INVALID"`. For a remote node, the control instance answers `503` with `errorClass: "transport_unreachable"` whenever it cannot reach the node when the request arrives: a stopped node, a disconnected Pilot tunnel, or a target it will not call. A Pilot tunnel that drops while a request is in flight answers a plain `502`; if that request started something, send it again with the same idempotency key to find out what happened. A per-user permission check the control instance makes itself, before the request reaches the node, answers with `error` and, usually, `code`, and no `errorClass`.

Access is checked before anything about the record is reported. A point in a state the request cannot act on, a volume that cannot be protected, and a restore target that already exists answer `403 permission_denied` to a caller who may not act on that record, the same answer as for a record the caller may not touch. An id that names nothing (an operation, a storage, a point, a volume) answers `403` too, unless the caller holds the access node-wide: a global role, or a role on the node. For an unknown operation id that also means permission to change system settings, because a repository operation needs it. A caller with that access gets the specific `400 invalid_request`. Cancelling a repository provisioning operation, or an overwrite that has started its swap, answers `409` with `errorClass: "not_cancellable"`.

While the node is still starting, a mutating request answers `503` with `errorClass: "capability_unavailable"` and `reason: "engine_starting"`. Wait for startup to finish and retry.

A node whose build predates the overwrite routes answers the preview and the overwrite with `409 UPDATE_REQUIRED` from the control instance, before the request reaches it. Update that node, or restore to a new volume on it.

A `partial` capture is not an HTTP error: the request was admitted, the point is stored as `partial`, and the operation carries `source_unreadable`. Read the operation to see it.
